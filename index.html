摘要

智能体（agent）= 模型 + harness：harness 是把 LLM 与外部世界耦合起来的运行时，它通过循环、工具、上下文管理、安全控制、编排以及扩展接口发挥作用。Harness engineering（harness 工程）于 2026 年初被命名为一门学科，它研究的就是这个运行时的设计与演化。本文为这门年轻的学科提供了迄今最全面的实证基础：对十一个生产级编码 harness 的源码解剖，分别是 Claude Code（Anthropic）、Codex CLI（OpenAI）、Gemini CLI（Google）、Mistral Vibe（Mistral）、OpenHands、Aider、Mini-SWE-Agent、Hermes（Nous Research）、Pi、OpenCode 和 OpenClaw；另外还把 Omnigent（Databricks）作为对照点进行分析，据我们所知，它是第一个 meta-harness（元 harness）。本文界定了什么是 harness，绘制了它的七个标准子系统，并给出每个子系统的最简与最繁实现，然后沿着这些子系统逐一剖析全部十一个系统。本文不做基准测试，也不排名；它描述并比较这些系统是如何构建的。

这次审计得出 13 条横切观察和一份包含 29 种反复出现的设计模式的目录。有两项“缺席”在语料扩大到三倍之后依然成立：在大约四百万行 Python、TypeScript 和 Rust 代码中，没有任何一个智能体运行时导入通用的智能体框架（LangChain、LangGraph、AutoGen 或其他十几种；Gemini CLI 连 Google 自家的两个框架都没有用），也没有任何一个用向量嵌入来检索代码；整个领域运行在手写的异步循环和确定性检索之上（ripgrep、tree-sitter、glob，以及自动发现的 Markdown 上下文文件）。可扩展性标准已经尘埃落定：SKILL.md 形式的 skills 在采用率上领先于 MCP（9/11 对 8/11），并且出现了注册中心、信任分级以及语料中第一批由智能体自己编写的 skill；ACP 已在六个系统中发布，并获得了第三种角色——托管 harness：OpenHands 可以把 Claude Code、Codex 或 Gemini CLI 作为可互换的后端来运行。

由于最初的八个系统是重新固定版本而不是被替换，本研究还包含一个受控的纵向样本：同一批 harness，跨一个季度做源码 diff。这份 diff 显示，趋同正在变成模仿（Codex 逐字采用了 Claude Code 的 hook 词汇，并发布了一个导入其会话和设置的导入器；OpenHands 能读取 Claude Code 的插件格式）；与此同时，行为策略正从提示词文字迁移到配置；四月版中的三条观察需要就地做实质性修订。

这些线索汇聚成本文的核心论点：在 2026 年上半年，编码 harness 完成了从工具到平台的转向。Harness 变成了可导入的 SDK，而框架厂商则开始发布 harness；插件市场、降低转换成本的工具和企业治理层纷纷出现；智能体可以作为一个“模型”，挂在 OpenAI 兼容端点后面被调用；而一个 meta-harness 如今在同一个 API 之后编排十一个厂商 harness（其中一半来自本文语料），自行重新实现昂贵的部分，并对专有的部分进行套利。本文最后给出 18 条锚定于所观察代码的设计建议，以及一个实现了其中十条的 90 行最小可行 harness 脚手架。

1 引言

智能体 = 模型 + harness。模型提供智能；harness 则通过循环、工具、上下文管理、安全控制、编排和扩展接口，把这份智能转化为实际工作。在短短五个月里，harness engineering 从厂商博客中造出的一个短语，变成了一门拥有实践指南、形式化定义、自动演化系统以及自己的 arXiv 谱系的学科（第 2.1 节）。这门学科尚缺的是一份参考：一份以生产源码为依据的说明，讲清 harness 到底是什么、由什么构成，以及该领域的领先实现彼此有何不同。本文就是这样一份参考，并且带着一个论点：harness 已经不再是工具，而是变成了平台。

现有文献两个目标都没有达到。基准综述只报告分数（通常是 SWE-Bench [1]），不触及架构；概念性分类法 [5,6] 只描述模式，不涉及实现；唯一一项同期的源码级分类 [34] 又排除了定义该领域前沿的厂商原生系统。它们都没有深入到那些决定 harness 是否可靠、可扩展、可部署的工程决策：循环如何组织，工具如何定义和沙箱化，安全如何落实，上下文如何配给。它们也都没有追问这个类别本身正走向何方。

我们在源码层面研究了十一个系统，版本固定在 2026 年 7 月的发布版。其中四个是主要商业 LLM 提供商的旗舰产品：Claude Code（Anthropic，TypeScript，基于一份流传的源码快照）、Codex CLI（OpenAI，Rust）、Gemini CLI（Google，TypeScript）和 Mistral Vibe（Mistral AI，Python）。另外七个是开源系统，覆盖了该领域的完整光谱：OpenHands（事件溯源的 SDK，自 2026 年年中起也能托管竞争对手的 harness）、Aider（十三种多态编辑格式）、Mini-SWE-Agent（100 行的研究底线）、Hermes（GitHub 上增长最快的 harness，带有自我改进的 skill 循环）、Pi（主张极简内核的逆潮流者）、OpenCode（star 数最多的专用编码智能体，拥有语料中最彻底的客户端/服务器架构）以及 OpenClaw（一个多渠道网关，是我们的非软件工程对照点）。第十二个系统 Omnigent（Databricks）是第一个 meta-harness，即凌驾于其他系统之上的编排层，我们把它作为第二个对照点进行分析。由于其中八个系统已在本研究 2026 年 4 月版中审计过，它们保留下来的快照构成了一个受控的纵向样本：同一批 harness，跨一个季度做源码 diff。

本文有七项贡献。第一项是这门学科的参考解剖（第 2 节）：给出 harness 的定义、谱系和边界情形，以及七个标准子系统的组件图——每个子系统都附有观察到的最简与最繁实现——它组织了全文其余部分。在这张图之上，本文构建了对十一个 harness 的系统性源码级比较，这是第一个覆盖全部四个厂商原生系统、两个采用最广的开源 harness 以及每个系统招牌能力的语料（表 4）。审计得出 13 条横切观察和一份 29 种反复出现的模式目录，其中若干是首次在此记录：智能体维护的记忆管线、停止前验证守卫（verify-on-stop guard）、谱系压缩（lineage compaction）、会话树版本控制、日志即队列循环（log-as-queue loop）、语法感知的命令权限、缓存方言扇出（cache-dialect fanout），以及 harness 模仿（harness mimicry）。

由于最初的八个系统是重新固定版本而不是被替换，本研究还包含一项纵向分析（第 14.5 节）：用源码度量的九十天 harness 演化。在这期间，趋同变成了模仿（hook 词汇被逐字照搬，插件格式被采纳，会话导入器被发布），模式沿着语料向下扩散，行为策略从提示词文字迁移到配置。有两项实证上的缺席在十一个系统的规模上得到确立，并在语料扩大到三倍后依然成立：没有任何智能体运行时使用通用智能体框架，也没有任何一个对代码使用基于嵌入的检索；它们在历史上的归宿在于 harness 与框架的合并。这一合并引出了平台转向的论点（第 14 节），并以具名产物为证：harness SDK 与基于框架构建的 harness 收敛到同一种形态，带有供应链安全机制的插件和 skill 市场，跨厂商的会话导入器，移动设备管理（MDM）治理，“智能体即模型”网关，以及对第一个 meta-harness 的源码级分析。最后，这些分析被浓缩为一份包含 18 条设计建议的实践者指南，每条建议都锚定于一条被引用的观察和一个实现了它的系统；另附一个 90 行的最小可行 harness 脚手架，它直接实现了其中十条，并与其余建议兼容。

2 什么是 harness？

在比较各种实现之前，我们先确定研究对象。本节定义 harness，追溯这个术语的短暂历史，把它与常被混淆的概念区分开，并列出我们语料中每个 harness 都以某种形式实现的七个子系统。初入这一领域的读者读完本节，应当确切地知道 harness 是什么、由什么构成；本文其余部分则用生产源码逐格印证这张图。

2.1 定义与谱系

智能体 = 模型 + harness。Harness 是除模型之外的一切：把 LLM 与世界耦合起来的运行时——它的循环、工具、上下文、安全控制、编排和扩展接口。Harness engineering 就是设计和演化这一运行时的学科。

“Agent = Model + Harness”这条一行等式，由 Trivedy 在 2026 年初的 LangChain 工程系列文章中推广开来 [28]；harness engineering 这个术语于 2026 年 2 月进入流通：先是 Mitchell Hashimoto 顺带一提，随后 Trivedy 在 LangChain 的 Deep Agents 工作背景下对其作了定义和阐述 [29]。1 这门学科在几周之内就有了自己的实践者文献：Böckeler 面向编码智能体用户的 harness engineering 指南 [30]（4 月）、O’Reilly 和独立作者的综述（6 月），以及社区整理的模式目录。学术界也沿着同样的轨迹跟进：Lin 等人的 Agentic Harness Engineering [85] 让 harness 演化自动化；HARBOR [35] 针对基准优化 harness；Wang 等人把代码本身重新诠释为 harness 的基底 [36]；Rombaut 对十三个开源脚手架的源码分类 [34] 是与本研究在方法上最接近的亲缘工作（第 3.3 节把他的十二个维度映射到我们的七个子系统上）；Macedo [33] 则给出了这一概念的第一个操作性定义，推导出什么算作 harness 的充分必要条件。我们采用 Macedo 定义的核心——包裹语言模型、把它变成能够在代码仓库上行动的智能体的那一层——并用第 2.3 节的子系统分解加以扩展；定义类文献对这种分解有所暗示，但尚未用生产源码加以印证。

2.2 harness 不是什么

这个术语的用法很松散，有四种边界情形造成了大部分混淆 [33]。

  • Harness 不是 scaffold（脚手架）——不完全是。这两个词在实践中几乎是同义词，本文也沿用了自己早期用语中的“scaffold”。在需要区分时，scaffold 指结构性代码（循环、注册表），harness 指嵌入了这些代码、最终交付的运行时产物：Mini-SWE-Agent 的 scaffold 是 100 行 Python；Claude Code 的 harness 则是一个拥有终端 UI、权限系统和插件生态的产品。
  • Harness 不是智能体框架。框架（LangChain、AutoGen、CrewAI）是开发者导入来构建智能体的库；harness 是开发者在其中工作的运行时。这一区分在 2025 年还很清晰，到 2026 年正从两个方向同时消融——这正是第 14.2 节的主题。
  • Harness 不是评测 harness。SWE-bench 的“harness”包裹一个智能体，让它跑任务；智能体 harness 包裹一个模型，让它去行动。同一个词，包裹的方向正好相反。
  • Harness 不是编排器。编排器（或 meta-harness，第 14.4 节）从上方协调一个或多个 harness，自己不实现任何编辑循环。Omnigent 编排十一个厂商 harness——其中五个是本文研究的系统——自己不实现任何编辑循环；它是关于 harness 的证据，而不是其中之一。

2.3 七个子系统

我们语料中的每个系统，从 100 行的研究基线到百万行的生产级 CLI，都必须在同样的七个子系统上表明立场（图 1）——哪怕这个立场是刻意缺席。它们是第 4 节中的分析维度 D1–D7，但我们认为，它们也是这一产物本身的标准解剖：最简实现显示每个子系统能缩到多小——其中一个（编排）甚至缩成刻意的缺席——而最繁实现则显示每个子系统里还蕴藏着多少工程上的余地。表 1 绘出了这份解剖：每个子系统做什么，观察到的最简和最繁形态，以及本文在哪里剖析它。

在这七个子系统之外，还有两个横切面：接口层（TUI、CLI 参数、IDE 协议、HTTP 服务器、SDK），供人和程序驱动 harness；以及会话基底（对话记录、持久化、恢复/分叉），由多个子系统共享。两者在整个语料分析中反复出现，尤其是接口层，承载了第 14 节的平台化论证。

2.4 最小 harness

上面的分解说明了 harness 由什么构成，却没有说明每个部分需要多少。语料在底线处给出了一个存在性证明：Mini-SWE-Agent 用大约 100 行代码实现了全部七个子系统——一个 while 循环、一个模板、一个工具、一个消息列表、两个上限、没有编排，以结构化类型作为它全部的扩展方案——并报告其在 SWE-bench Verified 上的结果与规模大三个数量级的系统处于同一区间。2 第 16 节以一个 90 行的最小可行 harness 收尾，实践者可以复制并加以特化。把底线与生产系统区分开的不是任务完成率，而是本文记录的其他一切：安全、恢复、成本管理、可扩展性，以及越来越重要的第 14 节所述的平台接口。

3 背景与相关工作

3.1 LLM 驱动的代码智能体

把 LLM 用作自主编码智能体的想法，随 SWE-Bench [1] 而兴起；这是一个由真实 GitHub issue 组成、要求端到端解决的基准。SWE-Agent [2] 提出了智能体-计算机接口（Agent-Computer Interface，ACI），为 LLM 提供专门的文件查看和编辑工具。CodeAct 范式 [3] 主张把智能体的动作统一为可执行代码，认为这可以涵盖离散的工具调用。ReAct [4] 则确立了支撑当今大多数智能体架构的推理-行动循环。

此后出现了第二波面向软件工程的智能体。AutoCodeRover [44] 用感知 AST 的检索和基于频谱的故障定位取代了基于文本的搜索。MASAI [48] 把 issue 解决流程拆解为模块化的子智能体，并在 SWE-Bench Lite 上报告了考虑成本的结果。MAGIS [47] 和 CodeR [46] 都把基于角色的多智能体协作形式化，用于解决 issue（MAGIS 中是 Manager/Custodian/Developer/QA；CodeR 中是显式任务图）。Lingma SWE-GPT [49] 把基础模型与软件工程流程循环联合训练，这是我们在第 7 节考察的模型-智能体协同设计的一个实例。SWE-Search [52] 在智能体轨迹之上叠加蒙特卡洛树搜索（延续了 Tree of Thoughts [70] 和 LATS [73] 所发展的基于搜索的推理路线，Plan-and-Solve [71] 是更简单的前身），而 Diversity-Empowers-Intelligence [53] 则在一个元策略下集成多个异构智能体。在设计光谱的另一端，Agentless [51] 报告称，一个固定的“定位/修复/验证”流水线在 SWE-Bench Lite 上可以与智能体循环相匹敌；在讨论智能体式复杂度是否必要时，这是一个有用的反例。OpenHands 平台论文 [45] 为我们在第 6 节审计其源码的那个系统提供了经同行评审的依据。与本研究同期，Lin 等人 [85] 提出了 Agentic Harness Engineering（AHE），利用可观测性驱动的反馈自动演化智能体 harness（工具、中间件、记忆、子智能体配置）。他们的系统从一个与 Mini-SWE-Agent 相当的只有 bash 的种子出发，在 SWE-Bench Verified 上达到 71.9%，而且演化出的 harness 可以跨模型家族迁移。他们的组件级消融实验，为我们通过源码分析独立得出的架构侧重点提供了定量证据：带来提升的是工具、中间件和长期记忆，而单靠系统提示词不行。

3.2 智能体架构综述

已有的智能体架构研究 [5,6,66] 识别出了工具使用、记忆管理和规划等常见模式。Guo 等人 [67] 详细讨论了多智能体维度；Liu 等人 [68] 梳理了面向软件工程的子集；AgentBench [69] 提供了标准的跨领域评测 harness。这些综述停留在概念层面，描述存在哪些组件，而不是它们如何实现。本文与之互补，把架构分析建立在具体实现之上，表明“同一种”模式（例如工具使用）在实践中可以有相当大的差异。

3.3 同期的源码级分类

与本研究方法上最接近的亲缘工作，是 Rombaut 的 Inside the Scaffold [34]，它与我们的四月版同期完成：对十三个开源编码智能体脚手架在固定 commit 上做源码分类，组织为三层共十二个维度（控制架构；工具/环境接口；资源管理），并得出一个有用的发现——大多数智能体是在组合多种循环原语（ReAct、生成-测试-修复、计划-执行、重试、树搜索），而不是只实现其中一种。两项研究是互补的，而非重复。Rombaut 的语料只包含开源系统，偏向面向基准的流水线（AutoCodeRover、Agentless、Moatless Tools、DARS、Prometheus、SWE-agent），并因为缺乏公开源码而明确排除了 Claude Code。我们的语料在源码层面覆盖了全部四个厂商原生 harness（包括那份流传的 Claude Code 快照）、网关和 meta-harness 两个对照点，以及最新的大规模采用系统（Hermes、Pi），并把分析扩展到他的分类未触及的维度：执行隔离之外的权限与安全架构、多智能体编排、扩展接口（hooks、skills、插件、MCP）、提示词内容、智能体间协议，以及第 14.5 节和第 14 节的纵向分析与平台分析。他的十二个维度与我们七个子系统的对应关系如下：控制循环策略、循环驱动和控制流实现细化了我们的 D1；工具集设计、编辑/补丁格式和工具发现策略细化了 D3；上下文检索范式、状态管理、上下文压缩和持久记忆细化了 D4；执行隔离是我们 D5 中“隔离”的那一半；多模型路由是我们 D2 中的一格。在他的用语比我们更精确的地方（循环原语组合），我们采用他的说法。

3.4 面向软件工程的多智能体系统

近期的工作探索了软件工程中的多智能体协作。MetaGPT [7] 给不同智能体分配专门角色（产品经理、架构师、工程师）。独立开发的 ChatDev [50] 围绕聊天链通信组织了一条角色扮演式开发流水线。AutoGen [8] 提供了一个多智能体对话框架。Magentic-One [9] 实现了带专门子智能体的编排器模式。具体到编码，MAGIS [47] 和 CodeR [46] 把角色分解与任务图结合起来，Chain-of-Agents [72] 则在长输入上让子智能体依次处理。本研究中有几个系统包含多智能体模式，使我们能在单一领域内直接比较这些方法。

3.5 语言模型中的工具使用

Toolformer [10] 证明了 LLM 可以学会使用外部工具。Gorilla [11] 表明，在提供文档的情况下，LLM 可以生成准确的 API 调用。ToolLLM [58] 把工具使用评测扩展到 16,000 多个真实 API，AnyTool [59] 则展示了面向大型 API 面的分层工具路由。Model Context Protocol（MCP）[12] 提出了把 LLM 连接到外部工具和数据源的标准接口。本文的分析发现，MCP 已成为跨系统的可扩展性标准，在所研究的十一个系统中有八个采用（全部四个厂商原生智能体，加上 OpenHands、Hermes、OpenCode 和 OpenClaw）。

3.6 厂商撰写的工程指南

与学术综述互补的一条线索，是主要 LLM 厂商直接发布的工程指南。2024 年 12 月至 2025 年 9 月间，Anthropic 发布了一个四篇文章的系列，共同阐述了一套连贯的智能体设计哲学：（i）Building Effective Agents [16]，对比了“工作流”（预定义的代码路径）与“智能体”（由 LLM 主导的动态过程），列举了五种可组合模式（提示链、路由、并行化、编排者-工人、评估者-优化者），并明确告诫不要使用通用智能体框架；（ii）Effective Context Engineering for AI Agents [19]，把“提示工程”重新表述为“上下文工程”，记录了长窗口中的上下文腐化（context rot），并推荐一种偏向通过 grep/tail/文件系统做即时（JIT）检索的混合方法，同时承认预建索引的检索在特定用例中可以补充 JIT 方法；（iii）Writing Effective Tools for AI Agents [18]，在 Building Effective Agents [16] 引入的智能体-计算机接口（ACI）概念之上，建议把工具整合为“少而精”的高信号操作，并报告了通过提示工程优化工具描述在 SWE-Bench 上带来的提升；（iv）How We Built Our Multi-Agent Research System [17]，一个案例研究，报告称带并行子智能体的编排者-工人架构在内部评测上比单智能体基线高出 90.2%，同时消耗的 token 约为单次聊天交互的 15 倍（比较对象是简单的聊天基线，而不是经过优化的单智能体流水线）。

把这四篇文章作为一个整体来读，它们勾勒出一个规范性框架，预见了我们后来在各厂商之间观察到的许多模式。我们把它们作为参考基线，用来评估所研究系统在源码层面的决策（尤其见第 15.1 节）。

3.7 2026 年的 harness 格局

本文研究的语料，是从一个发展速度远超追踪文献的领域中刻意抽取的样本。为本次修订开展的市场扫描（2026 年 7 月）在本文分析的系统之外，识别出二十多个仍在积极维护的编码智能体 harness；表 2 列出了其中最重要的几个。自本研究第一版（2026 年 4 月）以来，有三项进展重塑了语料所处的背景。3

每家厂商现在都在发布 harness，市场正在整合。

在我们深入分析的四个厂商原生系统之外，GitHub 的 Copilot CLI 于 2026 年 2 月正式发布（GA），Amazon 把它的 Q Developer CLI 并入以规格驱动为特色的 Kiro 品牌，xAI 则在 2026 年 5 月发布了 Grok Build [26]——值得注意的是，这是一个闭源二进制程序（据其发布产物判断用 Rust 编写），而其文档描述的却是对开放生态各项约定的全盘采纳：AGENTS.md 上下文文件、MCP 服务器、skills、hooks，以及用于嵌入编辑器的 ACP 服务器模式。整合随之而来：SpaceX 于 2026 年 2 月收购了 xAI，并在 6 月宣布以 600 亿美元收购 Cursor（Anysphere）；Google 在 5 月宣布 Gemini CLI 将过渡到 Antigravity CLI，随后于 6 月 18 日终止了面向消费者档位的 Gemini CLI 服务（企业版 Gemini Code Assist 许可仍保留访问和更新）。Google 的这次过渡既是品牌更换，也是许可上的转向：Gemini CLI 采用 Apache-2.0 许可、公开开发，积累了约 10.5 万个 star，而 Antigravity CLI 则以闭源的 Go 二进制形式发布，没有公开源码——因此，在语料中由厂商公开开发的三个系统（Codex、Gemini CLI、Mistral Vibe）里，有一个现在有了闭源的继任者，而我们固定的 v0.50.0 版本记录下了一条厂商原生 harness 谱系最后一个主要的开源状态。换句话说，harness 层已经不再是一片空白地带：它是厂商会去收购、更换品牌并设置门槛的战略性基础设施。

开源领域有它自己的重心。

OpenCode [24] 如今是 GitHub 上 star 数最多的专用编码智能体（约 18.4 万 star），Hermes [22] 则是 star 增长最快的（发布后五个月内约 21.2 万 star；数据截至 2026-07-10，与表 2 相同）；两者都在本次修订中加入了我们的语料，同时加入的还有 Pi [23]，它是相反的极简内核逆潮流的代表。Block 于 2026 年 4 月把它的 Rust harness Goose 捐赠给了 Linux 基金会旗下的 Agentic AI Foundation，这是我们在该领域发现的第一个厂商中立治理的案例。社区项目 Claw Code [27] 用 Python 和 Rust 重新实现了 Claude Code 的架构，自称是基于 2026 年 3 月那次源码泄露（也是我们的 Claude Code 分析所依据的来源）的净室衍生作品，几天之内就获得约 10 万个 star——这表明 harness 架构本身，而不仅仅是模型访问，就足以引起社区的兴趣。与此同时，一波中国厂商的 harness（阿里的 Qwen Code，它是 Gemini CLI 的分叉；月之暗面的 Kimi CLI；字节跳动的 Trae Agent）把开放权重模型的发布与自家 CLI 绑定在一起。而该领域的开创性系统之一 Aider，事实上进入了社区维护模式（最后一个稳定版发布于 2026 年 2 月），架构上的开发在一个社区分叉（aider-ce）中继续。

一个元层已经出现。

Databricks 于 2026 年 6 月开源了 Omnigent [25]：一个编排层，它把整个 harness（Claude Code、Codex、OpenCode、Hermes、Pi、Cursor）当作通用 API 之后可互换的组件，并添加了跨 harness 的策略、统一的 OS 沙箱以及可在多设备间共享的会话。第 14.4 节把它作为本文的第二个对照点加以分析；它的存在本身就是第 14.1 节平台化论证的一个数据点。

4 研究方法

4.1 系统选择

本研究涵盖十一个 harness 以及一个 meta-harness 对照点，选取标准是它们在三个轴上拉开的差异：设计哲学、成熟度和市场地位（表 3）；第 3.7 节把这份语料置于 2026 年 7 月更广阔的领域中。这组系统包括每家主要商业 LLM 提供商各一个智能体（Anthropic 的 Claude Code、OpenAI 的 Codex、Google 的 Gemini CLI [21]、Mistral 的 Mistral Vibe [20]），以及七个占据不同研究和生产生态位的开源项目——其中有本次修订新增的三个系统：Hermes（增长最快的开源 harness）、Pi（极简内核逆潮流）和 OpenCode（star 数最多的专用编码智能体，具有独特的客户端/服务器拆分）；沿用下来的开源系统是 OpenHands [13]、Aider [14]、Mini-SWE-Agent [15] 和 OpenClaw。它们涉及三种编程语言（Python、TypeScript、Rust），代码规模跨越三个数量级，设计哲学从研究基线一直到完全产品化的 CLI 工具。所有快照都重新固定到 2026 年 7 月可获得的最新发布版（原有系统的 2026 年 4 月快照被保留下来用于纵向比较，第 14.5 节同时使用两者）。

OpenClaw 作为外部对照点。

OpenClaw 是这组系统中的异类。它的 README 把自己描述为个人 AI 助理网关，而不是编码智能体；它覆盖 20 多个消息平台（WhatsApp、Slack、Discord、Signal、iMessage、Matrix 等），并且不带任何原生代码编辑工具（见表 7，其条目为 N/A）。OpenClaw 自己不写代码，而是通过插件（opencode、kimi-coding、github-copilot、copilot-proxy）把编码任务委派给专门的软件工程智能体。把它作为外部对照点纳入，有三个原因。第一，它的插件架构（260 个 SDK 文件、清单驱动的发现机制、严格的导入边界）能把软件工程特有的可扩展性模式，与属于更广泛的智能体平台类别的模式区分开来。第二，它采用了与软件工程优先的智能体相同的横切标准（ACP 会话派生、MCP、agentskills.io Skills），为检验趋同论断提供了一个非软件工程的参照。第三，它展示了网关委派模式：一个消费而非实现编码能力的多渠道助理。Hermes 介于两类之间：它像 OpenClaw 一样是多渠道个人助理网关（Telegram、Discord、Slack、WhatsApp、Signal、CLI），但与 OpenClaw 不同，它带有一整套原生编码工具，因此我们把它当作语料成员而不是对照点，并在相关之处指出它的混合属性。凡是采用计数会受 OpenClaw 是否纳入影响的地方，我们同时报告 11 个系统的计数和 10 个编码 harness 的计数。把趋同论断严格理解为只针对编码智能体的读者，应当使用 10 个系统的数字。

Omnigent 作为 meta-harness 对照点。

Omnigent（Databricks，2026 年 6 月开源 [25]）不是编码 harness，而是凌驾于 harness 之上的编排层：它把 Claude Code、Codex、Cursor、OpenCode、Hermes、Pi 以及用 YAML 自定义的智能体包装在一个通用 API 之后，并添加跨 harness 的策略、统一的 OS 沙箱和可在多设备间共享的会话。由于它不实现自己的编辑循环，把它和语料一起按七个维度打分会犯范畴错误；因此，第 14.4 节把它作为证据来分析：哪些 harness 能力正在向上迁移到元层。

4.2 分析维度

每个系统沿七个维度进行分析：（D1）智能体循环设计；（D2）LLM 集成与模型-智能体协同设计；（D3）工具与动作系统；（D4）记忆与上下文管理；（D5）安全与权限模型；（D6）多智能体编排；（D7）可扩展性机制。所有版本均截至 2026 年 7 月（确切版本见表 3）；对于从本研究 2026 年 4 月版沿用下来的八个系统，我们保留了四月快照并与七月快照做 diff，第 14.5 节报告三个月的 harness 演化在源码层面是什么样子。代码规模数字是在固定快照上测得的近似行数，用于按数量级定位各系统；在不同的计数约定之间，它们不是可复现的度量。

6 智能体循环设计

智能体循环是在 LLM 推理与动作执行之间交替的核心控制流，它是每个软件工程智能体的架构骨干。我们在所研究的系统中识别出三种不同的范式。

6.1 智能体循环范式的分类

全部十一个系统实现的都是 ReAct [4] 模式的变体，但这些实现在复杂度、并发和状态管理上差异巨大。我们识别出三种范式：迭代式动作-观察（九个系统）、反思增强（Aider；Hermes 则把同样的功能挪到了循环的停止条件中），以及协调者-工人（叠加在迭代循环之上的一层，在 Claude Code 和 Codex 中是规定性的，在 Hermes 中由配置开启）。Rombaut 的同期分类 [34] 提出了一个更细致的有用观点：大多数生产级循环是在组合多种原语（ReAct、生成-测试-修复、计划-执行、重试），而不是只实现其中一种；全部四个厂商原生系统如今都提供的计划模式（第 10 节），就是嫁接在 ReAct 上的计划-执行。

围绕这个子系统，该领域的词汇仍在被创造。Loop engineering（循环工程）一词在 2026 年 6 月进入流通，恰好在本研究两份快照之间：Steinberger（OpenClaw 的原作者）把这一转变浓缩成一句广为流传的格言——别再给编码智能体写提示了，“设计能给你的智能体写提示的循环” [31]——几天后 Osmani 为这种实践命名并加以结构化，给循环定出了触发器、拓扑、验证器和停止规则这样一套解剖 [32]。这个新词与本节的主题是互补关系，而非同义词：harness engineering 构建下文剖析的内层动作-观察循环，而 loop engineering 则从外部把这个循环组合成自我维持的外层循环，由外层循环去提示、验证并重新运行智能体，无需人类逐轮编写。两门学科之间的接缝在语料中已经可见，即外层验证循环模式（表 12）：OpenHands 的 /goal 端点让一个 LLM 评审对每次完成的运行做出判断，要么重新提示，要么停止；Hermes 的停止前验证守卫则可以否决内层循环自身的退出——这些 harness 功能的唯一目的，就是在内层循环外面再闭合一个外层循环。

6.2 迭代式动作-观察循环

最常见的模式遵循这样一个循环：构建提示词、LLM 推理、执行工具、收集观察结果。九个系统实现了这一模式，各有特色。

OpenHands：事件溯源的对话引擎。

OpenHands 的循环——自 2026 年年中重构以来位于 software-agent-sdk 仓库而非应用仓库中——是一个事件溯源的对话引擎：一个 LocalConversation 驱动 Agent.step()，每个事件都被追加到一个持久化的 EventLog 中（通过 FileStore 每个事件一个文件，使用基于 flock 的加锁，并通过 SecretRegistry 对密钥做脱敏），而 LLM 看到的历史是当前活动分支的一个缓存投影。对话状态是一棵带有可移动头指针的树，因此重放、分叉和分支导航都是一等公民。每次 step() 只发起一次 LLM 调用，但会把该响应中的所有工具调用作为一个动作批次来执行——可选地通过 ParallelToolExecutor 并行执行，由 tool_concurrency_limit 以及一个按各工具所声明的资源（文件、终端会话、浏览器）加锁的资源锁管理器来控制，因此只有涉及同一资源的调用才会串行（下文 Claude Code 一段和表 18 把它与 Claude Code 的布尔分区作了对比）。StuckDetector 在重新架构后完整保留下来：与 V0 代码库中相同的五种故障场景（重复的动作-观察对、带错误的重复动作、独白循环、交替模式，以及上下文窗口错误循环），现在阈值可配置，并且默认启用。

Claude Code：带并发工具批处理的流式循环。

Claude Code 的循环响应通过 Server-Sent Events（SSE）流式传输，并有细粒度的事件处理（content_block_start、content_block_delta、content_block_stop）。它最独特的功能是智能工具批处理：工具调用通过一个单遍 reduce 算法，按并发安全性划分为若干批次。工具默认 isConcurrencySafe = false（安全的默认值），必须显式选择加入并行执行。只读工具（grep、glob、读文件）是安全的；写工具（编辑、bash）则不是。当 LLM 同时请求多个相互独立的读取时，这种设计能显著降低延迟。

Codex：Tokio 异步状态机。

Codex 的循环用 Rust 实现，是一个基于 Tokio 的异步状态机。一个 Session 结构体通过来自 OpenAI Responses API 的流式 ResponseItem 事件（从 SSE 或 WebSocket 流帧反序列化而来）来编排各个轮次，工具调用通过 FuturesOrdered 处理以实现有序的并行执行，现在被抽取到一个专门的 ToolCallRuntime 中。关键入口点：Codex::spawn() 创建新会话，submit_with_id() 提交操作，next_event() 为流式响应提供非阻塞的事件读取（曾经庞大单一的 codex.rs 已被拆分为 session/ 模块和一个 CodexThread 抽象，但这些入口点保留了下来）。

Mistral Vibe：中间件管线循环。

Mistral Vibe 的循环是一个 Python async/await 迭代循环，其中轮次级策略被抽取到一条可组合的中间件管线中。核心对话循环驱动标准的“提示 → LLM → 工具”周期，但每次迭代都会先走一遍中间件栈的轮前检查，然后在事件完成时把它们交给调用方。开箱即用的中间件有六个：TurnLimitMiddleware、PriceLimitMiddleware（每个会话的成本上限）、TokenLimitMiddleware（会话总 token 上限，在 2.9 系列中加入）、AutoCompactMiddleware（在达到 token 阈值时触发摘要）、ContextWarningMiddleware（在对话接近上下文窗口上限时发出警告）以及 ReadOnlyAgentMiddleware（为只读智能体配置屏蔽写工具）；用户取消则通过 is_user_cancellation_event() 检查内联处理，而不是做成中间件。同一次 LLM 响应中的工具调用是并发执行的：每个工具都作为 asyncio.create_task() 派生出去，完成一个就产出一个事件，这是 Codex 的 FuturesOrdered 的一种更细粒度的变体。中间件设计在语料中独一无二。新的轮次级策略可以在不修改循环体的情况下加入，同一个循环只需更换中间件组合，就能驱动六个已注册的智能体配置（default、plan、accept-edits、auto-approve、explore、lean）；第七个 chat 配置不为 CLI 会话注册，而是由 ACP 层为 IDE 集成动态注册。与此同时，计划模式已经从仅靠提示词变成了结构性的：专门 plans 目录下的一个计划文件是该配置唯一可写的目标，而一个 exit_plan_mode 工具会发出 PlanReviewRequestedEvent，以此把关返回可写配置的转换。

Gemini CLI：带混合循环检测的异步生成器循环。

Gemini CLI 的循环用 TypeScript 实现为一个异步生成器。每次迭代都向 UI 产出带类型的 ServerGeminiStreamEvent 元组，通过 ModelRouterService 运行当前模型，通过 @google/genai SDK 流式接收响应，并通过一个状态机式的 Scheduler 分派函数调用，让每个工具依次经过“校验中 → 执行中 → 已完成/出错”。一个独特的功能是 LoopDetectionService，它是混合式的，而非纯确定性的：SHA-256 哈希低成本地捕捉常见的故障模式（五次相同的工具调用或十个相同的内容块会中止循环），而在单个提示内超过三十轮之后，会以自适应的间隔运行一次基于 LLM 的自检——这种两层设计与 OpenHands 手工列举的五种场景形成对比。会话轮次上限（默认 100）提供硬性天花板，一组十一个生命周期 hook 事件（BeforeAgent/AfterAgent、BeforeModel/AfterModel、BeforeToolSelection、PreCompress 等）让扩展可以检查或否决循环。调度器并行执行工具调用，并且从 v0.45 起按并发安全性分区：修改文件的工具（edit、write_file）和 update_topic 被强制串行执行，而且——在语料中独一无二——模型本身也被赋予一个并发旋钮：每个工具 schema 上都会自动注入一个 wait_for_previous 布尔值，模型可以借此把任何调用串行化。调度器通过 outputUpdateHandler 回调把实时工具输出流式推送到 UI，让用户看到长时间运行的命令的进度。

Hermes：带预算和停止守卫的循环。

Hermes 在每个用户轮次中运行一个单一的迭代式工具调用循环，由一个线程安全的 IterationBudget 限定（默认 90，execute_code 的迭代会被返还，预算耗尽时还有最后一次宽限调用，让模型做总结）。它的独特之处不在循环体，而在出口：十一种列举出来的轮次退出原因，以及两个可以否决过早的最终答案的停止守卫。停止前验证守卫的做法是：只要本轮修改了代码文件却没有产生新的验证证据，就把纯文本响应改写成一次继续——这正是反思循环的功能，只是从循环内部挪到了停止条件上，成本只是其一小部分。卡死检测对“工具名 + 排序后的 JSON 参数”做哈希（SHA-256），两次相同的失败后发出警告，八次后停止——但硬停止在发布时是关闭的：默认姿态是把警告追加到工具结果中，相信模型能自我纠正。工具批次只有在每个调用都是只读安全的，或者都限定在互不重叠的路径前缀内时，才会在一个八个 worker 的池上并行；轮次中途的用户引导会被拼接进最后一个工具结果，放在一个防注入标记之后。

Pi：带引导队列的函数式内核。

Pi 的循环是语料中仅次于 Mini-SWE-Agent 的最纯粹的迭代实现：一个约 790 行的函数式内核，没有规划器，没有反思步骤，没有轮次上限，没有卡死检测，也没有成本熔断开关——循环一直运行到模型不再调用工具为止，而所有这些缺席都是有文档记载的设计上的拒绝。有两个原语很突出。运行中途的用户输入是一等公民：一个 steer() 队列在当前轮次的工具调用之后注入消息，而 followUp() 只在智能体本来要停下时才被取出。工具调用默认通过 Promise.all 并行执行，由一个以 realpath 为键的逐文件修改队列来串行化编辑；还有一个独特的“截断中毒”防护：当助手消息在长度上限处被截断时，它的所有工具调用都会被判为失败而不执行，因为从流式输出中抢救解析出来的参数可能通过校验，却悄无声息地不完整。恢复机制是分层的而不是逐一列举的：一个约 40 种模式的瞬时错误重试白名单，以及在上下文溢出时进行一次“压缩后重试”。

OpenCode：日志即队列的循环。

OpenCode 的循环就是一个字面意义上的 while(true)，但有一个不寻常的变化：消息日志同时充当工作队列。待处理的子智能体派生和压缩不是控制流分支，而是被持久化的消息片段，循环每次迭代从中出队一个——这让循环在进程重启后可以轻而易举地恢复，因为队列就是对话记录本身。默认没有步数上限（maxSteps 默认为无穷大）；当达到配置的上限时，harness 会追加一条声明“工具已禁用”的助手消息，而不是抛出错误。卡死检测只有一条启发式规则，而且很有特色地经由权限系统处理：连续三次逐字节相同的工具调用会触发一次 doom_loop 权限询问，而不是自动中止——由用户而不是 harness 来决定这种重复是不是 bug。并行工具调用并发执行，harness 不设上限；重试在 harness 层进行，使用感知 retry-after 的指数退避；上下文溢出从不重试——它会转去执行压缩。

6.3 反思增强循环

Aider 用反思机制扩展了基本循环。run_one() 方法实现了一个嵌套循环：每次 LLM 响应之后，系统先应用编辑，然后检查 lint 错误（通过一个三阶段的 Python 流水线：语法检查 → 编译检查 → flake8）、测试失败和未解决的文件提及。如果发现问题，一条 reflected_message 会带着纠正性上下文重新调用 LLM，直到达到可配置的上限（默认：3 次反思）。

Linter 集成尤其值得注意：它使用 grep_ast 中的 TreeContext 显示错误行周围的代码上下文，为 LLM 的纠正提供精确的定位信息。Aider 仍是唯一一个主循环呈反思形态的系统，但语料中已出现了三个结构上的近亲：Gemini CLI 的编辑工具以一个修复匹配失败的 LLM“编辑修复器”子调用收尾（第 8.4 节），OpenCode 把 LSP 诊断信息反馈到每一个编辑结果中，Hermes 的停止前验证守卫则在轮次退出时执行一次反思检查，而不是每次迭代都检查。这种模式是语言模型自我纠正这一研究脉络——Reflexion [54]、Self-Refine [55]、CRITIC [56] 和 Self-Debug [57]——在实际系统中的落地，而这条脉络在其他地方大多仍停留在学术文献中。Aider 的贡献在于集成：lint 和测试信号被导回循环，成为那些论文从理论上讨论的纠正反馈。关于它的停止条件，需要说明一点：Aider 根本没有工具调用循环——补全流结束时一个轮次就结束，当没有待处理的反思或达到上限时 run_one 退出；它从不检查 end_turn 结束原因。

6.4 协调者-工人模式

Claude Code 和 Codex 支持一种协调者模式，由一个父智能体编排多个工人智能体；Hermes 则把同样的形态放在配置开关之后（一个 orchestrator 角色加上一个派生深度设置可以解锁嵌套的委派树，另有一个独立的看板蜂群（Kanban-swarm）模式，以子进程的方式在一块 SQLite 黑板上运行“规划根节点 → 工人 → 验证者”）。这是叠加在迭代循环之上的一层，增加了一个分层的分派层。

在 Claude Code 中，协调者通过 AgentTool 派生子智能体，每个子智能体获得一份分叉的上下文，带有独立的 AbortController、克隆的文件状态缓存，并屏蔽权限对话框。工人通过 <task-notification> XML 块回报结果，协调者在委派下一阶段之前综合各方发现。工作流是结构化的：调研 → 综合 → 实现 → 验证。

在 Codex 中，子智能体通过 AgentControl::spawn_agent() 派生，获得专属的 ThreadId，并通过带类型的 Mailbox 通道通信。每个线程维护自己的历史，SpawnAgentForkMode 控制上下文的继承方式（FullHistory 或 LastNTurns(N)）。

7 LLM 集成与模型-智能体协同设计

智能体脚手架与其底层 LLM 之间的关系，是系统中影响最深远的设计决策之一。语料覆盖了从单一提供商紧耦合到完全与提供商无关的整个范围，而在这条光谱上所处的位置，直接决定了脚手架能用上哪些优化。

7.1 提供商抽象光谱

十一个系统采用了五种不同的策略：

单一提供商紧耦合（Anthropic、OpenAI、Google）。

Claude Code 只使用 Anthropic SDK（@anthropic-ai/sdk）；Codex 使用 OpenAI Responses API 并通过 WebSocket 流式传输；Gemini CLI 使用 @google/genai SDK，并为企业部署额外耦合 Vertex AI。这些系统很难切换提供商：Claude Code 依赖 Claude 特有的功能（扩展思考、带静态/动态边界的提示缓存、tool_use 块格式）；Codex 依赖 OpenAI Responses API 的线上格式，并为每一代 GPT 维护专门的提示词，截至 2026 年年中，这些提示词以运行时刷新的服务端模型目录数据的形式下发，而不是编译进去的模板（第 7.2 节）；Gemini CLI 运行一个 ModelRouterService，通过一条可插拔策略链（后备、覆盖、审批模式、三种分类器策略——其中一种可以通过托管的 LiteRT-LM 运行时针对本地 Gemma 模型运行——以及默认策略），把每个请求分派给某个 Gemini 变体。在我们的两份快照之间，路由器的目标集合整整换了一代模型：gemini-3(.1)-pro-preview 和正式版 gemini-3.1-flash-lite 现在是默认的解析目标，Gemma 4 模型可以被路由，而 2.5 系列只作为无预览权限时的后备保留下来——这证明路由层的存在恰恰是为了吸收模型更迭，让循环不必为此改动。

以本家提供商为先、辅以通用后备（Mistral）。

Mistral Vibe 处在紧耦合与完全抽象之间：一个工厂在 MistralBackend（使用官方 mistralai SDK）与 GenericBackend 之间做选择，后者能对接 Anthropic、Vertex、OpenAI 兼容端点，以及自 v2.9 起的 OpenAI Responses 端点。Mistral 后端利用 Mistral 特有的功能（由模型五档 thinking 字段映射而来的 reasoning_effort 枚举，以及被解析到独立 reasoning_content 字段中的 ThinkChunk 流块），而通用后端提供了一个可移植的逃生口。这与基于 LiteLLM 的系统是不同的哲学：Mistral Vibe 不是对所有提供商一视同仁，而是给本家提供商更深的集成，把其他提供商当作后备。

通过抽象层支持多提供商。

OpenHands、Aider 和 Mini-SWE-Agent 都把 LiteLLM 用作通用抽象，支持各提供商的 100 多个模型。这让快速切换模型成为可能，但也引入了对 LiteLLM 提供商映射的依赖。Aider 走得最远，它有一个模型注册表，包含 350 多个模型的逐模型元数据：编辑格式、弱模型名称、缓存控制、额外 API 参数以及推理标签的处理方式。与此同时，OpenHands 在抽象层之上叠加了自己的路由：一个按用途索引的 LLMRegistry、一个用于具名配置的独立 LLMProfileStore、可插拔的 RouterLLM 实现，以及一套后备策略——因此“基于 LiteLLM”已不再意味着功能最少。

通过自有传输层支持多提供商。

本次修订新增的三个系统占据了四月版四分光谱中不存在的一个位置：完整的多提供商支持，却不使用任何抽象库，提供商矩阵由手工构建，打磨深度与厂商原生集成相当。Hermes 在 29 个声明式的 ProviderProfile 插件之后提供五种传输实现（chat-completions、Anthropic Messages、Bedrock Converse、Codex Responses，以及一个进程外的 Codex app-server）——配置文件“由传输层读取，而不是传进去 20 多个布尔标志”——并从 models.dev 拉取 3,800 多个模型的元数据。Pi 在 35 个内置提供商之上手写了九种线上协议实现，用约 20 个逐模型的 compat 怪癖标志（其中包括面向 OpenAI 兼容主机的十种 thinkingFormat 方言），把逐提供商的条件分支成本集中地一次付清——它还使用了语料中最大胆的耦合技巧：harness 模仿。在 Claude Pro/Max 的 OAuth 令牌下，它整套地冒用 Claude Code 的身份（“You are Claude Code”这句系统提示词开头、beta 请求头，甚至连标准的工具名大小写都在线上被改写成一致），借此搭上消费者订阅；它也用同样的方式对接 ChatGPT 套餐的 Codex 后端。OpenCode 把流式传输和工具分派交给 Vercel 的 AI SDK 和 models.dev 注册表——它是语料中唯一一个内部 LLM 管道是第三方 SDK 的系统——然后把协同设计集中在一个约 1,400 行的逐厂商变换矩阵中（按发布日期门控的推理档位、逐模型的 temperature 默认值、六种同时生效的提示缓存方言），甚至还能根据注册表中的一个字段在运行时安装新的提供商。

基于插件的混合方式。

OpenClaw 实现了一个可插拔的提供商系统，为 10 多个提供商提供一方适配器，具备认证配置轮换、为故障转移记录最近一次可用的配置，以及对降级密钥的冷却期过期处理。

观察 2。提供商原生的优化——缓存边界、扩展思考、推理强度、针对特定模型的提示词——并不取决于是否紧耦合，而取决于由谁来承担逐提供商条件代码的成本。Claude Code 在一个经 Blake2b 哈希的缓存边界处切分提示词，其静态前缀以全局范围跨会话缓存（分叉模式的子智能体还会逐字节地继承父提示词）；Codex 保留按代际划分的提示词（现在以服务端模型目录数据的形式下发）以及由 thread_id 派生的提示缓存键；Gemini CLI 的 ModelRouterService 把每个请求分派给够用且最便宜的 Gemini 变体。但现在有三个多提供商系统从光谱的另一端使用着同一份菜单，方法是刻意且集中地承担条件代码的成本：Hermes 手写了五个传输层，带有与提供商无关的缓存标记和逐位精确的前缀规范化，连本地 llama.cpp 的 KV 缓存都能命中；Pi 放置显式的 cache_control 断点并带有 TTL 分层，还把每轮缓存未命中所浪费的金额作为一等指标来审计；OpenCode 同时发出六家提供商的缓存方言，并把系统提示词限制为最多两条消息（默认一条）以匹配缓存槽位。基于 LiteLLM 的系统（OpenHands、Aider、Mini-SWE-Agent）只用到了菜单的一部分（表 17），其中 OpenHands 通过分缓存层级的提示词组装和可插拔路由缩小了差距。紧耦合仍然独有的收益是服务端协同演化：Codex 脚手架的行为——提示词、推理档位、工具模式，甚至多智能体工具的生成——都可以随每次模型发布，通过提供商的目录端点重新调校，而无需发布客户端。厂商耦合的意义已经不那么关乎能力，而更关乎由谁掌控更新回路。

7.2 提示工程架构

十一个系统的提示词构建策略差异极大。表 6 总结了各自的做法。

Gemini CLI：按能力门控的片段与分层记忆。

Gemini CLI 的 PromptProvider 用以下内容组装系统提示词：按模型能力选择的基础指令（isModernModel ? snippets : snippets.legacy）、来自注册表的工具/函数声明，以及在三个范围内发现并分层合并的一组 GEMINI.md 文件（全局 ~/.gemini/、扩展提供的、项目本地 .gemini/）。IDE 诊断信息和已打开文件的 diff 通过 IDE 配套包在对话中途注入；持久性事实由模型直接用普通编辑工具修改 GEMINI.md 或私有的逐项目 MEMORY.md 索引来写入——系统提示词明确说明不存在 save_memory 工具（第 9.6 节）。与 Claude Code 不同，提示词在每次更换模型时重建，但不按静态/动态缓存边界切分——Gemini 目前不提供请求级的提示缓存，因此缓存摊销交由 API 服务器负责。

Mistral Vibe：逐智能体的 Markdown 提示词。

Mistral Vibe 的提示词是普通的 Markdown 文件；只有 explore 和 lean 配置自带专门的系统提示词，而 plan、accept-edits 和 auto-approve 通过覆盖复用默认的 cli.md。一个通用的系统提示词构建器把基础提示词与自动生成的工具描述、一个 Git 上下文块（git log --oneline -N --decorate 和 git status --porcelain 的输出，带缓存）以及一个智能体专属的覆盖层组合起来，因此 plan 和 explore 子智能体得到的系统提示词与默认智能体完全不同，却无需任何代码分支。Skill 描述被动态追加。这种逐智能体的专门化比 Claude Code 的“共享提示词 + 子智能体提示词覆盖”更细粒度，在结构上与 Codex 针对特定模型的模板相似，只不过是以智能体配置而不是模型代际为键。

Claude Code：带缓存边界的模块化组装。

Claude Code 的提示词由十几个具名段落组装而成，中间由一个 SYSTEM_PROMPT_DYNAMIC_BOUNDARY 标记分隔。边界之前的段落（身份、系统规则、任务指导、工具模式、语气）是静态的，通过 Blake2b 哈希以 scope: ’global’ 缓存。边界之后的段落（会话指导、记忆、环境、MCP 指令、语言、草稿区）是动态的，每轮通过带记忆化的 systemPromptSection() 计算。这种设计最大限度地减少了提示缓存失效：静态前缀（占 token 的大部分）在各轮之间、甚至在各子智能体之间（通过分叉时共享 renderedSystemPrompt）都能获得很高的缓存命中率。

Codex：以服务端下发数据形式存在的逐模型提示词。

Codex 为每一代模型维护单独的提示词，而下发机制本身也在协同演化：早期版本中编译进去的 Markdown 模板仍留在代码树里，但已不再被代码引用——真正生效的提示词作为一份模型清单（models.json，内置作为后备，并带 ETag 缓存地从远程 /models 端点刷新）中的 base_instructions 字段下发。七月的清单覆盖从 GPT-5.2 到 GPT-5.6 家族，提示词按人格模板化：一个 {{ personality }} 变量被填入用户可选的变体（friendly/pragmatic）。提示词的内容在各代之间有可测量的漂移：GPT-5.2 的提示词以版本身份开头（“You are GPT-5.2 running in the Codex CLI…”），并带有明确的禁止提交和禁止引用格式的规则；GPT-5.5 的提示词以“You are Codex, a coding agent based on GPT-5…”开头（5.6 家族进一步缩短为“You are Codex, an agent based on GPT-5”），扩写了内容丰富的 Personality 段落，并完全删去了禁止提交规则和反镀金指令。行为策略正从提示词文字迁移到功能开关：一个 codex_git_commit 开关现在掌管提交行为。第 7.3 节会再回到这种“变薄”的现象。

OpenHands：带缓存分层的提示词注册表。

OpenHands 用一个 PromptRegistry 取代了它的 Jinja2 PromptManager；注册表由带守卫条件、有序的 PromptSection 对象组成，分别归入 CacheTier.STATIC 和 DYNAMIC，渲染成一条两块的系统消息，其静态前缀保持字节稳定，以便利用提供商的提示缓存——这与 Claude Code 的静态/动态缓存边界是同一种设计，却是在一个基于 LiteLLM 的多提供商系统内部独立得出的。它自带十八个具名静态段落（Soul、Role、Memory、Security、SecurityRiskAssessment、VersionControl 等），Jinja 模板只作为逃生口保留。

Hermes：带逐位精确前缀的三层组装。

Hermes 每个会话只构建一次提示词，分为三层——稳定层、上下文层、易变层——约 15 个指导块按模型家族门控（强制工具使用的指导块会发给 GPT/Codex/Gemini/Grok/Qwen/DeepSeek 模型，从不发给 Claude，代码注释中引用了各模型实际观察到的失败案例）。细节由缓存经济学驱动：单一的 system_and_3 策略放置四个 cache_control 断点，并对提示词前缀做逐位精确的规范化（工具调用 JSON 排序后紧凑地重新序列化、只到日期的时间戳、冻结的记忆快照），从而连本地 llama.cpp 和 vLLM 的 KV 缓存都能跨轮命中。

Pi：一个随工具集变化的小型构建器。

Pi 的整个系统提示词是一个约 170 行的构建器，输出 30–40 行内容：人格、工具列表、去重后的逐工具指南片段（每个工具贡献 promptSnippet/promptGuidelines，因此提示词随当前工具集变化）、来自 AGENTS.md 的 <project_context>、一个 <available_skills> XML 索引、日期和 cwd。几乎所有行为策略都被刻意省略，交给用户提供的上下文文件和扩展。

OpenCode：模型家族提示词矩阵。

OpenCode 按模型 id 子串分派九种基础提示词之一——claude、gpt-、gemini 等各自有专门的 .txt 提示词，语气各不相同（Claude 提示词的开头是“You are OpenCode, the best coding agent on the planet.”）——把 Codex 按代际划分的模板推广到了不同厂商。组装时刻意把系统提示词限制为两条消息（默认一条；插件扩展后的提示词会被重新合并），以匹配它同时用六种提供商方言发出的两个前置缓存断点槽位。

Aider：多态提示词。

Aider 的提示词系统独一无二：它的 13 种已注册编辑格式（architect、ask、context、diff、diff-fenced、editor-diff、editor-diff-fenced、editor-whole、help、patch、udiff、udiff-simple、whole）每一种都有一个专门的 CoderPrompts 子类，定义针对该格式量身定制的系统提示词、示例和提醒。5 一个工厂模式（Coder.create()）根据模型的元数据选择格式。提示词动态包含：文件内容、受 token 限制的仓库地图（通过 tree-sitter 符号提取生成）、聊天历史，以及特定格式的编辑说明。

Mini-SWE-Agent：一次性模板。

Mini-SWE-Agent 使用嵌入在 YAML 配置文件中的 Jinja2 模板，在会话开始时渲染一次。模板变量包括系统信息（platform.uname()）、模型统计（n_model_calls、model_cost）和任务描述。一个值得注意的细节：默认模板包含针对特定操作系统的说明（例如 macOS 上的 sed -i ’’）。

7.3 提示词内容与修辞风格

上一小节考察了提示词是如何组装的（缓存边界、模板、分层合并）。现在我们转向它们实际说了什么：每个脚手架投射出的人格、它向模型发出的明确指令，以及它为让这些指令“记得住”而使用的修辞手段。我们阅读了每个系统的标准系统提示词，提炼出若干反复出现的维度。有几种模式在彼此毫无关联的代码库之间呈现出趋同。

身份与人格。

人格开场白从简短到繁复不一而足。Mini-SWE-Agent 最简洁：“You are a helpful assistant that can interact with a computer”——不过 Pi 的内部智能体库比它更简（“You are a helpful assistant.”），编码层只补充一句“You are an expert coding assistant operating inside pi, a coding agent harness.”。OpenHands 加了一个角色：“You are OpenHands agent, a helpful AI assistant that can interact with a computer to solve tasks”——现在被包在一个从用户可覆盖的 SOUL.md 加载的 <SOUL> 块里。Codex 的 GPT-5.2 提示词在模型耦合上最为直白：“You are GPT-5.2 running in the Codex CLI, a terminal-based coding assistant”——GPT-5.5 这一代放弃了这个开头，改为“You are Codex, a coding agent based on GPT-5…”（5.6 家族进一步缩短为“an agent based on GPT-5”），并配上一个繁复的 Personality 段落。OpenCode 按模型变换人格：Claude、Codex 和 Meta 的模型被告知“You are OpenCode, the best coding agent on the planet”，而默认谱系得到的是朴素的“an interactive CLI tool that helps users with software engineering tasks”。Hermes 先叠加一个通用身份（“You are Hermes Agent…created by Nous Research…prioritize being genuinely useful over being verbose”），只有在自动检测到编码场景时才注入编码姿态：“Operate like a careful senior engineer.”。Mistral Vibe 在四月版中以对过往行为的抱怨开场（“CRITICAL: Users complain you are too verbose”），现在则以一份正式的指令层级契约开场：七个优先级（critical > 用户 > 仓库 AGENTS.md > 用户 AGENTS.md > 提示词默认值 > skills/MCP > 外部数据仅作数据）——把提示注入防御表达为一个排序，而不是一串禁令。Aider 完全回避人格，代之以一句角色声明：“Act as an expert software developer. Always use best practices when coding.”。Claude Code 介于两极之间，开头很短，随后在后面的段落中大量展开。

简洁度控制。

十一个提示词中有九个包含明确的简洁度指令，但实现方式差别很大。OpenCode 现在是语料中最激进的：“You MUST answer concisely with fewer than 4 lines…One word answers are best”，还配有 <example> 块（“user: what is 2+2? assistant: 4”）——不过值得注意的是，它针对 Claude 的提示词删掉了这条量化规则，而后备谱系仍保留着。Mistral Vibe 保留了 150 词的预算（“Most tasks need under 150 words of prose”）和结构优先规则（“Structure first. Prose after, if at all”）。Claude Code 的回复长度规则是量化的（工具调用之间的更新不超过 25 词，轮次结束时的总结不超过 100 词）——不过我们的复核发现，这个数字段落只在 Anthropic 内部构建中作为 A/B 实验启用；外部用户收到的是定性指导。Codex 在 5.2 这一代是定性的（“concise, direct, and friendly”）；5.6 的提示词把简洁度并入 Personality 段落，而 5.5 保留了自己的长度规则。Hermes 是定性的（“Be concise: lead with the change or answer, not a preamble”），Pi 极简（只有一条要点：“Be concise in your responses”），Aider 要求在任何补丁之前写“a few short sentences”。Mini-SWE-Agent 通过结构而非措辞达到同样的目的：每轮恰好一个 THOUGHT 块，后接一条 bash 命令。OpenHands 是唯一一个基本把简洁度交给模型自己的系统：它的基础提示词对长度只字未提，不过其针对 GPT-5 家族的模型专属块确实要求简洁回复和简短的开场。

禁用短语与被禁止的表面形式。

Mistral Vibe 开创了禁用短语清单；它重写后的提示词把四月的两份清单合并成了一份：“No filler words: ‘robust’, ‘elegant’, ‘seamless’, ‘powerful’, ‘Great!’, ‘Absolutely!’, ‘Of course!’, ‘Happy to help!’”——直接尝试压制 LLM 的语域口头禅。OpenCode 现在维护着语料中的第二份禁用短语清单，而且因模型而异：它的 GPT 提示词禁止“Done —”和“Got it”之类的开头，以及 emoji 和破折号。Mistral Vibe 还保留着语料中最严格的 emoji 禁令：“No emoji of any kind. No smiley faces, icons, flags, or Unicode symbols…This applies to prose, code comments, and commit messages.”。Claude Code 是有条件的（“Only use emojis if the user explicitly requests it”），OpenCode 在它的 Claude、默认、Meta 和 Trinity 提示词中带有完全相同的条件规则，而它的 GPT 提示词彻底禁止 emoji，它 GPT-4 时代的 beast 提示词反而要求用 emoji 作状态标记；Gemini CLI、Mini-SWE-Agent、Aider、Hermes 和 Pi 对 emoji 只字未提。Codex 的 5.2 提示词禁止一种 CLI 特有的表面形式——形如 [F:README.md L5-L14] 的内联引用（带方括号引用符号）——因为 Codex 终端无法渲染它们；5.5/5.6 的提示词中已没有这条规则。

反镀金指令。

一个近乎普遍的模式：脚手架告诉模型不要扩大请求的范围。Claude Code：“Don’t add features, refactor code, or make ‘improvements’ beyond what was asked”，另有单独一条反对投机性抽象。Mistral Vibe（自四月以来换了措辞，但实质保留）：“Change minimally…Don’t touch what wasn’t asked. Unused imports may have side effects. Redundant-looking code may be load-bearing. When fixing X, leave Y alone.”。Codex（5.2 这一代）：“Do not attempt to fix unrelated bugs. … Fix the problem at the root cause rather than applying surface-level patches”——5.4 的提示词中已没有，5.6 则完全删除。OpenHands：“NEVER create multiple versions of the same file with different suffixes (e.g., file_test.py, file_fix.py, file_simple.py).”。OpenCode：“NEVER create files unless they’re absolutely necessary.”。Hermes：不做超出请求范围的顺手重构、重命名或重新格式化。这种趋同令人瞩目——六个独立开发的脚手架都预见到了同一种故障模式（LLM 在需求不明确时会过度交付），并以修辞上同构的措辞来应对，尽管并非逐字照搬。Pi 是刻意的例外：它的提示词里没有这类指令，策略被整体交给用户提供的 AGENTS.md 和扩展。

先读后改与先验证后声称。

有三个提示词把阅读代码作为编辑的前提。Claude Code：“In general, do not propose changes to code you haven’t read.”。Mistral Vibe 在两份快照之间加强了它的版本：“Never edit a file you have not read in this session. Do not edit a file in the same turn you first read it—read, then act on the next turn.”。OpenCode 的编辑工具描述声称会强制执行（“This tool will error if you attempt an edit without reading the file”）——但该工具的源码中并不存在运行时的读取追踪；描述言过其实，这提醒我们提示词文字只是行为上的愿望，而不是机制。Claude Code 还禁止虚假的成功声明——“Never claim ‘all tests pass’ when output shows failures, never suppress or simplify failing checks (tests, lints, type errors) to manufacture a green result”——这一段和它的字数预算一样，先发给内部构建；Hermes 是唯一一个把同样的要求机制化的系统，靠的是第 6 节的停止前验证守卫，外加一条通用的反捏造指令（“NEVER substitute plausible-looking fabricated output…”）。其他系统则把这一点视为不言自明。

Git 提交策略：一次已经瓦解的趋同。

在 2026 年 4 月，这是语料中最紧密的修辞趋同：每一个提到 git 的提示词都禁止自主提交。到了七月，局面分成了三路。这条禁令保留在 Claude Code（“NEVER commit changes unless the user explicitly asks you to”）、OpenCode（“NEVER commit changes unless the user explicitly asks”）、Hermes（“don’t commit, push, or rewrite history unless asked, and never read, print, or commit secrets”）以及 Codex 5.2 代的提示词中。Mistral Vibe 掉转了方向：它删除了标为“Never Commit”的硬规则（变更日志写着“Loosened the no-git-commit constraint”），现在反而主动教模型如何提交，并强制附上 Co-Authored-By 签名尾注。OpenHands 从来就没有可以撤销的提交禁令——它的 <VERSION_CONTROL> 段落早在这个时间窗口之前就一直在教带共同作者尾注的提交方法——同时在单独的 <PULL_REQUESTS> 段落中，把 push 和创建 pull request 限定为必须由用户明确要求。而 Codex 最新的提示词完全删掉了这条规则：GPT-5.6 的指令中一次都没有出现“commit”。一个 codex_git_commit 开关曾短暂掌管提交署名行为，但到七月快照时已被弃用（不再使用）——这条指令就这样离开了提示词。仍然普遍成立的是外层边界：语料中没有任何提示词允许自主 push、强制 push 或改写历史。换句话说，四月的提交趋同并不是一个稳定的工程结论，而是信任校准的一张快照——而信任在一个季度内发生了可测量的变化。

强调标记。

语料中有三种不同的提示词内强调惯例。Claude Code、Codex、OpenHands 和 OpenCode 使用内联的大写标记：IMPORTANT:、CRITICAL:、NEVER（OpenCode 还在运行时注入 <system-reminder> XML）。Mini-SWE-Agent 使用类 XML 标签（<important>…</important>），Pi 只把 XML 用作数据分隔符，Hermes 则把 MUST/NEVER 大写与对勾/叉号的范例对结合起来——并且只把它的 XML 标签强制块发给 GPT/Codex 和 Grok 模型。Aider 几乎不用强调——它的约束来自补丁格式示例，而不是加重语气的文字（补丁格式说明中还残留着一个零星的 IMPORTANT:）。Mistral Vibe 走得最远：CRITICAL: 标记和 Hard Rules 段落都已不复存在；强调现在完全是结构性的，是一份明确的可覆盖性契约，分为名为“Critical instructions—not overridable”和“Overridable defaults”的段落。这种对比暗示了三个流派：修辞式强调（大写标记）、结构式强调（具名规则块和优先级契约）以及示例驱动的强调（范例对和格式样例），大多数系统至少结合其中两种。

工具使用哲学。

工具使用指导的具体程度各不相同。Claude Code 坚持用专门工具而不是 shell：“Do NOT use the Bash tool to run commands when a relevant dedicated tool is provided. … Using dedicated tools allows the user to better understand and review your work.”。Codex 为并行而优化：“Parallelize tool calls whenever possible—especially file reads.”。Aider 的说明是格式机械式的：“Your entire response containing the patch MUST start with *** Begin Patch on a line by itself. … Each file MUST appear only once in the patch.”。Mini-SWE-Agent 限制最严：每轮恰好一个 bash 块，目录和环境变量的改变要以内联前缀写出（MY_VAR=val cd /path && …），因为每次调用都运行在一个新的子 shell 中。

明显缺席的内容。

十一个提示词中没有一个包含明确拒绝有害请求的措辞。没有“如果用户要求你做 X，就拒绝并解释原因”这种形式的指令——唯一带有拒绝意味的文字涉及的是操作风险（破坏性的 git 操作、密钥卫生、危险的 shell 模式），而不是策略层面的危害。语料中最接近的是拒绝礼仪：OpenCode 的默认提示词沿用了早期 Claude Code 的措辞，指示模型在拒绝时不要说教原因（“keep your response to 1-2 sentences”）——这是对一次拒绝的风格指导，而拒绝的依据从未说明。防范滥用的安全工作完全交给了底层模型的预训练以及提供商一侧的任何策略层。这是一个值得注意的设计选择：生产级脚手架，即便是与自家提供商捆绑的那些，也不会在系统提示词中重复对齐工作——而且这一发现在新增三家厂商和社区谱系之后，现在在 11/11 个系统上都成立。

观察 3。在工程经验趋同的地方，提示词修辞也趋同；随后，随着信任得到校准，修辞又会变薄。反镀金措辞以近乎同构的表述出现在六个独立开发的脚手架中，禁止自主提交的规则在 2026 年 4 月是普遍的。到七月，语料展示了这些规则的生命周期：Mistral Vibe 把提交禁令反转为提交指导，并强制附上共同作者尾注（OpenHands 一直都在教提交方法），而 Codex 最新一代模型从提示词中同时删去了提交规则和反镀金指令——随着模型把这些规范内化，行为策略在变薄。现在有三种修辞策略并存：由 harness 强制的策略文字（Claude Code、OpenCode、Hermes）、结构性契约（Mistral Vibe 的七级指令层级和可覆盖性段落），以及几乎完全交给用户上下文（Pi 的 30 行提示词）。按模型而定的修辞已经成为一个独立的维度：Hermes 按模型家族门控强制块，注释中引用了各模型实际观察到的失败；OpenCode 维护九个逐家族的提示词，其严格程度因接收者而异。在全部十一个系统中稳定不变的是：任何地方都没有策略层面的拒绝措辞——对齐工作从不在 harness 提示词中重复。

7.4 流式传输与响应处理

响应处理策略的跨度很大：

  • Claude Code：SSE，带细粒度事件（content_block_start/delta/stop、message_delta）。通过 thinking 块支持扩展思考，budget_tokens 可配置。
  • Codex：WebSocket + SSE 后备。从 JSON-RPC 中解析 ResponseItem 事件。用 generate=false 进行连接预热。通过 x-codex-turn-state 头维持轮次状态。
  • Gemini CLI：@google/genai SDK 的 chat.sendMessageStream()，配有一个四次尝试的流中重试循环（MidStreamRetryOptions），可从内容、网络和无效流错误中恢复。把 SDK 包装在一个自定义的 GeminiChat 类中，以绕过一个函数响应校验的 bug。在记录响应时就把扩展思考部分排除在持久化历史之外，以免污染之后的缓存查找。
  • Mistral Vibe：Mistral SDK 的 stream_async() 聚合 LLMChunk 块；ThinkChunk 块被路由到单独的 reasoning_content 字段。在整个流上生成聚合的用量统计。
  • Aider：token 级流式传输，用 mdstream 做丰富的终端渲染。带指数退避的重试循环；遇到 FinishReasonLength 时用助手预填充续写。
  • Mini-SWE-Agent：完整响应（不流式）。最简单的做法；依赖模型原生的补全。
  • OpenHands：通过 LiteLLM 包装的 SSE，现在有一等的流式支持（一个 LLM.stream 字段，token 增量通过 on_token 回调转发），外加一条 OpenAI Responses 路径。支持 Anthropic 模型的提示缓存标记。
  • Hermes：五种自有传输实现；一个约 23 个取值的 FailoverReason 枚举驱动分类恢复（压缩、轮换凭据、后备链还是中止）。
  • Pi：九种线上协议实现，配有一个 partial-json 抢救解析器来处理流式工具参数——并与第 6 节的截断防护配合使用，因为抢救出来的参数可能在不完整时也通过校验。
  • OpenCode：由 Vercel AI SDK 的 streamText 负责分派；token 粒度的片段增量被持久化，并由内嵌服务器通过 SSE 重新提供，因此每个客户端（TUI、Web、IDE）重放的是同一个流。
  • OpenClaw：针对文本、思考和工具调用的 ACP 增量事件；由各提供商专属的传输流处理底层的 SSE/WebSocket 层。

7.5 高级 API 特性

单一提供商系统利用了多提供商抽象无法使用的功能：

Claude Code 的扩展思考集成暴露了一个 budget_tokens 参数，控制模型在回复前进行多少内部推理；虽然 LiteLLM 确实会透传 Anthropic 的 thinking 块，但在任何多提供商设计中，要把 budget_tokens 作为一等的脚手架旋钮暴露出来，仍然需要 Anthropic 专属的条件代码。Codex 的推理强度枚举涵盖 minimal/low/medium/high/xhigh，并在 2026 年年中扩展了 max 和 ultra——而 ultra 不只是更多推理：模型目录把它描述为最大推理加上自动的子智能体任务委派，这是一个会改变编排行为的强度级别，在语料中独一无二。Mistral Vibe 的逐模型 thinking 字段现在有五档（off/low/medium/high/max），映射到 Mistral 的 reasoning_effort 枚举上；Pi 则把整个格局归一到一个统一的七级刻度之后，通过十种逐 API 的 thinkingFormat 方言进行转换。Codex 通过一个由会话 ThreadId 派生的 prompt_cache_key 实现提示缓存（并为委派会话和 guardian 会话提供显式的覆盖钩子）；这是一种比 Claude Code 的 Blake2b 哈希静态/动态边界更轻量的策略。Aider 的视觉支持值得一提：当当前模型的 supports_vision 属性被设置时（通过 LiteLLM 元数据），Aider 会在聊天中接受图片文件，处理 MIME 类型，并把它们传给模型。这种支持取决于模型而非无条件提供，因此在表 17 中标为“可选”；Mistral Vibe 在 v2.14–2.18 中加入了视觉一列（TUI 中的 @ 提及、剪贴板粘贴、ACP 内联图片块），Mini-SWE-Agent 保留着一条需选择开启、默认关闭的多模态路径（一个把带标记内容展开为图片块的 multimodal_regex），因此语料中没有任何系统是无条件纯文本的。Gemini CLI 暴露扩展思考（并剥离思考部分以保持缓存干净），然后把模型本身的选择交给 ModelRouterService；把每个请求的模型选择当作由分类器驱动的运行时调度，这种处理方式在语料中仍然独一无二（OpenHands 的 RouterLLM 配置是按配置路由，而不是按每个查询分类），现在还延伸到一个托管的端侧运行时（一个 gemini gemma 命令组会配置一个本地 LiteRT-LM 服务器，路由链可以把本地 Gemma 模型用作查询分类器）。在可观测性方面，Gemini CLI 输出 OpenTelemetry 追踪，同时做逐 token 的成本统计。Mistral Vibe 也用 OpenTelemetry 为其智能体循环、工具执行和 hooks 埋点（agent_span/tool_span/hook_span 异步上下文管理器，配有 OTLP 导出器和 GenAI 语义约定属性），而 Pi 贡献了语料中最不寻常的可观测性指标：每轮缓存未命中金额浪费审计，为每一次本可避免的缓存失效标出价格。

注 5：另有三个函数调用式 coder 仍留在代码树中但未注册——一个在 coders/__init__.py 中被注释掉，另外两个根本没有被导入——因此 Coder.create() 恰好解析出 13 种格式；四月版前后不一致地报告为 14 种。 ↩

8 工具与动作系统

工具系统定义了智能体实际能做什么：它能调用哪些动作，以及这些动作如何执行。在我们研究的每个成熟智能体中，这个子系统都吸收了很大一部分工程投入。

8.1 工具数量谱系

图 3 展示了从极简到极繁的工具设计谱系。这些系统从单个 bash 工具一直到 109 个以上的工具（包括媒体处理和渠道集成）不等——Pi 把稀疏的一端变成了一种哲学（构建了七个工具，默认暴露四个，其余一切都是扩展），而 Hermes 把通用的一端推到了 69 个内置工具，背后由一个工具集层来限定每个平台的模型实际能看到什么。

8.2 工具接口架构

工具接口从几乎没有抽象——Mini-SWE-Agent 把一切都交给单个 shell 调用（subprocess.Popen(shell=True)，外面只包了一层在超时时杀掉进程组的逻辑）——到丰富的类型化契约不等。Claude Code 的 43 个工具各自把校验、权限检查、并发安全和 UI 渲染声明为独立的接口关注点。Codex 用 Rust trait 对象实现运行时多态——注册表存储 Arc<dyn CoreToolRuntime>，其中 CoreToolRuntime: ToolExecutor，这一抽象现已被抽取到一个独立的 codex-tools crate 中，与 code mode 和扩展共享。Gemini CLI 通过一个状态机式的 Scheduler 路由调用，让每次调用依次经过确定性的“校验中 → 执行中 → 已完成/出错”阶段。Mistral Vibe 增加了经 tree-sitter 解析的 bash——一条基于 asyncio.create_subprocess_shell 的执行路径，在派生进程之前用 tree_sitter_bash 校验命令结构——以及细粒度的权限范围（命令模式、文件模式、URL 白名单、目录包含关系）。Hermes 的单例注册表把注册与暴露分开：69 个工具在导入时自注册，一个工具集层限定每个平台的模型能看到什么，逐工具的可用性探测（30 秒 TTL，外加一个沿用最近一次可用结果的宽限窗口）避免一次偶发失败的 docker version 就把整个工具集剥掉，还有一个强制转换层修复 schema 漂移（"42" → 42），其动机来自实际观察到的开放模型输出。Pi 给它的七个工具各自配了一个可插拔的 Operations 接口（BashOperations、EditOperations 等）——这是唯一的远程化接缝，SSH、容器和微型虚拟机扩展都通过它迁移执行位置，而无需改动工具本身。OpenCode 用 Effect schema 注册了 17 个一方工具，并按模型切换工具面：GPT 家族模型得到一个移植自 Codex 的 apply_patch DSL，并完全失去 edit/write（第 8.4 节）。这条谱系反映了“简单性对能力”这一轴：接口面越大，安全保证越多，但工程成本也越高。

8.3 延迟加载工具

Claude Code 引入了延迟加载工具：标记为 shouldDefer = true 的工具不进入初始系统提示词。LLM 通过 ToolSearchTool 按需发现它们，该工具支持关键词搜索和直接选择（select:<tool_name>）。这显著缩小了提示词的大小：在 43 个工具中，初始只加载一个核心子集。延迟工具集通过 getDeferredToolsCacheKey() 缓存，在集合变化时失效。

四月版把这描述为 Claude Code 独有的功能；到七月，它已是一个不断扩散、有多个独立实现的模式。Codex 用一个 defer_loading 标志标记工具（默认是 MCP 工具），并暴露一个 tool_search 工具，背后是在工具规格上建立的 BM25 词法索引——同样的提示词经济学，只是用带排序的搜索取代了子串匹配。Hermes 用一个阈值把这个想法一般化：当 MCP 和插件的 schema 会超过上下文窗口的 10% 时，它们被折叠成三个桥接工具（tool_search/tool_describe/tool_call），由一个内联的 BM25 引擎来检索。OpenCode 延迟加载 skills（目录只列出名称和描述；由原生的 skill 工具获取正文），并把它实验性的 code mode 当作对 MCP 目录的延迟加载：它不暴露每一个 MCP 工具，而是用一个 execute 工具针对整个目录运行模型编写的脚本。相比之下，Mistral Vibe 的 defer_mcp 标志只是为了降低启动延迟而推迟 MCP 连接，并不推迟提示词中的可见性——一旦集成完毕，每个 MCP 工具都对模型可见，因此我们不再把它归入提示词层面的延迟加载模式。

8.4 文件编辑策略

文件编辑是软件工程智能体的核心动作。十一个系统实现了八种根本不同的策略，汇总在表 7 中。

两份快照之间，编辑格局发生了重组。

四月版把 Mistral Vibe 和 Gemini CLI 描述为一对“按程度多态”的系统——粗粒度的整文件工具加上模糊的细粒度补丁工具。这一季度过后，这两半都没能保留下来。Mistral Vibe 干脆删掉了它的 SEARCH/REPLACE 工具，收敛到 Claude Code 的精确唯一子串契约上（带一个 replace_all 逃生口，以及一个现在只能新建文件的 write_file）：这是生产级 harness 在编辑策略簇之间迁移的一个罕见的可观察案例，也证明了更强的模型会把最优点从工具侧的漂移容忍推向严格的契约。6 仔细审视之后会发现，Gemini CLI 的 edit 是一个带级联匹配器（精确 → 空白宽松 → 正则 → 模糊）的旧/新字符串工具，末端是其他系统都没有的东西：一个 LLM 编辑修复器子调用，依据模型提供的 instruction 修复匹配失败的旧/新字符串对——这是语料中第一个在工具内部由 LLM 辅助的编辑修复。

模糊级联家族及其可见的谱系。

在 Mistral Vibe 离开的地方，两个新成员带着语料中最精细的漂移容忍机制加入，而它们的源码记录了这套机制的来历。OpenCode 的九阶段替换器级联（精确 → 行修剪 → 块锚定 → 空白/缩进/转义规范化 → 上下文感知，Levenshtein 阈值 0.65，并带有防止不成比例匹配的守卫）在文件头注释中致谢了 Cline 和 Gemini CLI 的评测；Hermes 的九策略链则注明“inspired by OpenCode”。编辑机制现在有了一条可见的跨 harness 谱系——是通过继承而趋同，而不只是重新发现。Pi 选择了第三种立场：完全没有相似度阈值，只做 Unicode/空白规范化（NFKC、智能引号、行尾空白），替换在规范化空间中计算，然后逐行叠加回原始字节上，使未被触及的行保持原本精确的空白——此外还会在工具执行前渲染一个异步的 diff 预览。

Aider 的 RelativeIndenter 仍然值得特别关注。它用 Unicode 标记（默认：左箭头 ←，选它是为了避免与文件内容冲突）把绝对缩进转换为相对变化。make_relative() 方法追踪相邻行之间的缩进差，make_absolute() 则重建原始缩进。这让编辑块能够跨越不同的缩进层级工作，而这正是其他系统的常见故障模式。再结合通过 diff_match_patch 进行的模糊匹配（阈值 0.95，距离 500），就形成了一条稳健的编辑流水线。

观察 4。文件编辑策略是软件工程智能体代码修改准确性最重要的决定因素之一，而模型感知的多态已不再是 Aider 独有的了。Aider 通过一个提示词类工厂按模型选择编辑格式；OpenCode 通过工具注册表得出了同样的洞见，按模型切换工具集（GPT 家族模型得到 Codex 风格的补丁 DSL，并完全失去字符串替换工具）。语料中的编辑机制现在呈现出明确的跨 harness 谱系（Hermes 的匹配器“inspired by OpenCode”；OpenCode 的级联致谢 Cline 和 Gemini CLI），并且处于明显的变动之中：Mistral Vibe 在一个季度内从模糊 SEARCH/REPLACE 迁移到了 Claude Code 风格的精确匹配，而 Gemini CLI 增加了 LLM 辅助的编辑修复。Aider 的 RelativeIndenter 仍然是解决缩进敏感匹配问题最精巧的方案。

8.5 执行与沙箱

表 8 详细比较了各种沙箱方法。

Codex 是语料中在沙箱上投入最认真的系统，现在被打包成一个专门的 sandboxing crate。在 Linux 上，它运行 Bubblewrap——自 2026 年年中起内置并在代码树内编译，通过 C FFI 调用——来做命名空间隔离（--ro-bind、--unshare-net、--unshare-user、--unshare-pid），Landlock 则被降级为功能开关之后的旧版后备。在 macOS 上，它通过 /usr/bin/sandbox-exec 驱动 Seatbelt 配置。在 Windows 上，它使用受限令牌进程。受保护路径（.git、.agents、.codex）即便位于可写的根目录之内，也会被重新标记为只读。结果是在没有容器运行时开销的情况下实现了 OS 级隔离。

Gemini CLI 加入 Codex，成为第二个跨平台沙箱实现者。

Gemini CLI 的 SandboxManager 实现了与 Codex 相同的三平台栈：Linux 上用 Docker 或 Bubblewrap，macOS 上通过 /usr/bin/sandbox-exec 使用 Seatbelt，Windows 上用受限令牌进程。Codex 把策略固化在 Starlark execpolicy 规则中（第 10 节），而 Gemini CLI 则叠加了一套基于 TOML 的按模式沙箱策略（plan / default / accepting_edits），并在每条命令运行之前对提供商凭据做环境变量清洗（针对 TOKEN/SECRET/KEY/AUTH/CREDENTIAL 的名称模式正则、一个拒绝名单，以及匹配 GitHub 令牌值的正则）。Gemini CLI 在沙箱上的投入明显比 Codex 轻，因为它复用了 Node 的子进程 API 和操作系统自带的二进制程序，而不是自己实现底层的命名空间管道；Codex 更大的体量则花在了内置 Bubblewrap 的集成和 Rust 原生的命名空间控制上。四月版观察到，语料中规模最大的两个系统恰好也是具备原生跨平台沙箱的两个，并提出疑问：这种相关性是不是结构性的？扩大后的语料给出了否定的回答：Hermes（约 64.2 万行）不带任何 OS 级隔离原语，把隔离交给六种可插拔的执行后端，同时把安全预算投入到内容传播的威胁上；OpenCode（约 57.8 万行）则只靠策略。规模能预测的是某种大型安全投入，而不特指沙箱；第 10 节梳理了各系统转而把投入花在了哪里。

9 记忆与上下文管理

我们考察的每个智能体迟早都会遇到同一个问题：对话超出了上下文窗口。文献提供了两大类解决方案：分层记忆架构（例如 MemGPT [74]，它在上下文内的工作集与外部存储之间来回调度数据）和提示词压缩方法（例如 LLMLingua [75]，它在文本到达模型之前将其缩短）。语料中的十一个系统实现了四种实用策略（图 4），我们大致按复杂度递增的顺序介绍。

9.1 策略分类

9.2 线性历史（Mini-SWE-Agent）

Mini-SWE-Agent 完全不尝试管理上下文。完整的消息列表无上限地增长，依赖 LLM 原生的上下文窗口（Claude 4 家族最多可达 100 万 token）。这种简单性带来了完美的可复现性和直观的轨迹分析，是研究基线系统的刻意选择。

9.3 递归摘要（Aider）

Aider 的 ChatSummary 类实现了一种递归折半算法。当消息历史超过 max_tokens（默认：1024）时，它按 token 数把消息分成两半，保持尾部（最近的 50%）不变。头部通过一次 LLM 调用（summarize_all()）进行摘要。如果摘要加尾部的总量仍超过上限，这个过程会递归，最多 3 层。可以配置一个单独的“弱模型”（例如 GPT-3.5-turbo）来以较低成本做摘要。

9.4 可插拔压缩（OpenHands）

OpenHands 通过一个抽象的 Condenser 基类开创了可插拔的记忆管理。V0 应用自带十种实现；V1 SDK 把这个“动物园”精简为三种（NoOpCondenser、LLMSummarizingCondenser、PipelineCondenser），建立在一个 RollingCondenser 基类之上——这是一个说明问题的简化，大多数专门化变体都被证明是不必要的。伴随精简而来的是两项升级：压缩本身也是事件溯源的（日志中有 CondensationRequest/Condensation 事件，因此压缩历史可以重放），而且压缩器还兼作错误恢复——上下文窗口溢出和历史格式错误会触发一次压缩，而不是崩溃。摘要型压缩器在事件数阈值之外还增加了一个 token 数触发条件（max_tokens），使 OpenHands 与下文的阈值压缩家族保持一致。

9.5 阈值压缩（七个系统）

Claude Code 的压缩在运行中的 token 估计值进入模型有效上下文窗口下方的缓冲区时触发（AUTOCOMPACT_BUFFER_TOKENS = 13 000，另有一个可通过环境变量覆盖、用于测试的百分比阈值）。过程如下：（1）从消息中剥离图片（替换为 [image] 标记），（2）按 API 轮次对消息分组，（3）调用 LLM 生成对话摘要，（4）创建一条 SystemCompactBoundaryMessage，把压缩前的历史与摘要分隔开。压缩后的清理会恢复最多 5 个文件（POST_COMPACT_TOKEN_BUDGET = 50 000），并把每个 skill 截断到 25 000 token 的预算内。

Codex 既支持本地进程内的摘要，也支持通过专门的 /responses/compact 端点在云端做摘要，由 model_auto_compact_token_limit 控制何时触发摘要（单独的 /memories/trace_summarize 端点服务于第 9.6 节的记忆管线）；2026 年春季的发布版加入了远程压缩 v2 路径和逐线程的 rollout token 预算（带剩余预算提醒，预算耗尽时中止轮次）。

Gemini CLI：多阶段上下文管线。

Gemini CLI 的上下文管理比简单的压缩更精巧。在顶层，一个 ChatCompressionService 在历史超过模型 token 上限的 50% 时触发，调用 Gemini 生成一份状态快照，并逐字保留最近 30% 的历史（现在在压缩之前还会先运行一遍按 token 预算截断的预处理，以及一个 PreCompress hook）。在此之下，一个专门的上下文处理器模块实现了一条多阶段的上下文蒸馏管线，带有可插拔的处理器（滚动摘要、节点蒸馏、节点截断、大块数据降级、工具屏蔽、状态快照），并在 v0.43–0.45 中整合为一个 ContextManager：它在工作缓冲区中维护一张“原始与活动”对照的上下文图，通过一个带迟滞触发阻尼的编排器运行各处理器，并用一个根据实际观察到的 API token 计数校准的自适应 token 计算器，取代静态的“每 token 字符数”估算。一个单独的 ContextCompressionService 追踪每个文件的压缩级别（FULL、PARTIAL、SUMMARY、EXCLUDED），比 Claude Code“已压缩/未压缩”的二元划分粒度更细；一个可插拔的 AgentHistoryProvider 接口则允许扩展用自己的压缩逻辑替换。

Mistral Vibe：由中间件触发，现在是两层且可被动响应。

Mistral Vibe 的 AutoCompactMiddleware 在每轮之前检查 context_tokens >= auto_compact_threshold；压缩例程本身被抽取到一个 CompactionManager 中，自四月以来有三项改进：压缩后的状态是一个上下文信封，会把先前的用户消息与摘要一起重新注入（这样原始任务目标在重置后得以保留）；对缓存友好的主摘要失败时，会退回到一个专门的、不带工具的摘要器；当一个轮次在进行中溢出上下文窗口时，同一个例程也会被动触发。通过中间件管线进行集成，在架构上仍然比在循环内检查更干净：压缩只是另一条轮次策略。Mistral Vibe 配套的 RewindManager 为每条用户消息创建文件系统级检查点，支持回退并可选恢复文件——现在还可以分叉为新会话，并通过 ACP 暴露，让 IDE 客户端驱动回退。检查点功能曾是它独有的，现在有了一个粒度更细的同类：OpenCode 为每个项目维护一个影子 git 仓库（在真实 worktree 之上使用单独的 --git-dir），在流开始前、步骤开始和步骤结束时做快照，产生逐步骤的补丁片段，并能完整回退“对话 + 文件系统”。

Hermes：谱系压缩。

Hermes 属于阈值家族（在上下文的 50% 减去 max-tokens 处触发，下限 64K；保护前三条消息以及一个按 token 预算保留的尾部；由辅助模型做迭代摘要，上限为 min(上下文的 5%, 12K token)），但它加入了一个其他系统都没有的结构：压缩并不改写对话记录——而是结束会话。每次压缩都会关闭当前的 SQLite 会话（end_reason=’compression’），并轮转到一个通过 parent_session_id 链接的子会话；谱系辅助函数沿着祖先链遍历，会话搜索也跨谱系去重。上下文管理和会话持久化成为同一个机制，而且任何历史都不会被销毁。引擎是可插拔的（一个 ContextEngine 抽象基类），呼应了 OpenHands 的压缩器。

Pi：基于会话树的压缩。

Pi 在 contextWindow − 16,384 token 处触发（保留最近的 20K），并借用了其他策略的两个特点：摘要是迭代合并的——更新提示词会重新读入上一份摘要，而不是从头重新摘要（递归摘要的特点）——以及一个 session_before_compact hook，允许扩展否决或完全替换结果（可插拔压缩的特点）。它独特的基底是会话本身：一棵只追加的 JSONL 树，每个条目都带有 id/parentId，一个可移动的叶指针定义当前活动分支。/tree 导航、/fork 和 /clone 统一了其他 harness 作为三个独立功能来实现的东西（检查点、回退、替代方案探索）；放弃一个分支时，可以选择生成一份 LLM 分支摘要并拼接到新位置，因此探索的成果永远不会丢失——代价是明确的：文件系统状态不会被恢复。累积的 <read-files>/<modified-files> 列表作为结构化记忆在多次压缩之间持续保留。

OpenCode：锚定的增量摘要。

OpenCode 在 limit.input 减去预留输出余量处触发，使用“字符数 / 4”的估算（整个代码树中都没有分词器），并生成语料中增量性最为明确的摘要：上一份摘要以 <previous-summary> 块传回，由一个隐藏的、所有工具都被禁用的 compaction 智能体进行合并（“保留仍然成立的细节，删除过时的细节”），写入规定的 Markdown 段落（Objective / Important Details / Work State / Next Move / Relevant Files）。逐字保留最后两个用户轮次的尾部；可选启用的修剪会软删除旧的工具输出，保护最新的 40K token，并且只在可回收量超过 20K 时才触发。

9.6 持久记忆管线

本研究的四月版可以用每个系统一句话来描述跨会话记忆：这里是一个 Markdown 上下文文件，那里是一个对话记录存储。三个月后，持久记忆成了厂商原生系统差异化最激烈的地方，而各种设计在一个维度上的分歧颇具启发：谁来写记忆，谁来审查它。

Codex 采用最自主的设计。一条后台两阶段管线先从最近的会话 rollout 中提取结构化记忆（对每个 rollout 做 LLM 提取，存入一个 SQLite 状态数据库，带有租约任务、重试退避和密钥脱敏），然后把它们整合成位于一个以 git 为基线的 ~/.codex/memories/ 根目录下的文件系统产物——整合工作由一个沙箱化的内部子智能体（无需审批、无网络、只能本地写入）通过审查一份 git 风格的工作区 diff 来完成。记忆被注入到新会话中，带有引用追踪和基于使用情况的排序。因此，Codex 是语料中第一个由智能体而不是代码来维护长期记忆的系统；一个实验性的“chronicle”边车进程则把同样的机制延伸到被动的屏幕上下文。

Gemini CLI 在治理上走向了相反的方向。它四月时可调用的 save_memory 工具已经消失——系统提示词现在直截了当地说明不存在这样的工具——取而代之的是：（a）模型直接用普通编辑工具修改 GEMINI.md 或私有的逐项目 MEMORY.md 索引；（b）一个异步的 skill 提取子智能体，挖掘已完成的会话记录，并把标准补丁文件输出到逐项目的 .inbox/ 中，由用户通过 /memory 审查并应用。Codex 让智能体自主整合记忆，Gemini CLI 则在提取与持久化之间插入了一个由人把关的审查收件箱——这是语料中唯一的此类设计。

Hermes 刻意让持久记忆保持极小且对缓存友好：两个有大小上限的 Markdown 文件（MEMORY.md，2,200 个字符；USER.md，1,375 个字符），作为冻结快照注入，因此会话中途的写入会落盘，但不会使提示缓存失效。对话回忆是确定性的——一个 session_search 工具，作用于由触发器维护的 SQLite FTS5 表（BM25，外加针对中日韩文字的三元组索引），“任何地方都不调用 LLM”——嵌入只存在于需选择开启的记忆插件中。OpenClaw 提供一个 Active Memory 插件（需要记录在案的是，它早在我们前一版所审计的那个四月发布版中就已存在），在主回复之前立即运行一个专门的记忆子智能体，另外还有它较早的、需选择开启的 LanceDB 对话记忆扩展。OpenHands 把记忆纳入它的上下文文件约定：一个 <MEMORY> 提示词段落指示模型把持久性事实写入 AGENTS.md 本身。Claude Code 为每个项目持久保存由 Markdown 事实组成的记忆目录；Pi 和 Mini-SWE-Agent 则刻意不在会话基底之外持久保存任何东西。

观察 5。持久记忆已经取代压缩，成为上下文工程的前沿。压缩设计已经趋同（十一个系统中有七个使用阈值触发的 LLM 摘要，并越来越多地采用增量合并）；如今让各系统拉开差距的是记忆的写入路径。四种治理模式并存：由智能体维护（Codex：一个沙箱化子智能体在以 git 为基线的存储上整合记忆）、由人把关（Gemini CLI：提取子智能体写入一个补丁收件箱，由用户通过 /memory 审查）、模型直接写入但有界（Hermes：有字符上限的 Markdown 快照，为了缓存卫生按会话冻结；OpenHands、Claude Code：上下文文件约定），以及轮前的智能体式回忆（OpenClaw 的 Active Memory 子智能体）。值得注意的是，十一个系统中没有一个把基于嵌入的检索用作主要的记忆基底——观察 13.2 中关于确定性检索的发现从代码延伸到了记忆，生产环境中的上限是 SQLite 全文检索（Hermes）。

9.7 仓库上下文

除了对话历史，智能体还必须管理代码上下文：

  • Aider RepoMap：基于 tree-sitter 的符号索引，配合 diskcache（SQLite v4）——仍是语料中唯一带排序的仓库地图。符号按与当前对话的相关性排序。token 预算是自适应的（map_tokens，默认 1024），并针对大型仓库提供一个 map_mul_no_files 乘数。
  • Claude Code 记忆系统：通过专门的 claudemd 子系统自动发现 CLAUDE.md 文件（从工作目录出发遍历托管、用户和项目三个范围），作为去重后的嵌套记忆附件注入；单独的 memdir 机制管理逐项目的持久自动记忆目录。
  • Codex 指令：分层的 AGENTS.md 指令——准确地说，是从项目根目录一直到工作目录的拼接（嵌套内容最后追加，因此所谓“优先级”只体现在位置上），外加一个 AGENTS.override.md 逃生口，以及可配置的根标记和后备文件名。
  • Gemini CLI 上下文文件：三个范围的 GEMINI.md 合并（全局、扩展、项目），受文件夹信任机制把关；外加通过工具输出即时注入子目录上下文文件，以及私有的 MEMORY.md 项目索引。
  • Mistral Vibe 即时发现：提示词中包含顶层 AGENTS.md（用户和项目两个范围），并且——自 v2.19 起——当 read_file 触及嵌套 AGENTS.md 所在目录下的文件时，即时呈现这些文件。
  • Hermes 带威胁扫描的层级：“先找到者胜出”的遍历（先找 .hermes.md/HERMES.md 直到 git 根目录，然后是 AGENTS.md、CLAUDE.md、.cursorrules）；每个上下文文件都会被扫描提示注入模式，一旦匹配就整体屏蔽；一个子目录提示追踪器把逐目录的上下文文件追加到工具结果中，保持缓存的提示词不变。
  • Pi 祖先目录遍历：从 cwd 到根目录收集 AGENTS.md/CLAUDE.md，放入 <project_context> 标签；加载由仓库控制的配置（扩展、skills）需要经过信任把关，但上下文文件无论如何都会加载——这是一种有文档记载的、对注入面的刻意接受。
  • OpenCode 基于拉取的附加：向上遍历查找 AGENTS.md/CLAUDE.md/CONTEXT.md（第一个找到的文件名胜出），外加远程 URL 指令文件；当 read 工具触及嵌套 AGENTS.md 所在目录下的文件时，惰性附加这些文件。
  • OpenHands 第三方摄取：skills 子系统把 AGENTS.md、.cursorrules 以及嵌套的逐目录 AGENTS.md 作为带范围的规则摄取——一个系统读取另外三个生态的约定。
  • OpenClaw 对话记录：按智能体/会话持久保存的 JSONL 对话记录文件，位于 ~/.openclaw/agents/<agentId>/sessions/<sessionKey>.jsonl。

10 安全与权限模型

智能体被赋予的自主性越大，安全机制就越重要，二者成正比。近来的一系列学术工作已经把威胁模型形式化：通过文件或网页内容进行的间接提示注入 [77]，作为注入攻击与防御动态评测环境的 AgentDojo [76]，R-Judge [78] 之类的风险意识基准，以及 ToolSword [79] 整理的工具使用安全故障模式目录。语料覆盖的范围很广，从基本没有安全控制的系统，到多层架构的系统。

10.1 Claude Code：三层权限系统

Claude Code 实现了在架构上最优雅的安全系统，共有三层（图 5）：

对于后台子智能体和分叉出来的子智能体，只有第 1–2 层可用——原本会弹出的询问被判为拒绝——而默认的前台子智能体仍然可以弹出交互式对话框。无法解决的情况会上交给父协调者。一个拒绝追踪机制会统计每个会话中的权限拒绝次数；在 N 次拒绝之后，系统退回到提示询问。每个异步智能体都维护本地的拒绝状态，以防止跨智能体污染。

10.2 Codex：带原生沙箱的四层权限栈

四月版把 Codex 的安全描述为两种机制——策略规则加 OS 沙箱——并把它的审批关卡形容为“几乎不可见”。七月的快照显示有四层，其中两层正在向 Claude Code 的设计收敛：

第 1 层：执行策略（是 Starlark，不是 TOML）。

可执行的规则（execpolicy/）用 Starlark 编写：prefix_rule(pattern=[…], decision="allow|prompt|forbidden", match=[…], not_match=[…]) 和 network_rule(…) 函数，从 CODEX_HOME/rules/ 以及各配置层的规则目录加载。7 一个独特的细节：规则可以带有内联的 match/not_match 示例，并在解析时进行校验——这就是写在策略文件里的可执行测试用例。

第 2 层：生命周期 hooks。

一个 hooks crate 对外暴露外部 hooks，其事件词汇几乎逐字照搬 Claude Code：PreToolUse、PermissionRequest、PostToolUse、PreCompact、SessionStart、UserPromptSubmit、SubagentStart、SubagentStop、Stop——外加一个在 Claude Code 中没有对应项的 PostCompact 事件——输出为阻止/允许的决定。第 14.5 节把这作为语料中最清晰的一个案例来讨论：一个厂商原生 harness 把另一个厂商原生 harness 的扩展接口当作事实标准来采用。

第 3 层：Guardian，一个 LLM 审批审查器。

当一条命令需要用户审批时，一个专门的 Guardian 会话会对照一份策略提示词，对确切的计划动作重新评估（紧凑地重建对话记录，给出严格 JSON 格式的裁决），在超时或输出格式错误时失败即关闭，并带有一个按轮次计算的拒绝熔断器。四月版拿来与 Claude Code 对比的“没有 LLM 分类器”已不再成立：两家厂商原生旗舰现在都实现了“静态规则 → LLM 分类器 → 交互/OS 兜底”的模式。一个面向用户的协作模式选择器（Plan/Default 预设，会覆盖模型、推理强度和开发者指令）完成了这次趋同：全部四个厂商原生系统现在都提供只读的规划模式。

第 4 层：原生 OS 沙箱。

沙箱实现覆盖三个平台：

  • Linux：内置、在代码树内编译的 Bubblewrap（通过 C FFI 调用），只读文件系统（--ro-bind / /），通过 --bind 设置可写根目录，网络命名空间隔离（--unshare-net），用户/PID 命名空间隔离；Landlock 被降级为旧版后备。
  • macOS：通过 /usr/bin/sandbox-exec 使用 Seatbelt 配置，允许/拒绝规则可配置。
  • Windows：受限令牌进程，带基于 ACL 的读写限制。

观察 6。OS 级沙箱是语料中代码成本最高的能力之一，而且它是一种选择，而不是规模的必然结果。四月的语料暗示了一种与规模的相关性（其中最大的两个系统恰好是两个跨平台沙箱实现者）；扩大后的语料打破了这种相关性。Hermes 是这里最大的系统之一，却不带任何 OS 级隔离原语：它把隔离交给六种可插拔的执行后端，转而把安全预算花在内容传播的威胁上（promptware 扫描——对提示注入载荷做模式匹配——一条 skills 供应链，以及一个连 --yolo 都无法绕过的命令策略底线）。规模相当的 OpenCode 只靠策略，把投入放在语法感知的命令权限上，而不是隔离。Pi 把这种拒绝写成了一条安全论证：一个不完整的进程内沙箱“很容易被误解为安全边界”。仍然成立的是成本这一面：凡是构建了原生沙箱的地方（Codex、Gemini CLI；Claude Code 则把 Anthropic 可复用的 sandbox-runtime 包装为可选功能），它都是一笔数千行代码的可观投入——而第 14.4 节显示，meta-harness 在更上一层又把同一笔账付了一遍。

10.3 OpenHands：集成式纵深防御

OpenHands 可插拔的 SecurityAnalyzer 框架在 V1 SDK 中大幅成熟。V0 时代的 Invariant 分析器已经消失；当前的组合把一个 LLMSecurityAnalyzer（智能体自己为每个动作的 security_risk 打分，系统提示词指示它填写这个参数）和一个 GraySwanAnalyzer（外部对抗性 API），与两个新的确定性分析器配对——PatternSecurityAnalyzer 和 PolicyRailSecurityAnalyzer，后者基于 shell AST 解析，提供 fetch-to-exec、raw-disk-op 和 catastrophic-delete 等具名护栏。一个 EnsembleSecurityAnalyzer 以“最坏情况胜出”的方式融合各个裁决，出故障的子分析器会失败即关闭，判为 HIGH。LOW/MEDIUM/HIGH/UNKNOWN 风险枚举保留了下来；确认机制现在是一个策略对象（AlwaysConfirm/NeverConfirm/ConfirmRisky）。提示词一侧补全了双向的注入防御：来自仓库的上下文被包在 <UNTRUSTED_CONTENT> 标记中，还有一个专门的提示词段落来教授风险评估协议。

10.4 OpenClaw：基于范围的授权

OpenClaw 实现了基于范围的授权，在带命名空间的范围（operator.read/write/admin/pairing 等）之上设有 operator 和 node 两种连接角色。网关对每个方法强制执行范围要求。其他安全机制包括：按 IP/令牌的固定窗口限流、SSRF 策略强制、带配对审批流程的私信白名单、针对浏览器动作和插件动作的执行审批关卡，以及聊天内容净化。2MB 的 MAX_PROMPT_BYTES 上限提供了拒绝服务防护（CWE-400）。

10.5 Gemini CLI：四种审批模式加跨平台沙箱

Gemini CLI 叠加了两种互补的安全机制。第一，一个 ApprovalMode 枚举把每次工具调用归入四种模式之一：

  • PLAN：只读；模型能看到完整的工具列表，但只能调用读取类工具（Glob、Read、Grep 等）。它的回复以计划的形式呈现，用户必须明确批准才能退出计划模式。
  • DEFAULT：每次工具调用都弹出交互式审批对话框；用户可以批准一次、始终批准或拒绝。
  • AUTO_EDIT：编辑操作自动批准，而 shell 和其他有副作用的工具仍需询问；用于在本地代码上快速迭代。
  • YOLO：所有动作自动批准。仅用于 CI/脚本场景。

第二，一个 SandboxPolicyManager 强制执行基于 TOML 的按模式策略：哪些路径可读/可写，哪些网络主机可以访问，哪些环境变量要被清洗。这一组合在结构上类似于 Codex 的“策略即代码 + 沙箱”栈，但在顶部叠加了一个明确面向用户的模式选择器——Codex 后来也通过它的协作模式预设采用了这种人机工程设计。另有一个 isTrustedFolder() 检查，根据目录是否在用户的信任列表中来扩大或缩小上下文发现的范围，提供了第四层可选的粒度。在我们两份快照之间，发布节奏主要被策略引擎和供应链加固所主导——无头模式下受信任把关的 .env 加载、带核心工具白名单的 shell 命令校验、skill 安装时的路径穿越检查——这支持了观察 10.2 的论断：在最大的系统中，安全吸收了不成比例的工程投入。

10.6 Mistral Vibe：权限范围模式加智能体配置关卡

Mistral Vibe 没有 OS 沙箱（一个可选的 --worktree 标志现在提供分支级隔离），但它用比其他无沙箱系统更细粒度的权限模型来弥补。每次工具调用都要按一个层级逐项检查：

  • 智能体配置级别的工具全局 permission 设置（ALWAYS、ASK、NEVER）。
  • 工具专属的校验器（例如 resolve_file_tool_permission 对路径做模式匹配），外加一个默认的只读命令白名单，自动批准 ls/cat/grep 一类的命令。
  • 用户声明的 shell hooks（hooks.toml，before_tool），可以在权限评估之前拒绝一次调用或改写它的输入。
  • 在运行时添加的会话规则——现在对于“始终允许”的授权会跨会话持久保存。
  • 向用户呈现的交互式审批回调，除非设置了 bypass_tool_permissions（即改名后的 auto_approve）。

智能体配置内置了安全分级：plan 和 chat 配置是 SAFE（只读）；default 是 NEUTRAL；accept-edits 是 DESTRUCTIVE；auto-approve 是 YOLO。工具也可以覆盖智能体的默认值：无论哪个配置，write_file 对敏感模式（.env 文件）都会强制 ASK。没有基于 LLM 的风险分类器，也没有 OS 级隔离；安全归结为显式的逐模式匹配、hooks 和用户询问。

10.7 Hermes：连 YOLO 都无法绕过的策略底线

Hermes 把沙箱问题反转了过来：语料中最大的 Python 系统不带任何 OS 级隔离原语——它的工具代码树中没有任何 Seatbelt、Landlock、seccomp 或 Bubblewrap——而是把隔离交给六种可插拔的执行后端。在本地后端上，安全是大规模的“策略即代码”：一个 3,200 行的审批模块，其文档写道“config.yaml IS the security policy”。它的各层是：用户的拒绝通配符；一条由十二种模式构成、连 --yolo 都无法绕过的硬性底线（rm -rf /、mkfs、dd 写块设备、fork 炸弹、关机）——YOLO 环境变量在模块导入时就被冻结，正是为了让遭到提示注入的 skill 无法在运行时把它翻转；47 种危险命令模式，在去混淆后的变体上进行匹配（去除引号拼接、折叠命令替换、锚定命令位置）；一个外部的 Rust 内容扫描器（Tirith，安装时经 cosign 验证）；以及一个可选的辅助 LLM 关卡（_smart_approve：temperature 0，最多 16 个 token，输出 APPROVE/DENY/ESCALATE——其代码致谢了 Codex 的 Smart Approvals）。它独特的威胁模型针对内容传播的威胁：对上下文文件、记忆写入、MCP 工具描述和 skill 安装做 promptware 扫描（带有内置/受信任/社区三级信任分层和隔离区）；始终屏蔽云元数据端点的 SSRF 防护；不受信任的工具结果被包在 <untrusted_tool_result> 分隔符中，并对仿冒字符做去武装处理。容器后端完全跳过危险命令这一层——直到一个宿主机绑定挂载让它重新生效。值得注意的缺席：没有逐工具的允许/询问/拒绝矩阵，也没有只追加的审计日志。

10.8 Pi：把缺席写成文档，作为安全论证

Pi 是语料中唯一一个把安全基础设施的缺席作为设计原则写进文档的系统：它的安全文档论证说，一个不完整的进程内沙箱“很容易被误解为安全边界”，宣称通过上下文文件进行的提示注入是无法防护的，并让内置工具以调用者的用户权限无条件执行。唯一的内置关卡是项目信任：由仓库控制的配置（扩展、skills、提示词、主题）只从受信任的路径加载，按规范路径逐一判定，并查找最近的祖先目录——明确声明“不是沙箱”，而上下文文件无论如何都会加载。权限控制是字面意义上的“策略即代码”：tool_call 扩展事件暴露可修改的工具参数和一个 {block, reason} 否决机制，参考示例 permission-gate 在用户空间里用约 80 行代码实现了常见的“正则 + 确认”流程（rm -rf、sudo、chmod 777）；如果需要隔离，它以扩展的形式出现（Anthropic 的 sandbox-runtime、一个 QEMU 微型虚拟机），通过逐工具的 Operations 接缝接入。只追加的会话树同时充当完整的审计轨迹。

10.9 OpenCode：语法感知的权限控制，默认宽松

OpenCode 是继 Hermes 之后第二大的不带 OS 级隔离的系统（它代码中的“sandbox”指的是 git worktree），其默认姿态与 Codex 正好相反：在项目内 "*": allow，询问只保留给 external_directory 访问、.env 读取和 doom loop。它独特的投入是语法感知的命令权限控制：每条 bash 命令都用 web-tree-sitter 解析（bash 和 PowerShell 语法）；确切的命令文本成为询问的模式，而“始终允许”的授权则由一个约 130 条、明确由 LLM 生成的命令元数字典来限定范围（git → 2，npm run → 3），生成 git commit * 这样的授权，而不是一揽子批准；操作文件的命令会解析其参数路径，项目之外的路径会触发 external_directory 询问。权限规则（{permission, pattern, action}，在通配符上“最后匹配者胜出”）按“默认值 → 内置智能体 → 用户配置 → 逐智能体 → 逐会话”分层；对某个工具拒绝 "*" 会把它完全从 LLM 的视野中移除——工具的可用性本身就是由权限推导出来的。一个并行的 v2 引擎反转为默认拒绝，并把审批持久化到 SQLite；无头运行时自动拒绝所有询问。没有危险命令拒绝名单，也没有风险分类器。

10.10 最低限度的安全（Aider、Mini-SWE-Agent）

Aider 提供交互式确认模式，但没有自动化的风险评估。不过，它带有三阶段 Python lint（语法 → 编译 → flake8）的反思循环，通过在错误扩散之前将其捕获，提供了隐性的安全保障。

Mini-SWE-Agent 只把资源上限作为安全机制——step_limit、cost_limit，以及（在 v2.4 系列中加入的）挂钟时间上限和连续格式错误上限，外加一个可选的交互式确认模式——这对基准评测来说足够了，但不足以用于生产。

11 多智能体编排

十一个系统中有九个支持多智能体执行，而它们的架构差异很大。这是语料分布最分散的一个维度，因此我们在这里比在其他章节讲得更详细。

11.1 多智能体分类

我们识别出六种不同的多智能体模式：

  • 单智能体（无多智能体）：Mini-SWE-Agent、Aider——以及 Pi 的内核，它不带任何派生或 task 工具；它的子智能体存在于扩展空间中（见下文）。
  • 顺序委派：Mistral Vibe（父智能体通过 task 工具派生一个子智能体，并等待其完成）。
  • 并行子会话：OpenHands（task 和 delegate 工具把子任务作为独立对话运行，在线程中并发执行），OpenCode（task 创建运行同一循环的子会话；同一条消息中的多个调用并发执行）。
  • 带扇出的层级线程树：Codex（专属线程、由分叉模式控制的继承、按模型划分的工具代际、map-reduce 式扇出、持久化的父子拓扑）。
  • 递归组合：Claude Code（智能体可组合地派生子智能体，并通过共享提示缓存的方式分叉）。
  • 注册表 + 跨进程协议：Gemini CLI（具名智能体定义位于一个对称的本地/远程会话协议之后，远程智能体通过 A2A 接入）、OpenClaw（ACP 会话派生）、Hermes 的看板蜂群（在 SQLite 黑板上运行的子进程）。

11.2 深入剖析：Claude Code 的递归组合

Claude Code 的多智能体架构是所研究系统中最精巧的。它支持三个层次的协调：临时子智能体、带类型的智能体定义，以及完整的协调者模式。

11.2.1 智能体定义系统

智能体通过 JSON/Zod schema 定义，指定描述、提示词、可选的工具白名单/黑名单、模型选择、轮次上限、权限模式、MCP 服务器绑定、隔离级别、后台执行标志和 skills。

智能体定义按一个优先级层次加载：内置智能体 → 插件智能体 → 用户设置 → 项目设置 → 命令行标志设置 → 策略/托管智能体。后面的来源覆盖前面的。内置智能体包括 Explore（快速代码库搜索）、Plan（架构设计）和 VerificationAgent（执行测试）。

11.2.2 上下文分叉

当通过 AgentTool 派生子智能体时，父级的上下文沿六个维度分叉：

  • AbortController：一个与父级关联的新控制器（父级中止 → 子级中止，反之则不然）。
  • 文件状态缓存：克隆 LRU 缓存，以防止并发修改。
  • 权限询问：对异步智能体屏蔽（shouldAvoidPermissionPrompts = true）。
  • 应用状态：对异步智能体设为空操作，以防止修改已失效的会话。
  • 拒绝追踪：全新的本地状态（拒绝次数不在全局累积）。
  • 工具决策：每个智能体一个全新的 Map（不会跨智能体污染）。

一项关键优化是提示缓存共享：父级的 renderedSystemPrompt 在分叉时被冻结，并逐字传给子级。这确保了在分叉/恢复的边界之间仍能命中提示缓存，防止 GrowthBook 功能开关的分歧导致缓存失效。

11.3 深入剖析：Codex 的线程树模型

Codex 的多智能体架构围绕三个核心抽象构建：

AgentControl

是派生和管理子智能体的中央控制平面。

AgentRegistry

追踪会话树中所有存活的智能体，维护 LiveAgent 元数据结构体。

派生流程。

spawn_agent_internal() 函数预留一个派生槽位，继承父级的沙箱和执行策略，从来源解析分叉模式和元数据，创建一个带有相应历史（完整、截断或全新）的线程，并发出一条会话已启动的通知。

SpawnAgentForkMode。

一个独特的功能是 SpawnAgentForkMode，它控制子智能体继承多少对话历史：

  • FullHistory：继承所有消息（完整上下文）。
  • LastNTurns(N)：只继承最近的 N 轮（缩减的上下文）。

消息过滤（keep_forked_rollout_item()）只保留 system/developer/user 消息和最终的助手回答，过滤掉中间的工具调用和推理过程。这种选择性继承防止了子智能体中的上下文膨胀。

智能体间通信。

早期版本中专门的邮箱模块已被并入会话的输入队列：智能体间的消息以带邮箱投递阶段的 InputQueue 活动的形式流动，承载为带类型的 InterAgentCommunication 记录（Spawn/Message/Followup/Result）。两代工具并存——multi_agents（spawn/wait/send_message/interrupt/list）和 multi_agents_v2（spawn/wait/send_input/resume_agent/close_agent）——通过模型元数据中的 multi_agent_version 字段按模型选择，父子拓扑由一个专门的 agent-graph-store crate 持久化。父级通过一个 AgentStatus 枚举监控子级状态。

扇出与声明式角色。

在派生和邮箱之外，Codex 还发展出了 map-reduce 式的编排：spawn_agents_on_csv 为 CSV 的每一行启动一个子智能体，所有子智能体遵循一份共享的 JSON-schema 结果契约，带有并发规范化和运行时上限，结果通过 report_agent_job_result 汇总回来。子智能体由声明式的 TOML 角色定型（内置的 explorer 和 worker 角色在代码树中处于启用状态；一个 awaiter 角色文件仍在，但目前未注册），这些角色作为高优先级的配置层生效——这是 Codex 对 Claude Code 智能体定义的回应——而委派本身由模型掌控：ultra 推理档位把最大推理与自动任务委派结合在一起，可配置的委派模式（禁用 / 仅在明确请求时 / 主动）在线程和轮次层面生效。

11.4 OpenHands：基于对话树的并行委派

V0 时代的 AgentDelegateAction（顺序执行，一次一个委派，共享事件流）已经消失。V1 SDK 通过工具进行委派：一个形态明显像 Claude Code 的 TaskTool（prompt、subagent_type、description、resume），由一个 TaskManager 为每个任务创建独立的对话（有自己的事件日志，指标同步回父级）；还有一个带 spawn/delegate 命令的 DelegateTool，在线程中并发运行委派任务。子智能体以带 YAML 头信息（名称、描述、模型、工具、skills、hooks、MCP 配置、权限模式、压缩器）的 Markdown 文件声明，分为项目/用户/内置/插件几个级别——内置的有 code-explorer、bash-runner 和 web-researcher（外加一个 general-purpose 默认智能体）——并且明确支持嵌套。在委派层之上是一个脚手架级的外层循环：一个 /goal 端点在每次运行后让 LLM 评审审视对话记录，要么注入一条后续提示，要么以完成状态停止；与之配套的是可插拔的评审器（critic），其改进迭代上限可配置。

11.5 Mistral Vibe 的顺序子智能体委派

Mistral Vibe 的多智能体支持刻意保持简单：父智能体调用 task 工具，该工具以请求的智能体配置（例如 explore）构造一个全新的 AgentLoop 实例，在进程内运行到结束，并把子智能体的 AssistantEvent 输出和 ToolResultEvent 摘要返回给父智能体。一个守卫确保只有标记为“subagent”的配置（目前只有 explore）可以被委派，防止意外地递归升级到具备写权限的配置。每个子智能体都获得一个全新的 VibeConfig、自己的会话目录和独立的消息历史，提供与 Codex 线程树相当的隔离，但代价是失去真正的并行：父智能体在 await 上阻塞，直到子智能体退出。这种架构上的简单（一个工具、顺序、进程内）意味着 Mistral Vibe 处在多智能体光谱的简单一端——除了完全没有委派的系统之外，它是语料中最简单的委派，让人想起 OpenHands 已经退役的 V0 AgentDelegateAction。

11.6 Gemini CLI：注册表、对称会话协议与 A2A

Gemini CLI 的多智能体模型分为两层。在本地，一个 AgentRegistry 保存具名智能体定义——带有必填 YAML 头信息的 Markdown 文件——从用户、项目和扩展三个范围加载。例如，内置的 generalist 智能体可以访问所有已注册的工具，运行预算为 10 分钟、20 轮。调用可以通过 /agent 斜杠命令、@agent-name 提示写法，或者——自 v0.39 统一子智能体以来——一个可由模型调用的 invoke_agent 工具进行，每次运行都获得一个隔离的工具注册表。调用路径已被抽象到一个智能体会话协议之后，该协议有对称的本地和远程实现，因此由进程内执行器支撑的注册表条目，与由远程 A2A 智能体支撑的条目，都通过同一个接口驱动。

Gemini CLI 与我们语料中其他所有系统都不同的地方，是 packages/a2a-server 模块，它是 Google 的 Agent-to-Agent（A2A）协议的一个实验性实现。A2A 之于智能体间通信，就如同 MCP 之于工具集成：一个 JSON-RPC 标准，让一个智能体进程能够发现另一个智能体进程、向其认证并与之交换消息，对方可能在另一台机器上，由另一家厂商构建。Gemini CLI 的 A2A 服务器允许远程编排器像驱动一个已注册的本地智能体一样驱动本地的 Gemini CLI 实例——现在还会通过该协议报告用量元数据，以便进行跨厂商的资源核算——为跨厂商的多智能体拓扑打开了大门，而语料中没有其他系统原生支持这一点（第 14.4 节的 meta-harness 恰恰是从外部构建这样的拓扑）。

11.7 Hermes：受保护的委派、蜂群与混合智能体

Hermes 默认是扁平委派，另有两个向上的逃生口。delegate_task 在线程池上以进程内方式构建子智能体：全新的对话、聚焦的系统提示词、只返回摘要、工具集与父级取交集（“子智能体不得获得父级没有的工具”），以及一个六个工具的屏蔽名单（不允许递归、不允许与用户交互、不允许写记忆、不允许调度）。默认值很保守——三个并发子智能体、50 次迭代预算、深度为 1——但 role="orchestrator" 配置加上一个派生深度设置可以解锁嵌套树，其中编排者提示词块明确写着“modeled on OpenClaw’s buildSubagentSystemPrompt”。后台委派返回一个句柄，结果通过一个完成队列作为全新的轮次重新进入，而不是在轮次中途拼接——这是一个为保护提示缓存而做的选择。在这之上还有一个进程级的层次：看板蜂群把“规划根节点 → 并行工人 → 验证者 → 综合者”作为独立的 hermes -p <profile> 子进程运行，通过一块 SQLite 看板和一块由结构化 JSON 评论组成的黑板来协调——是通过共享数据库而不是协议或通道实现的协调者-工人模式。第三个叠加层 /moa 会扇出若干提供参考意见的模型（最多八个并发），用它们的输出来调味主模型的下一次迭代。

11.8 Pi：子智能体是扩展，智能体舰队是一个包

Pi 的内核没有派生或 task 工具——子智能体是其“扩展论”的旗舰演示，以一个约 1,000 行的示例形式提供。每次调用都派生一个独立的 pi --mode json -p --no-session 操作系统进程，从构造上就提供了硬性的上下文隔离；父级解析子进程的 JSONL 标准输出来汇总进度和成本。一个工具提供三种形态：single、parallel（四个 worker 的池，最多八个任务），以及带 {previous} 替换的 chain。智能体定义是 Markdown 加头信息，通过子进程的 --tools 标志进行工具过滤；没有深度计数器，运行中途父子之间也不能互发消息。在单个进程之上，一个实验性的 orchestrator 包以 RPC 模式监管成群的 Pi 实例，并向一个托管的协调器登记在线状态——这是多实例管理，而不是循环内的协调者。值得注意的是，当 Pi 真的做多智能体时，它落在跨进程的 JSONL 上，而不是进程内原语上——第 13.3 节会再回到这个数据点。

11.9 OpenCode：权限推导能力的子会话

OpenCode 的子智能体是子会话，而不是独立的引擎：task 工具创建一个带 parentID 的 Session，运行同一个循环，可以通过 task_id 恢复，只返回包在 <task_result> XML 中的最终助手文本；后台结果作为合成的用户消息注入。智能体和模式统一在一个 schema 中（mode: primary|subagent|all）：内置的有 build、plan（除计划文件外禁止编辑）、general、只读的 explore，外加隐藏的 compaction/title/summary 工具型智能体——计划模式是一个权限规则集加一次 <system-reminder> 注入，而不是架构上的叠加层。工具的可用性处处由权限推导（对某个工具拒绝 "*" 就会把它从 LLM 的视野中移除），而且约束是不对称的：子级只继承父级的拒绝规则。递归默认关闭（task 对子级自动拒绝），但可以按智能体选择开启，且没有数字形式的深度上限；自定义智能体来自配置、Markdown 文件，或者——独一无二地——由 LLM 生成（对 {identifier, whenToUse, systemPrompt} 调用 generateObject）。

11.10 OpenClaw 基于会话的编排

OpenClaw 的多智能体模型从根本上不同：它通过一个 ACP 转换器运作，把 Gateway 的线上协议桥接到智能体进程（这里的 ACP 是 Agent Client Protocol，即 Zed/Google 面向编辑器的 JSON-RPC 标准，见 agentclientprotocol.com，而不是 IBM 更早的同名 Agent Communication Protocol）。子智能体作为带 RPC 绑定的子进程派生。每个智能体都有自己的会话，并以 JSONL 对话记录持久化。通信通过 ACP 增量事件（文本、思考、工具调用）进行，而不是共享内存。一个限流器（MAX_PROMPT_BYTES = 2MB）提供拒绝服务防护。

观察 7。协调者-工人模式在语料中独立地涌现：出现在全部四个厂商原生系统中（Claude Code、Codex、Gemini CLI、Mistral Vibe），出现在 OpenHands 中（基于对话树的并行委派），出现在 Hermes 中（由配置开启的编排者角色，外加一个在 SQLite 黑板上运行的子进程蜂群——一种新颖的协调基底），出现在 OpenCode 中（并发子会话），也在协议层出现在 OpenClaw 中。这里我们宽泛地使用“协调者-工人”一词，指任何由父级派生工人的委派方式；第 6 节中那个更狭义的规定性叠加层只适用于 Claude Code、Codex 和（经配置开启的）Hermes。如此多独立开发的代码库收敛到同一种层级形态，是趋同演化的有力证据——不过这种趋同应限定在把多智能体内建于核心的系统中：Pi 是一个生产级的软件工程 harness，却刻意以单智能体形式发布，把子智能体放逐到扩展空间。各实现在优化目标上的分歧颇具启发：Claude Code 分叉上下文并在子级之间共享提示缓存（成本）；Codex 构建一棵追踪深度的线程树，带有类型化的智能体间记录、按模型划分的工具代际和 CSV 扇出（隔离与规模）；Gemini CLI 把调用抽象到一个对称的本地/远程会话协议之后（可移植性）；Mistral Vibe 在进程内顺序运行子智能体（简单性）；Hermes 对工具集取交集，并默认屏蔽递归（约束）。Hadfield 等人 [17] 把编排者-工人描述为适用于“涉及大量并行、信息量超出单个上下文窗口、需要与众多复杂工具交互的高价值任务”的自然模式，这恰好也是对一个长周期编码会话的贴切描述。

11.11 编排流水线：Claude Code 与 Codex 对比

Claude Code 和 Codex 是两大主流商业编码智能体，各自代表其提供商生态中的最高水平。从用户请求到任务完成，它们端到端的编排流水线采取了非常不同的设计立场。表 18 突出了关键的分歧。

这张表揭示了两种自洽的哲学，而它们之间的差距在我们两份快照之间有了可测量的缩小。Claude Code 是组合式-规定式的：它强制执行结构化的阶段（调研 → 综合 → 实现 → 验证），通过工具白名单限制子智能体的能力，递归地组合智能体，并围绕提示缓存经济学做激进的优化。Codex 原本是沙箱化-涌现式的——安全在 OS 层面得到保证，工作流的组织交给模型——但它也发展出了自己的规定性结构：一个带 Plan 预设的面向用户的协作模式选择器、声明式的子智能体角色、追踪深度的派生控制，以及一个与 Claude Code 中间那层权限相对应的 Guardian 分类器；与此同时，Claude Code 的 hook 词汇和插件格式已经成为 Codex 的接口（第 14.5 节）。两者在真实世界的基准上都取得了很好的结果；剩下的哲学差异在于安全在哪里得到保证（OS 强制执行还是分层审查），而不在于工作流如何组织。

12 可扩展性机制

语料中的每个系统都提供扩展点，只是机制相当不同。

12.1 插件架构

OpenClaw 提供了语料中最成熟的插件架构——而且自 2026 年春季的发布版以来，它还是一个外置化的架构：官方的提供商插件和渠道插件被切换为独立的一等 npm 包，采用清单优先的元数据，把模型目录和路由表移出了内核。插件由清单驱动（openclaw.plugin.json），在工作区目录中被发现，通过 jiti 动态加载，并通过带类型的 SDK 契约注册：

  • 渠道插件：实现 ChannelEntry（接收、发送、状态、配置）。
  • 提供商插件：实现 ProviderEntry（推理流）。
  • Skill 插件：通过能力系统注册。

它强制执行严格的导入边界：扩展的生产代码只能导入公开的插件 SDK 接口和本地 API 汇总模块，禁止直接导入 src/**。

不过，OpenClaw 在“清单驱动插件”阵营中已不再孤单。Codex 的插件架构在我们两份快照之间大幅扩展：在原有的插件管理器之外，又加入了市场添加流水线（GitHub、git、本地路径、URL）、一个可由模型在对话中调用的审批工具（request_plugin_install）、对 .claude-plugin 格式的兼容，以及工作区级的共享；插件可以贡献工具、skills 和生命周期 hooks。OpenHands 的插件系统把这种趋同表现得再明白不过：它的插件打包了 skills、hooks、MCP 配置、智能体和命令，而它的清单加载器接受 [".plugin", ".claude-plugin"] 这两个目录以及其中的 plugin.json——它是刻意去读取 Claude Code 的插件格式，这是语料中“通过采纳实现互操作”最清晰的案例。Claude Code 本身通过一个带内置、自定义和插件来源的 JSON/Zod schema，支持 MCP 服务器（用于外部工具）、skills（用于专门工作流）和智能体定义（用于自定义智能体类型）（第 11.2 节）。Pi 则把整个问题挪了个位置：扩展是运行时加载的 TypeScript 模块，面向一套约 33 种类型化事件的 API，涵盖会话生命周期、工具拦截（阻止调用和就地修改参数）、整个上下文的改写，以及——不同寻常地——对提供商原始 I/O 动手术（before_provider_request、after_provider_response）；仓库附带 78 个示例，逐项功能对照来看，它们正是其他 harness 的内置功能，大多每个只有 1–16 KB，通过包管理器分发（pi install npm:…|git:…）。OpenCode 的插件是返回约 20 种类型化 hook 的异步函数（chat.params、tool.execute.before/after、改写 tool.definition、多步 OAuth auth 流程），为保证确定性而顺序执行；自定义工具根本不需要插件——任何 .opencode/tool/*.ts 导出都会成为一个工具。

Gemini CLI：扩展 + 斜杠命令 + 早期采用 MCP。

Gemini CLI 提供一个明确的 ExtensionLoader 接口，以 GeminiCLIExtension 类型为支撑。扩展可以贡献自定义工具（通常通过 MCP）、斜杠命令、hooks、skills 和 GEMINI.md 片段，并从 ~/.gemini/extensions/ 目录中被发现。Gemini CLI 是 MCP 的早期采用者，对 stdio 派生的本地服务器、SSE 连接和 Streamable HTTP 传输都有一等实现，外加内置的认证提供方（google-credentials、OAuth）。它的 MCP 支持不止于工具，还扩展到 prompts 和 resources（更完整的 MCP 规范），而大多数其他系统的适配器都省略了这些。斜杠命令（/agent、/mcp、/skill、/memory、/help）本身也可以通过 skill 元数据扩展，允许扩展注册新命令。

Mistral Vibe：Skills、MCP、自定义工具、智能体与 hooks。

Mistral Vibe 的可扩展面已经发展到五个相互正交的维度。Skills 遵循 agentskills.io 规范 [43]：每个 skill 是一个目录，其中包含一个带 YAML 头信息的 SKILL.md，从 .agents/skills/、.vibe/skills/、~/.vibe/skills/、~/.agents/skills/ 以及用户配置的任意路径中发现——现在还补充了内置 skills（包括一个向 harness 自己介绍自己的“自我认知” skill），以及一个从托管目录安装带版本 skills 的远程注册中心客户端。完整的跨系统比较见第 12.5 节。MCP 服务器以 [[mcp_servers]] 块声明，支持 http、streamable-http 和 stdio 传输，工具的命名空间为 {server_name}_{tool_name}，权限处理与内置工具完全相同；这一层在两份快照之间成熟为一个托管的集成面——从 TUI 驱动的 OAuth 登录流程（/mcp add|login|logout|status）、一个精选的托管 Mistral “connectors”注册中心，以及一个 MCP sampling 处理器，允许已连接的服务器借用 Mistral Vibe 的 LLM 后端完成它们自己的补全，这是语料中其他系统都没有实现的反向依赖。自定义工具可以通过基于路径的发现（tool_paths）添加；自定义系统提示词放在 ~/.vibe/prompts/{prompt_id}.md；自定义智能体放在 ~/.vibe/agents/{agent_name}.toml，通过深度合并机制覆盖基础配置——而这本身现在也是一个明确的配置层栈的一部分（默认值、用户 TOML、受信任项目的 .vibe/config.toml、VIBE_* 环境变量、运行时覆盖、智能体配置）。第五个维度是面向用户的生命周期 hooks：在 hooks.toml 中声明的 before_tool/after_tool/post_agent_turn shell hooks 可以拒绝一次工具调用、改写其输入或追加上下文——在结构上与 Claude Code 的 PreToolUse/PostToolUse 是直系亲属，叠加在内部中间件管线之上（而不是取代它）。

12.2 基于协议的接口

Mini-SWE-Agent 使用 Python Protocols 实现结构化子类型：任何实现了 Model、Agent 或 Environment 协议的类都可以直接替换，无需继承。这是最轻量的扩展机制，不需要注册、不需要清单、也不需要 SDK，只需符合接口。

12.3 配置驱动的可扩展性

Aider 的模型注册表包含 350 多个模型的逐模型元数据，包括编辑格式、弱模型名称、缓存控制设置、额外 API 参数、推理标签处理和编辑器模型配置。这种数据驱动的方式让它无需修改代码就能支持新模型。

Codex 的分层 TOML 配置现在延伸到了用户之上：移动设备管理（MDM）层、主机级系统层和企业云端下发层作为基础默认值进入，位于用户（config.toml 加具名配置）、项目（.codex 目录）和会话参数这几个范围之下；同时，一个单独组合的要求/约束引擎（由同样的 MDM、系统和云端来源供给）负责校验，并可以硬性限制下层能设置什么。这是语料中最面向企业治理的配置模型。Mistral Vibe 现在也采用了类似的分层方式（六层，由一个 ConfigBuilder 按字段的合并策略合并），使显式的配置层栈成为一个两个系统共有的模式。

OpenClaw 的配置系统是语料中最复杂的：一个经 Zod 校验、包含数百个嵌套结构的 openclaw.json，外加一个为所有内置渠道自动生成的大型 TypeScript 校验规则文件，以及一个手工维护的 schema 帮助说明。

12.4 Model Context Protocol（MCP）

MCP 仍然是一种横切的扩展机制，Claude Code、Codex、Gemini CLI、Mistral Vibe、OpenHands、Hermes、OpenCode 和 OpenClaw 都支持它——11 个系统中的 8 个（10 个编码优先系统中的 7 个）。OpenHands 通过 MCPToolAction/MCPToolObservation 事件类型实现 MCP，用单一的 MCPServer 模型校验四种传输（stdio、http、streamable-http、sse），并提供一等的认证，直到带令牌状态的完整 OAuth 流程。Hermes 的支持近乎完整（stdio/Streamable HTTP/SSE、resources、prompts、sampling、elicitation、OAuth；只忽略了提示词列表变更通知），而且 Hermes 本身也是一个 MCP 服务器，与 OpenClaw 的渠道桥接相当。OpenCode 覆盖了 tools、prompts、resources 和 resource templates，并支持 OAuth 动态客户端注册（sampling 和 elicitation 被明确禁用，并附有指向跟踪 issue 的注释）。语料中唯一一个出于原则而拒绝的是 Pi，它的文档直接拒绝 MCP——“build CLI tools with READMEs”——把“skills + shell”作为它明确提出的、替代线上协议的方案。

12.5 Skills：一种正在兴起的能力包标准

在 MCP 之外，语料中还出现了第二种横切的扩展机制：skills。MCP 标准化的是智能体如何与外部工具进程对话；skills 标准化的是智能体如何把一份专业知识打包成一个可被发现的目录（说明、可选脚本、可选工具白名单、元数据），可以放进项目或用户主目录，由智能体在发现阶段拾取。Mitra 等人 [80] 从训练的角度阐述了同样的想法：skills 是智能体工作流中可以被传授的单元。十一个系统中有九个实现了某种形式的 skills 系统；只有 Aider 和 Mini-SWE-Agent 没有（表 10）。

在 SKILL.md 格式和 .agents/skills/ 路径上趋同。

在九个采用者中，格式基本上是统一的：一个以 skill 命名的目录，其中包含一个带 YAML 头信息的 SKILL.md 文件（至少有 name 和 description，常常还有 paths、requires 或 user-invocable 等可选字段）。.agents/skills/ 这个发现路径，即 agentskills.io 的标准位置，被六个系统接受（Mistral Vibe、Gemini CLI、OpenClaw、OpenHands、Pi、OpenCode），而各厂商专属的主目录（~/.claude/skills/、~/.gemini/skills/、~/.vibe/skills/、~/.hermes/skills/、~/.pi/agent/skills/、~/.openclaw/skills/）与项目本地的对应目录并存。最鲜明的互操作数据点是：OpenCode 刻意去搜索竞争对手的主目录——它的发现列表包括 ~/.claude/skills 和 .claude/ 目录，因此为 Claude Code 安装的 skills 无需修改就能在 OpenCode 中使用。

Skills 对 MCP：平局已被打破。

MCP 和 skills 处理的是不同的层次。MCP 是一种线上协议，供智能体与一个单独运行、暴露 tools、prompts 和 resources 的进程对话；skills 是一种文件系统约定，用于打包一份由智能体直接读取的“说明 + 脚本”套件。两者可以组合：Claude Code 的 skill 注册表会对 MCP 提供的、看起来像 skill 的 prompts 去重；Mistral Vibe 则从另一个方向组合，允许 MCP 服务器通过 sampling 借用它的 LLM，同时 skills 从一个托管注册中心而来。四月时，两个标准的采用率打成平手，都是 6/8；扩大后的七月语料打破了平局，skills 胜出——skills 9/11，MCP 8/11——因为 Pi 实现了 agentskills.io，同时直接拒绝了 MCP。“用 skills 取代 MCP”现在是一个被明确提出的立场，而不再只是两者并存。

延迟加载成为主导模式。

与 Claude Code 的延迟加载工具（第 8.3 节）相呼应，九个采用者中有八个现在只预加载 skill 元数据，正文按需获取——通过专门的工具（SkillTool、ActivateSkill、skill、OpenHands 的 invoke_skill），通过 $ 提及和隐式调用检测（Codex），通过三层披露链（Hermes），或者最简地，通过普通的 read 工具读取一份 XML 索引（Pi）。OpenHands 四月时还是一个预加载的异类，在 V1 SDK 中转向了渐进式披露；OpenClaw 仍然是唯一一个预加载者，它用资格把关来弥补，使不符合条件的 skills 永远不会进入提示词。

门控与条件激活。

在架构上最有意思的变化是条件激活。OpenClaw 的 skills 声明运行时要求（PATH 上的二进制程序、环境变量、操作系统家族），并在加载时被过滤，避免“如何使用 kubectl”在一台没有 kubectl 的机器上污染提示词。Claude Code 的 paths 头信息会在模型触及匹配文件时（通过 Read、Edit 或 Write 工具）激活一个 skill，而 OpenHands 现在把同样的想法实现为在触及文件时注入的 PathTrigger 规则——把 skills 与 [19] 的即时上下文哲学结合了起来。相对于 MCP，这是一个结构性的进步，因为 MCP 对每个已连接的服务器一视同仁，不管它的工具是否与当前任务相关。

Skills 有了供应链——也有了作者。

分发在一个季度内就专业化了。远程注册中心现在存在于四个系统中（Mistral Vibe 的托管目录客户端、OpenCode 带版本索引缓存的 URL 注册中心、Hermes 的 Skills Hub、OpenHands 的市场 API），随分发而来的是供应链安全：Hermes 实施信任分级、安装前静态扫描、隔离区和依赖检查；OpenClaw 让安装经过一个审批流程，并使用经来源验证的来源；Gemini CLI 加固了 skill 安装以防路径穿越；Codex 会自动安装 skill 所声明的 MCP 服务器依赖（可选先询问）。更引人注目的是，skills 有了非人类的作者：Hermes 的后台审查智能体会从已完成的任务中创建和修补 skills（还有一个策展者维护整个集合），而 Gemini CLI 的提取子智能体会把会话挖掘成 skill 补丁，放进收件箱供审查。能力包这一层正以惊人的速度获得包管理器式的经济形态——注册中心、来源证明，以及如今的生成式包。

观察 8。Skills 已经超越 MCP，成为语料中采用最广的可扩展性标准：9/11 个系统实现了 SKILL.md 套件（只有 Aider 和 Mini-SWE-Agent 没有），而 MCP 是 8/11；四月的平局被 Pi 明确的“要 skills、不要 MCP”的立场打破。三项二阶发展标志着这一层的成熟：延迟加载现在几乎是普遍策略（9 个采用者中的 8 个）；条件激活（Claude Code 的 paths、OpenHands 的 PathTrigger、OpenClaw 的 requires）把即时上下文工程推进到了可扩展性层；而且一条供应链已经出现——四个系统中有托管注册中心，Hermes 有信任分级和隔离区，OpenClaw 有来源验证——同时出现的还有第一批由智能体编写的 skills（Hermes 的自我改进循环、Gemini CLI 的提取收件箱）。

13 横切观察与启示

13.1 架构模式目录

表 11 和表 12 列出了在十一个系统中识别出的 29 种反复出现的设计模式：四月版的十七种（成员已更新），加上扩大后的语料贡献或使之定型的十二种。

13.2 双重缺席：没有智能体框架，没有代码 RAG

在更广泛的 LLM 应用文献中被视为任何生产级智能体核心的两项技术，结果在全部十一个系统中都不见踪影。8 就本分析而言，这些缺席至少与那些存在一样富有信息量。

缺席一：智能体框架。

我们检查了每一份依赖清单，并在每一棵源码树中 grep 广泛部署的智能体框架的导入：LangChain、LangGraph、LlamaIndex、AutoGen、CrewAI、Pydantic AI、Genkit、Haystack agents、Semantic Kernel、Google 的 ADK，以及若干较小的库（Smolagents、Swarm、Agno）。在大约 400 万行 Python、TypeScript 和 Rust 代码中，没有任何一条生产智能体代码路径导入其中任何一个——这个结果值得从两个方向细细品味：Gemini CLI 连 Google 自家的两个框架（Genkit、ADK）都没用，而 Hermes 中仅有的“LangChain”字符串位于内置的 skill 文档里，内容是教智能体用户可能会如何使用向量数据库。有两个边界情况需要说清楚。Aider 附带一个可选的、与框架沾边的附加组件：它的 /help 命令可以安装 llama-index，对 aider 自己的文档做文档 RAG——这是一个可选的功能依赖，而不是智能体循环的编排。OpenCode 则把内部的 LLM/工具管道交给 Vercel 的 AI SDK——这是一个提供商抽象层，而不是智能体编排框架，但它是语料中第一个内部循环管道用到第三方 SDK 的系统（一个自研的替代客户端位于功能开关之后，表明这一依赖是过渡性的）。

每个循环都是用宿主语言的原生原语手写的：asyncio（OpenHands、Mistral Vibe、Hermes）、阻塞式同步 Python（Aider、Mini-SWE-Agent）、Promise/异步迭代器（Claude Code、Gemini CLI、Pi、OpenCode、OpenClaw）、Tokio（Codex）。每个工具注册表都是围绕 Pydantic、Zod、TypeBox、Effect Schema 或 Rust 枚举自行构建的。每个提示词模板都是普通的 Markdown、Jinja2 或字符串拼接。

缺席二：针对代码的检索增强生成。

我们并行开展了另一项搜索，覆盖向量存储依赖（Chroma、Pinecone、Weaviate、Qdrant、Milvus、FAISS、LanceDB、sqlite-vec、向量模式下的 Elasticsearch）、嵌入库，以及名称匹配 embedding、vector_store、vectordb、rag 或 retrieval 的文件夹或文件。对于代码检索，结果没有变化，而现在覆盖了十一个系统：零。所有例外都与对话记忆有关，而在这一点上七月的图景确实有所变化：OpenClaw 的默认记忆插件（memory-core）现在运行一种混合的 sqlite-vec KNN + FTS5/BM25 搜索，嵌入默认开启（提供方默认是 OpenAI；本地 GGUF 模型需选择开启；四月时代的 LanceDB 扩展作为可选插件保留下来），使 OpenClaw 成为唯一一个默认开启嵌入的系统——用于聊天回忆，从不用于阅读源码树。Hermes 在大规模上展示了相反的选择：它核心的历史对话搜索刻意采用词法检索（由触发器维护的 SQLite FTS5，BM25 加上针对中日韩文字的三元组分词，“任何地方都不调用 LLM”），嵌入只局限在需选择开启的记忆插件中。

双重缺席为何重要。

第一项缺席印证了智能体设计者自己的建议。Schluntz 和 Zhang 的 Building Effective Agents [16] 告诫说，框架“常常会制造额外的抽象层，遮蔽底层的提示词和响应，使其更难调试”，并建议从原始 SDK 调用开始。这条建议发表于 2024 年 12 月；我们在 2026 年所做的源码审计表明，每一家商业提供商都遵循了它。这一点值得注意，因为在同一时期，更广泛的 Python LLM 应用社区一直在持续投资框架抽象。生产级软件工程智能体所遵循的复杂度预算，似乎与通用 LLM 应用不同。一旦智能体开始修改真实的源代码，手写的、可调试的代码就会胜过可复用的抽象，因为那些故障模式（悄无声息的提示词损坏、不透明的缓存、版本不兼容的工具 schema）代价太高，无法一笑置之。

第二项缺席与 Rajasekaran 等人 [19]（2025 年 9 月）最近的指导意见一致：他们偏向“即时”（JIT）检索，同时推荐一种混合方法：“我们并不记住整个信息语料，而是引入文件系统、收件箱和书签这样的外部组织和索引系统，按需检索相关信息。”这篇博文并没有一口否定预建索引的检索，但它的实践建议全都指向 JIT 方法。语料中的每个系统都遵循这一方法，尽管仓库级的代码检索是一个被充分研究过的领域：RepoCoder [60]、RepoBench [61] 和 CrossCodeEval [62] 都为代码构建了检索流水线，Long Code Arena [64] 则提供了相应的长上下文评测。Wang 等人的 CodeRAG-Bench [63] 提出的正是本节提出的问题——“检索能增强代码生成吗？”——并发现收益在不同任务之间差异极大：在文档查阅和库使用场景中提升可观，但在模型已经具备足够参数化知识的任务中提升甚微或没有提升。这些收益的不一致，或许有助于解释为什么生产级软件工程智能体干脆完全跳过 RAG 层，而不是投资于依任务而定的检索路由。原因是领域特有的。代码携带着密集的、确定性的结构元数据——文件路径、语言服务器、tree-sitter 解析结果、类型信息——这是语义相似度检索无法复制的（而 RepoAgent [65] 和 Aider 的 RepoMap 等感知结构的工具则直接利用这些信息）。代码每分每秒都在变化，因此预建索引的嵌入几乎从构造上就是过时的。每个编码环境本来就自带一套近乎最优的检索系统，那就是 ripgrep、find 和 glob。在典型的软件工程智能体任务上，RAG 只增加运营成本（嵌入计算、向量存储维护、漂移管理），却不提供边际价值。

观察 9。在更广泛的 LLM 应用文献中被视为核心的两项技术，在全部十一个系统中都不见踪影——这一发现经受住了语料扩大到三倍和为期三个月的复核。没有任何系统在其智能体运行时中使用通用智能体框架（LangChain、LangGraph、AutoGen、CrewAI，或我们检查过的其他十几种中的任何一种；Gemini CLI 连 Google 自家的两个框架都不用）；每个循环都是用宿主语言的异步原语手写的，OpenCode 在内部管道中使用提供商抽象 SDK 是最接近的边界情况。没有任何系统用向量嵌入 RAG 做代码检索；所有系统都依赖 ripgrep、tree-sitter、glob 和自动发现的 Markdown 上下文文件；而在需要对话规模的回忆时，生产环境的答案是词法搜索（Hermes 的 SQLite FTS5），或者在恰好一个默认配置中（OpenClaw）对聊天历史使用混合嵌入——从不针对源码树。生产级 harness 所遵循的复杂度预算与通用 LLM 应用不同：当故障模式是修改真实代码时，可调试性和提示词透明度比框架复用更重要。第 14.2 节为这一缺席给出了它在历史上的归宿。

观察 10。Anthropic 的 Effective Agents 工程系列（2024 年 12 月至 2025 年 9 月）中描述的架构模式，与在四个独立构建的厂商原生系统中观察到的架构高度吻合。这反映的是共同的经验现实、公开指南的影响，还是两者兼有，仍是一个开放问题。

13.3 智能体间协议：对外采纳，对内进程内

双重缺席涉及的是两项根本没有在语料中出现的技术。智能体间协议（ACP、A2A）则又是另一种模式——而这是在我们两份快照之间变化最大的维度。ACP 现在作为一等的生产依赖或实现，出现在十一个系统中的六个里：Mistral Vibe（agent-client-protocol==0.10.1，通过协议暴露会话分叉、工作区信任和回退）、OpenClaw（网关转换器）、OpenCode（opencode acp 通过 stdio 提供智能体一端）、Hermes（ACP 适配器和注册表模块）、OpenHands（一个 ACPAgent 类，下文讨论），以及 Gemini CLI（它的 A2A 模块是承担网格角色的另一种协议）。在语料之外，xAI 的 Grok Build 在发布第一天就带有文档记载的 ACP 服务器模式（第 3.7 节；有厂商文档，未经源码核实）。语料中的采用没有一个是实验性的。

有意思的是它们所处的位置——而 ACP 现在占据了三种不同的架构角色：

  • 编辑器 ↔ 智能体（对外的服务器）。这是 ACP 的“LSP 角色” [41]：Zed、JetBrains 和其他 IDE 像驱动语言服务器一样驱动本地智能体。Mistral Vibe、OpenCode、Hermes、OpenClaw 和 Grok Build 都服务于这一边界。
  • 智能体即后端（对内的宿主）。这是四月时无人担当的角色：OpenHands 的 ACPAgent 把它的 step() 委派给一个外部 ACP 服务器，并为固定版本的 claude-agent-acp、codex-acp 和 gemini --acp 二进制程序提供提供商元数据——竞争对手的 harness 变成了 OpenHands 对话中可以互换的“大脑”。第 14.4 节的 meta-harness 用同样的方式驱动它的 Goose 和 Qwen 适配器（并在驱动 Kiro 的 TUI 时接入其 ACP 权限流），Hermes 则把一个 ACP 智能体当作模型传输层来使用（把 GitHub Copilot 的 CLI 当作聊天后端）。为编辑器打造的协议，结果成了托管的接口。
  • 跨厂商网格（A2A [42]）。在语料中仍然只有 Gemini CLI 一家：远程编排器把本地的 Gemini CLI 当作多厂商拓扑中的一个节点来驱动，现在还会通过线上传输用量元数据。

表 14 列出了每个多智能体系统在主智能体与其自身子智能体之间使用的通信机制，以及它的协议角色。

四月版提出的“对内/对外”划分以更精细的形式保留了下来。在协调自己的子智能体时，九个多智能体系统中有八个仍然使用进程内原语，或者在跨进程时使用标准协议以外的东西：Pi 的扩展派生说普通 JSONL 的操作系统进程，Hermes 的蜂群通过一块 SQLite 黑板协调。变化之处在于对整个 harness 的对内消费：把竞争对手的智能体作为可替换的后端来托管——OpenHands 的 ACP 托管、Hermes 把 ACP 当作模型传输层、meta-harness 的适配器舰队——是一种四月时还不存在的生产模式，而 ACP 是它的通用语。Pi 补上了最后一个细节：它拒绝标准协议，却为同样的嵌入角色发明了一个专有的对外 RPC——这证明即便在标准被拒绝的地方，对外协议的压力也是真实存在的。

观察 11。智能体间协议的位置，已经从两种角色的故事（对外：编辑器集成和网格；对内：无）演变为三种角色的故事。ACP 出现在十一个系统中的六个里，现在服务于：（1）它设计之初的编辑器 ↔ 智能体边界；（2）一个超出协议设计初衷的角色——托管 harness，OpenHands 把 Claude Code、Codex 或 Gemini CLI 当作可互换的 step 后端来运行，Hermes 把一个 ACP 智能体当作模型传输层来使用；以及（3）通过 A2A（仍然只在 Gemini CLI 中）实现的跨厂商网格。对于 harness 自己的子智能体，九个多智能体系统中有八个仍然使用进程内原语，或在跨进程时使用标准协议以外的东西（Pi 的 JSONL 扩展、Hermes 的 SQLite 黑板蜂群）；OpenClaw 的 ACP 派生是唯一一个通过标准协议路由子智能体协调的案例。给实践者的指导也相应地变得更明确：构建一个 ACP 服务器（现在它能同时为你带来编辑器、宿主和元编排器）；让你的子智能体留在进程内；把 A2A 视为对跨厂商网格的一次押注，其大规模需求仍未得到证明。

13.4 权衡框架

我们把五个基本的权衡轴形式化：

轴 1：简单性对能力。

据报告，Mini-SWE-Agent 的极简脚手架在 SWE-Bench Verified 上达到 74% 以上，而 Codex 庞大得多的代码库报告的是 69.1%。这些数字不能直接比较（底层模型不同、评测运行不同、部署配置不同：Mini-SWE-Agent 没有沙箱，Codex 有沙箱），我们也不据此得出正面对比的结论。这一差距在定性上说明的是：Codex 中额外的代码并没有投入到原始的任务完成逻辑上，相当一部分投入到了安全（跨平台沙箱）、用户体验（TUI、流式输出）、可扩展性（MCP、插件）和稳健性上。在条件匹配的情况下，生产级脚手架能否在同一基准上带来可测量的提升，是一个本研究没有回答的开放问题（关于效度威胁，见第 15 节）。

轴 2：安全对自主。

安全基础设施更多的系统（Codex、Claude Code）会给智能体的动作带来更多摩擦。安全措施较少的系统（Mini-SWE-Agent、Aider）执行更快，但若不加额外防护，就不适合企业部署。

轴 3：提供商耦合对提供商无关。

Claude Code 和 Codex 利用提供商特有的功能（提示缓存、扩展思考、针对特定模型的提示词），代价是厂商锁定。基于 LiteLLM 的系统为了提供商的灵活性而牺牲了这些优化。

轴 4：单体对模块化。

Codex 由 126 个 crate 组成、百万行代码的 Rust 工作区，针对类型安全和性能做了优化。Mini-SWE-Agent 的单文件智能体则把可理解性最大化。Pi 把整条轴挪进了运行时组合：一个极简内核加上一条扩展事件总线。OpenClaw 的插件 SDK 和 OpenCode 的客户端/服务器拆分，分别带来了可扩展性和可嵌入性。这条光谱上的每个点服务于不同的用户群体。

轴 5：脚手架复杂度对模型能力。

这是在哲学上最有意思的一条轴。Mini-SWE-Agent 有竞争力的基准表现表明，当前的模型已经足够强大，只需极简的脚手架就能成功。生产系统投资脚手架，并不是因为模型完成任务需要它，而是因为用户需要它来获得安全、可靠性和工作流集成。

注 8：我们原本预期至少会在开源项目里找到对 LangChain 或其他框架的某些使用。这种一致性让我们感到意外；在接受这一结果之前，我们花了好几周寻找反例（打包进来的依赖、动态导入、转译后的 TypeScript 构建产物）。七月的复核在全部十二棵代码树上重复了依赖清单和导入扫描，包括三个新加入语料的系统和那个 meta-harness。 ↩

14 平台转向

前面各节把 harness 当作一件产物来剖析。本节要论证的是，这件产物已经换了类别：在 2025 年到 2026 年年中之间，编码智能体 harness 完成了从工具到平台的转向——它成了一个运行时，拥有自己的扩展生态、包经济、治理层、转换成本，而且自 2026 年 6 月起还有了自己的元层。本研究的四月版曾以“CLI 即框架假说”的名义提出过这一论断的谨慎版本。此后积累的证据——来自语料自身的源码树、厂商 SDK 和市场——让我们可以把它作为一个论点明确提出。

14.1 从假说到论点：CLI 即框架

对 LangChain、AutoGen 等框架缺席的标准解读（观察 13.2）是：生产级 harness 不需要框架。但还有第二种解读：它们之所以不需要框架，是因为 harness 本身就是框架——是开发者交付软件时默认使用的编排层，而不仅仅是他们拿来查询的工具。

想一想框架传统上提供什么：一个循环、一个工具注册表、一个记忆层、一个配置面、一个扩展机制。这里研究的每一个生产系统都具备其中的每一项。Claude Code 提供一个流式 ReAct 循环、43 个注册工具、一个基于压缩的记忆管理器、由 CLAUDE.md 驱动的配置、用于集成的 MCP 和用于能力包的 Skills——Codex、Gemini CLI、Mistral Vibe、Hermes 和 OpenCode 也都如此，只是各有各的风格（Pi 具备除 MCP 之外的每一项要素，它明确拒绝 MCP，转而选择 CLI 工具加上它的扩展总线）。区别在于，这个“框架”不是开发者导入到自己代码中的库；它是开发者在其中工作的运行时。开发者的“程序”是一个自然语言任务，加上一棵配置智能体行为、工具访问和领域知识的 Markdown 文件树（CLAUDE.md、AGENTS.md、GEMINI.md、SKILL.md）。“API”是文件系统、终端和 git。

语料中有四个趋同的信号支持这一解读。

信号 1：作为声明式程序的 skills。

十一个系统中有九个实现了 Skills（观察 12.5）：包含一个 SKILL.md（内有说明、可选脚本和元数据）的目录。从功能上说，一个 skill 就是一个为 LLM 运行时而不是 CPU 运行时编写的程序。它声明智能体应该做什么（SKILL.md 正文）、何时应该激活（Claude Code 中的 paths 头信息、OpenHands 中的 PathTrigger 规则、OpenClaw 中的 requires），以及可以使用哪些工具。这在结构上相当于传统框架中的插件，只不过编程语言是英语加 YAML 头信息——而且这一层现在已有注册中心、供应链安全和智能体作者（第 12.5 节）。

信号 2：作为扩展基底的 hooks 和事件总线。

四月时，面向用户的生命周期 hooks 是 Claude Code 的特色。到七月，它们已是占主导地位的扩展基底——十一个系统中有九个支持，只有 Aider 和 Mini-SWE-Agent 没有：Codex 提供的 hooks 事件名与 Claude Code 逐字相同；OpenHands 把 pre_tool_use/post_tool_use/stop hooks 接入 Agent.step()，并允许用一个智能体作为 hook 处理器；Mistral Vibe 在内部中间件管线之外加入了 hooks.toml shell hooks（拒绝、改写输入、追加上下文）；Gemini CLI 向扩展暴露十一个循环生命周期事件；Pi 本身就是一条事件总线，约 33 种类型化事件，从工具拦截一直到提供商原始 I/O；OpenCode 的插件是返回二十种类型化 hook 的函数。这与 Web 框架和构建系统几十年来一直使用的扩展模型相同，只是应用到了 LLM 执行循环上。开发者不是在为智能体写代码，而是在智能体内部写代码。

信号 3：工具与工作流之间正在消失的边界。

在传统开发工作流中，开发者写代码、跑测试、读日志、提交、开 PR，是一个个独立的步骤。在 harness 工作流中，这些步骤通过自然语言指令委派给智能体，并通过智能体的工具系统执行。智能体循环就是工作流引擎：Claude Code 的协调者阶段、Codex 的 update_plan 工具和 /goal 工作流、OpenHands 经评审审核的目标循环。当开发者输入一个任务，智能体派生子智能体、分派工具、管理上下文并产出结果时，CLI 已经接管了构建系统、任务运行器和 IDE 的角色。

信号 4：作为服务接口的 harness。

四月之后最清晰的信号是：harness 现在提供的是平台的接口。OpenCode 内嵌一个 HTTP 服务器，发布 OpenAPI 规范和自动生成的 SDK，每一个 UI——TUI、桌面、Web、IDE 插件、CI action——都是客户端。OpenHands 通过一个 OpenAI 兼容网关暴露对话，因此任何能调用 chat-completions 端点的工具都能驱动智能体：智能体即模型。Mistral Vibe 能把本地会话“传送”到托管运行时；Claude Code 把它的 SDK 与托管的 Managed Agents API 配套。一个拥有客户端、SDK 和托管档位的运行时，不是一个带生态的工具；它是一个拥有分发渠道的平台。

14.2 Harness 与框架的合并

如果 harness 就是框架，那么这两类产物理应合并——而在 2026 年，它们正从两个方向明显地合并（表 15）。

无论是从终端产品出发，还是从编排库出发，两个方向都收敛到同一种产物形态——循环 + 工具 + skills + 子智能体 + hooks + MCP + 会话。这种收敛本身就是一种验证：当 LangChain——观察 13.2 记录了它在所有 harness 运行时中的缺席——终于构建了一个 harness 时，它独立地采纳了语料中的约定（SKILL.md 渐进式披露、AGENTS.md 记忆、子智能体派生、待办规划）。下一小节的 meta-harness 则从上方补全了这幅图景：它的基线安装把 claude-agent-sdk 和 openai-agents 作为生产依赖导入——2026 年的编排层所依托的“框架”就是 harness SDK。2025 年那一代框架的双重缺席由此得到了它在历史上的归宿：harness 没有采用这些框架，而是取代了它们，自己变得可以被导入，并把“我该用哪个智能体框架？”这个问题变成了“你已经在用哪个 harness？”。

14.3 平台经济学：市场、转换成本、治理

九十天窗口中的三项进展，是教科书式的平台经济学。

市场。

Codex 有了一个插件市场（GitHub/git/URL 来源、对话内安装审批、工作区共享）；skills 注册中心出现在四个系统中，带有信任分级、来源验证和隔离区（第 12.5 节）；OpenClaw 把它的官方插件外置到了 npm。能力分发现在有了应用商店式的机制——包括应用商店的安全病症，正如 SkillProbe 对已发布 skills 的审计所显示的那样 [89]。

转换成本。

Codex 提供了一个一等的导入器，用于导入 Claude Code 存在磁盘上的状态：它检测 ~/.claude/projects 中的会话 JSONL 文件，在一份导入台账下把它们转换为 Codex 的 rollout 条目，并提议把 ~/.claude/settings.json 转换为 ~/.codex/config.toml。厂商们为彼此的会话存储编写导入器，标志着平台竞争进入了用户数据成为护城河的阶段——而与之抗衡的力量同样清晰可见：OpenCode 读取 Claude Code 的 skills 目录，OpenHands 读取 Claude Code 的插件清单，并直接托管竞争对手的 harness，而 meta-harness 则把每家厂商的锁定机制套利成自己的适配器接口。

企业治理。

Codex 的配置栈现在延伸到了用户之上——MDM 管理的偏好设置、主机级系统文件和企业云端下发的配置包，既提供基础默认值，又供给一个约束引擎，后者可以硬性限制用户和项目范围能设置什么。与此同时，Google 宣布 Gemini CLI 将过渡到以 Antigravity 为品牌的 CLI——闭源的，而 Gemini CLI 是 Apache-2.0（第 3.7 节）——并撤回了面向消费者的免费档；SpaceX 与 xAI 的合并，加上已宣布的 600 亿美元收购 Cursor（截至 2026 年 7 月尚待完成），以收购级的价码为 harness 层定了价。治理层、门控档位和收购级定价，是平台而非独立工具的标志。

14.4 Meta-harness 层

Omnigent [25] 不是第十二个 harness；它押注的是：harness 已经成为商品化的组件，而持久的价值位于更上一层。Databricks 于 2026 年 6 月将其开源（Apache 2.0，总计约 100 万行，其中生产 Python 约 31.2 万行）：一个四层的进程拓扑（服务器 ⇄ 主机守护进程 ⇄ runner ⇄ 每个对话一个 harness 子进程），按照明确的设计，其适配器边界是 Omnigent 自身公开 REST API 的一个递归子集。它的注册表提供 23 个标准 harness 适配器（外加 16 个别名和一个社区入口点组），涵盖 Claude Code、Codex、Cursor、OpenCode、Hermes、Pi、Goose、Qwen、Kimi、Kiro、Copilot 和 Antigravity，并形式化为五种集成模式（sdk-in-process、cli-subprocess、acp-subprocess、native-tui、native-server）——所声明的能力会与一套一致性测试台核对（探测基本轮次、工具调用、流式输出、中断、模型覆盖、策略拒绝），其中四个旗舰 SDK 适配器已完成实时验证，其余则是尽力而为的声明。Harness 像硬件一样被测试。

在这条边界之上，元层增加了四样任何单个 harness 都不提供的东西。组合：注册表中的任何 harness 都可以作为其他任何 harness 的子智能体会话来调用，因此一个以 Claude 为“大脑”的编排器可以把工作派给 Codex，再让 Cursor 来审查。跨 harness 策略：一个三级策略平面（会话 → 智能体 → 管理员；六个阶段；CEL（Common Expression Language）、Python 或 LLM 分类器作为评估器；跨会话的按用户预算），通过每家厂商自己的扩展机制强制施加到外来 harness 上——Claude Code hooks、Cursor hooks、Hermes hooks、ACP 权限请求——并采用失败即关闭的语义。观察 7.1 中的锁定机制，从上一层看过去，变成了一个适配器接口。统一的沙箱与出站流量栈：Linux 上是 bubblewrap 加 seccomp，macOS 上是自动生成的 Seatbelt 配置，Windows 上是 Job Objects——与语料在 Codex 内部记录的架构相同，在元层重新实现了一遍；外加一个 L7 中间人出站代理（自有 CA、按主机的规则、默认拒绝），其中托管着一个无密钥的凭据代理，真实令牌永远不进入沙箱，合成的占位符在传输途中被替换为真实凭据——Codex 也提供了这种设计（它的 network-proxy crate），在这里被提升到元层，覆盖所有被包装的 harness。可共享的会话：在服务端持久保存的对话记录，支持多设备同步、ACL 授权、审查评论、分叉，以及会话中途切换 harness。

同样富有信息量的是它不做什么：它不实现编辑循环，不实现仓库上下文，也不实现编辑应用策略——解剖图中 D3/D4 的核心留在这条线之下——而且它也不假装各个 harness 是等价的：逐 harness 的能力记录、厂商专属的 webhook 端点、一个 Claude 专属的 todos 字段，以及一个只属于 Codex 的 goal-mode 扩展，都按设计从“通用” API 中漏了出来。它的旗舰示例 Polly 是一个跨厂商的协调者-工人：一个以 Claude Code 为“大脑”、自己不写代码的编排器，把工作扇出给六个厂商 harness，每个任务一个 git worktree，并在编排者提示词中强制要求跨厂商审查——审查者必须与实现者来自不同厂商（机制层的护栏把关的是扇出和影响范围，而不是厂商身份）。就连它的克制也富有信息量：沙箱的施加按设计是不一致的（它把 Claude CLI 包进自己的沙箱中执行，却把 Codex 委派给 Codex 原生的沙箱模式），这证明 OS 级隔离很难被抽取成一项共享服务。而双重缺席在元层依然成立：百万行代码中，没有智能体框架，没有 RAG——除非你把它的两个基线依赖 claude-agent-sdk 和 openai-agents 算进去，而这恰恰就是第 14.2 节的要点。

14.5 Harness 演化的九十天

由于四月版的八个系统是重新固定版本而非被替换，语料包含一个受控的纵向样本：同一批 harness，跨一个季度做源码 diff。这个时间窗口可以用四种动向来刻画。

趋同变成了模仿。

四月的趋同大多是独立的重新发现；七月的趋同则有迹可循。Codex 逐字采用了 Claude Code 的 hook 事件词汇及其计划模式的人机工程设计；OpenHands 采用了 Claude Code 的插件清单格式、它的 task 工具签名和它的静态/动态缓存边界；OpenCode 读取 Claude Code 的 skills 目录；Hermes 的源码注释致谢了 OpenCode（编辑匹配器）、Codex（smart approvals）、OpenClaw（编排者提示词）和 Goose（上下文提示）。跨 harness 的谱系如今就写在代码里。

模式沿着语料向下扩散。

延迟加载工具从一个系统扩散到三个（外加七个 skills 变体）；只读计划模式从两个扩散到全部四个厂商原生系统；LLM 审批分类器从一个（Claude Code）变成两个（加上 Codex 的 Guardian）；轮次级检查点从一个（Mistral Vibe）变成三个；感知安全的调度器分区从一个变成两个。在这个领域，一项竞争性特色的半衰期目前以周来计算。

策略从文字中迁出。

本季度最清晰的修辞趋势（观察 7.3）：Codex 最新的模型提示词删掉了禁止提交和反镀金规则，改用功能开关；Mistral Vibe 删除了它的“Never Commit”硬规则，并以一份七级优先级契约重新奠定其提示词，在服务端做 A/B 测试；OpenHands 则在教授提交方法。随着模型把规范内化、harness 长出治理接口，行为策略正从提示词（模型阅读它的地方）迁移到配置（平台强制执行它的地方）。

代码树本身以平台的速度变化。

Codex 的工作区在一个季度内几乎翻了一番（Rust 代码从 62.1 万行增至约 112 万行，crate 从 89 个增至 126 个）——记忆、Guardian、市场插件、code mode、实时语音；Mistral Vibe 增长了 77%（从 3.56 万行增至 6.3 万行）；OpenHands 重新架构为 SDK，而它的应用仓库变成了一个自动化控制中心；Gemini CLI 宣布了品牌转向，并对免费档设置了门槛；该领域的先驱 Aider 进入社区维护状态，窗口期内只有 18 次提交。四月版的三条观察需要就地做实质性修订——耦合二分法（观察 7.1）、“规模意味着沙箱”的相关性（观察 10.2），以及协议位置的叙述（观察 13.3）——每一条都被九十天前尚不存在、或我们当时看不到的证据所纠正。这条方法学教训具有普遍性：在这个领域，清单式论断（工具数量、功能单元格、版本号）几周之内就会过时，而结构性论断（循环分类、子系统解剖、双重缺席）迄今为止被证明是经久的。我们在这一版中始终把两者区分开来。

观察 12。编码智能体 harness 在 2026 年上半年完成了它的平台转向，而这一转向的每一层现在都在源码中清晰可见：扩展基底（hooks、skills、插件）在所有生产系统中趋同；能力分发有了市场、注册中心、信任分级和智能体作者。厂商们为彼此存在磁盘上的状态发布导入器，并提供 MDM 级的治理层；harness 变成了可导入的 SDK，而框架厂商发布了 harness（第 14.2 节所说的合并）；智能体本身可以作为一个“模型”，挂在 OpenAI 兼容端点之后被调用；而一个 meta-harness 现在在同一个 API 之后编排着一支由十一个厂商 harness 组成的舰队——其中包括本文研究的五个系统——重新实现每个 harness 昂贵的部分（沙箱、策略），并对专有的部分（hooks、会话存储）进行套利。这个领域的竞争单元已不再是智能体循环，而是围绕它的生态接口。

15 讨论

15.1 作为实证验证的 Anthropic Effective-Agents 系列

2024 年 12 月至 2025 年 9 月间，Anthropic 发表了四篇就智能体设计给出规范性指导的工程文章：Building Effective Agents [16]、Effective Context Engineering for AI Agents [19]、Writing Effective Tools for AI Agents [18]，以及案例研究 How We Built Our Multi-Agent Research System [17]。贯穿这四篇文章的是一套连贯的设计哲学：手写循环优于框架抽象，少量高信号的工具优于“包装一切”的 API，即时的结构化检索优于预建索引的 RAG，编排者-工人模式优于扁平的单体，对智能体的规划保持透明，并把明确的上下文预算当作一门工程纪律。

十一个独立开发的系统（其中只有 Claude Code 一个来自 Anthropic）都与这些主张相吻合：

  • “除非必要，不要使用框架” [16]：11 个系统中有 0 个在智能体运行时中使用 LangChain、LangGraph、AutoGen、CrewAI、ADK、LlamaIndex、Pydantic AI、Genkit 或 Semantic Kernel（观察 13.2）。
  • “ACI 与 HCI 同样重要” [16]（这一概念源自这篇文章；Aizawa 等人 [18] 用实用的工具建议对其作了扩展）以及“少而精的工具” [18]：Aider 的 13 种多态编辑格式、Claude Code 的延迟加载工具、Codex 的自定义补丁格式、Hermes 的九策略编辑链，以及 OpenCode 按模型而定的工具面，都是在 ACI 上的重大投入（观察 8.4）。
  • “即时检索优于 RAG” [19]：11 个系统中有 0 个对代码使用向量嵌入；全部使用 grep、tree-sitter、glob 和文件系统，外加自动发现的 Markdown 上下文文件（观察 13.2）。
  • “对可并行、跨越多个上下文的任务使用编排者-工人” [17]：出现在 Claude Code（递归组合）、Codex（带扇出的线程树）、Gemini CLI（注册表 + 会话协议）、Mistral Vibe（task 工具）、OpenHands（并行委派）、Hermes（编排者角色 + 蜂群）和 OpenCode（并发子会话）中（观察 11.10）。
  • “在派生子智能体之前把计划保存到外部记忆” [17]：Claude Code 的 CLAUDE.md，Gemini CLI 的计划文件和 MEMORY.md 项目索引，Codex 的 AGENTS.md 层级及其由智能体维护的记忆根目录。
  • 面向长周期任务的“压缩 + 结构化笔记 + 子智能体” [19]：全部四个厂商原生系统——以及全部三个新成员——都同时实现了这三者。
  • “多智能体系统消耗的 token 约为聊天的 15 倍” [17]（对比的是单次聊天基线，而不是单智能体流水线）：这正是 Claude Code 共享提示缓存的分叉机制、Hermes 共享缓存的后台分叉与只返回摘要、以及 Gemini CLI 剥离思考内容（在记录响应时把扩展思考文本排除在持久化历史之外，使它永远不会重新进入缓存）背后的动机。没有这些优化，成本将高得令人望而却步。

这套指导中有一处张力需要指出。Hadfield 等人 [17] 告诫说：“与研究相比，大多数编码任务中真正可以并行的子任务更少，而且 LLM 智能体目前还不太擅长实时地协调和委派给其他智能体。”然而，本研究十一个系统中有七个（若算上 OpenClaw 协议层的变体则是八个）恰恰为编码工作流实现了协调者-工人模式。仔细审视会发现，所观察到的这些模式大多用于广度优先的探索阶段（并行调研代码库），而不是并行实现；一旦把分析单位从整个系统转移到单个工作流阶段，这与 Hadfield 等人的告诫是一致的。

15.2 极简主义论证

Mini-SWE-Agent 用一个极简脚手架和单个 bash 工具，取得了有竞争力的自报基准表现（SWE-Bench Verified 上 74% 以上），这削弱了“丰富的工具生态是必需的”这一假设。这一发现呼应了 CodeAct [3] 的论点：可执行代码可以涵盖离散的工具动作。仅就基准评测而言，生产系统中的大部分脚手架其实都是额外开销。

反方的论点是：基准只衡量了价值主张中很窄的一部分。生产系统（Claude Code、Codex、Gemini CLI、Mistral Vibe、OpenHands）在基准不奖励的方面投入巨大：

  • 安全：防止对用户代码库执行破坏性操作。
  • 用户体验：流式响应、丰富的终端 UI、进度追踪。
  • 可扩展性：支持自定义工具、MCP 服务器、插件。
  • 稳健性：处理边界情况、卡死检测、错误恢复。
  • 成本管理：提示缓存、上下文压缩、模型选择。

这些关注点在 SWE-Bench 上看不见，但对生产环境的采用至关重要。

15.3 安全即架构

安全是语料分布最分散的维度。Codex 采取纵深防御：OS 级沙箱加策略即代码加审批流程，从一开始就把安全当作首要的工程关注点，而不是后来才加上的东西。Gemini CLI 处在光谱上相近但更轻的位置：跨平台沙箱（复用操作系统自带的二进制程序），加上四种明确的审批模式（PLAN/DEFAULT/AUTO_EDIT/YOLO）和按模式的 TOML 策略。Claude Code 的三层系统（hooks → 分类器 → 对话框）介于纯自动化与人工监督之间。Mistral Vibe 的权限范围层级（命令/文件/URL 模式加智能体配置关卡）比 Aider 的二元确认更细粒度，但没有 OS 级的强制执行。OpenHands 可插拔的 SecurityAnalyzer 框架允许把基于规则的分析与基于 LLM 的分析结合起来。

四月版观察到，语料中规模最大的两个系统（当时 62.1 万行的 Codex，以及 56.8 万行的 Gemini CLI）恰好也是两个跨平台沙箱实现者，并把这种相关性解读为结构性的。扩大后的语料证伪了这种结构性解读，但保留了关于成本的论断：Hermes 和 OpenCode 规模相当，却没有任何 OS 级隔离，分别把安全预算花在了内容传播的威胁和权限粒度上（观察 10.2）。仍然成立的是，原生沙箱一旦构建，就是 harness 中代码成本最高的组件之一——Codex 把 bubblewrap 内置进了自己的代码树，而 meta-harness 在更上一层又把整笔账重付了一遍（第 14.4 节）。Aider 和 Mini-SWE-Agent 极小的安全面，对于它们的目标场景（面向受信任用户的开发者工具）来说是站得住脚的，但限制了它们在企业或自动化部署场景中的适用性。

15.4 模型-智能体协同设计论点

智能体脚手架与基础模型之间的耦合是双向的。

模型塑造智能体。

Codex 的逐模型提示词——现在是覆盖 GPT-5.2 到 5.6 家族的服务端下发目录数据，带有逐模型的工具模式和多智能体工具代际——明确表明，脚手架设计必须随模型能力一同演化，而厂商打算在不发布客户端的情况下推动这种演化。Claude Code 的扩展思考集成（budget tokens、thinking 块）利用了 Claude 特有的推理功能。Gemini CLI 的 ModelRouterService 把模型选择本身当作一项运行时调度决策，把每个请求分派给够用且最便宜的 Gemini 变体——并在一个季度内吸收了整整一代模型的更替（默认值从 2.5 换成 3.x）；同样的想法在 Hybrid LLM [84]、RouteLLM [83] 和 FrugalGPT 级联 [82] 中得到了形式化研究。Mistral Vibe 的 reasoning_effort 映射和 ThinkChunk 解析利用了 Mistral 的推理枚举。Aider 感知模型的编辑格式选择，让编辑策略适应每个模型的输出模式；OpenCode 在其工具注册表（GPT 家族模型得到补丁 DSL；其他模型得到字符串替换）和九种提示词的模型家族矩阵中，重新推导出了同样的想法。OpenHands 提供针对特定模型的工具预设（default、gemini、gpt5、planning）——协同设计甚至延伸到了一个多提供商系统的工具面。

智能体塑造模型的使用方式。

Claude Code 的延迟加载工具减少了提示词 token，改变了模型的有效上下文窗口。Claude Code 的提示缓存边界切分系统提示词以最大化缓存命中，提示词的结构既围绕逻辑组织，也同样围绕缓存经济学；Gim 等人 [81] 为这种做法所隐含的模块化注意力复用策略提供了系统层面的依据。Gemini CLI 在记录响应时就把扩展思考的轨迹排除在持久化历史之外，使它们永远不会泄漏到之后的缓存查找中（并在切换认证时剥离思考签名）。Mistral Vibe 的中间件管线允许把每轮的 token 预算策略与循环体正交地组合。OpenHands 的压缩器有选择地遗忘事件，塑造模型“记得”什么。

启示。

四个厂商原生系统（Claude Code、Codex、Gemini CLI、Mistral Vibe）可以同时优化这种耦合的两侧，让提示词、工具和功能随模型更新同步演化——Codex 通过它的服务端下发模型目录，做得最为直接。四月版据此推断，多提供商系统必然只能按最低公分母来设计；扩大后的语料表明这个推断过强了。Hermes、Pi 和 OpenCode 证明，只要刻意且集中地承担逐提供商条件代码的成本（观察 7.1）——逐模型的怪癖元数据、提供商配置插件、变换矩阵——就可以从多提供商的基底上用到完整的提供商原生优化菜单。多提供商系统无法复制的是更新回路：只有厂商能在模型发布当天在服务端重新调校脚手架的行为。Mistral Vibe 的“本家优先、通用后备”设计和“自有传输层”这一位置，都仍然是可行的中间路线，区别在于由谁承担维护负担。

15.5 脚手架-能力前沿（一种引导性直觉）

最后，我们给出的是一种引导性直觉，而不是一个形式化的假设：在固定的任务分布和固定的模型下，脚手架复杂度与观察到的任务成功率之间，似乎大致呈一条凹曲线。有一个底线，低于它智能体根本无法运作（没有循环、没有工具、没有记忆、没有结果）；有一个早期收益陡增的区域，在这里加入少量结构性元素（一个 bash 工具、一个读写工具、一个 Markdown 上下文文件）就能迅速提高成功率；还有一个收益递减的平台区，在这里继续投入脚手架，回报体现在运营方面的关注点（安全、用户体验、可扩展性）上，而不是完成率上。我们把这幅图景称为脚手架-能力前沿，并把它当作一个有待检验的假设，而不是设计空间中已被证明的性质。

文献中有两项独立结果与这幅图景相符，但并不能证实它。Mini-SWE-Agent 用刻意极简的脚手架在 SWE-Bench Verified 上报告了约 74% 以上的成绩，这表明对于前沿模型上 SWE-Bench 风格的任务，底线已经远低于大多数生产级脚手架。Lin 等人 [85] 报告说，他们的 Agentic Harness Engineering（AHE）系统从一个与 Mini-SWE-Agent 相当的只有 bash 的种子出发，利用可观测性驱动的反馈自动演化 harness，在 SWE-Bench Verified 上达到 71.9%。他们的组件级消融发现，带来提升的是结构性的 harness 元素（工具 +3.3 个百分点，中间件 +2.2 个百分点，长期记忆 +5.6 个百分点），而单靠系统提示词反而会让性能下降（−2.3 个百分点）；演化出的 harness 还能在四个模型家族之间迁移。我们把这解读为一项提示性证据：结构性的脚手架比文字层面的提示词策略更具可移植性，这与我们在架构层面（而非权重层面）对模型-智能体协同设计的讨论相一致。

一个操作性的定义至少需要：一个固定的任务分布 T，一个固定的模型 M，一个衡量脚手架复杂度的指标（代码行数、工具数量、结构性特征数量，或它们的某种加权组合），以及一个目标成功率 p。这样，“(T,M,p) 的最小可行脚手架”就是那些在 T 上使用 M 时经验成功率超过 p 的脚手架复杂度取值的下包络。我们在这里没有做这样的测量。要做到这一点，需要一项受控的跨系统运行研究，而本文刻意回避了这类研究（见第 15 节“效度威胁”）。我们把脚手架-能力前沿标记为一个留待后续实证工作研究的问题，并指出相关的最小值几乎肯定会随以下因素而变化：

  • 任务复杂度：多文件重构可能比单文件 bug 修复需要更精巧的工具支持。
  • 安全要求：企业部署需要基准所不衡量的脚手架。
  • 交互模式：长时间运行的交互式会话能从记忆管理中获益，而简短的基准运行并不需要它。

15.6 效度威胁

这种形式的研究有实实在在的局限，值得明确说明。

本分析依据的是源码阅读，而不是运行时测量。我们不声称知道这些系统中任何一个有多快；我们声称知道的是它们如何构建。凡是本文报告基准数字的地方，数字都来自系统自己的文档，而小数点后最后一位并不是有意思的部分。

架构比较背后的定性打分涉及主观判断。我们尽量把每个分数都锚定在一个具体的实现细节上，并欢迎任何阅读同样代码库、给出不同打分的人提出异议。我们刻意避免引用行号，并把所有代码规模数字标注为 2026 年 7 月的固定版本：语料中的每个系统都在积极开发中，更精细的精度在论文被读到时就已经过时了。所有版本都固定到确切的发布标签和 commit（表 3），2026 年 4 月的快照被保留用于第 14.5 节的纵向比较，而且——这是那个季度直接教给我们的一课——我们现在把清单式论断（我们为其标注日期）与结构性论断（我们预期它们会经久）区分开来。四月版的三条观察在这一版中依据新证据做了实质性修订；修订被就地整合，并在出现之处加以标注。

Claude Code 的分析是可复现性方面最薄弱的一环。它依据的是一份 2026 年 3 月公开流传的源码快照，而不是官方发布版，而实际发布的二进制程序此后已有相当大的演进（我们在变更日志层面追踪其演进，但不把变更日志中的说法当作源码证据）。这些架构论断仍应能对照公开的 claude-agent-sdk 和实际发布二进制程序的行为加以检验，但我们承认它与其他十个系统之间存在不对称：后者的源码树可以从公开的 Git 历史中轻松重新获取。

框架缺席这一发现（观察 13.2）证据有力，但在结构上是保守的。我们检查了依赖清单，并在三种语言中进行了导入 grep——做了两次，相隔三个月，覆盖包括 meta-harness 在内的十二棵代码树；我们没有追踪内部分叉、通过动态 importlib/require 加载的插件，或转译后的发行版。原则上，一家公司可能通过我们没有检查到的代码路径，在生产级软件工程智能体内部使用 LangChain。我们会感到意外，但不会震惊。

从 Anthropic 指南到观察结果的映射（观察 13.2）具有提示性，但本身并不能确立因果关系。正确的后续工作是对各家厂商的工程师进行访谈；我们没有做这件事。

我们还对每个系统做了独立比较，而不是让全部十一个系统在一套共享任务上运行。正面对比的执行研究可以把部分定性打分转化为可测量的量。但它的成本也会比本文高出一个数量级，我们选择了一个可以驾驭的范围。

16 设计建议：实践者指南

前面各节是描述性的，记录的是十一个生产级 harness 实际包含了什么。本节是规范性的：我们把观察结果提炼成可操作的建议，供设计新编码智能体的工程师参考。每条建议都引用支持它的观察，列出实现它的系统，并指出可能让人做出不同选择的权衡。凡是语料与 Anthropic Effective Agents 系列 [16,19,18,17] 一致的地方，我们把这种一致标注为跨来源的验证；凡是语料与该系列有所分歧或对其有所扩展的地方，我们也会注明。建议按子系统分组，大致按照实践者从零搭建一个智能体时会遇到它们的顺序排列。

16.1 循环架构

建议 1。从一个线性 while 循环开始；只有在出现相互正交的轮次策略时，才升级为中间件管线。证据：观察 5（循环复杂度不能预测基准表现）；Mini-SWE-Agent 的 50 行线性循环在 SWE-Bench Verified 上报告了 74% 以上的成绩（自报；见表 4 的脚注）。升级路径：一旦你需要三条或更多相互独立的轮次级策略（轮次上限、成本上限、自动压缩、上下文预算警告、只读模式），就采用 Mistral Vibe 的中间件管线模式——每条策略都成为一个可组合的中间件，而不是循环体中的一个新分支。

16.2 提供商耦合

建议 2。如果你发布基础模型，就与自家提供商紧耦合，并为可移植性提供一个通用后备适配器；如果你不发布，提供商原生的优化仍然可以用上——只是要为逐模型的元数据预留预算。证据：观察 7.1。Mistral Vibe 的“本家优先、通用后备”仍然是厂商的模式。对于多提供商 harness，Pi 的逐模型 compat 怪癖标志、Hermes 的声明式提供商配置和 OpenCode 的变换矩阵表明，缓存断点、思考档位和推理强度都可以从一个抽象层上用到——代价是一个需要持续维护的逐提供商调教层，集中地一次付清。

16.3 工具设计

建议 3。一开始只给一个 bash 工具。只在观察到具体的故障模式时才增加更多工具。证据：Mini-SWE-Agent 的单工具设计在基本没有工具基础设施的情况下，在 SWE-Bench 上报告了 74% 以上的成绩（自报）；Aizawa 等人 [18] 告诫说“更多的工具并不总能带来更好的结果”。一个常见的顺序是：当 bash 输出截断成为问题时，加入 read_file 和 write_file；当 bash 加 find/rg 用起来别扭时，加入 grep/glob；当整文件写入浪费 token 时，加入 search_replace。

建议 4。当工具数量超过约 15 个时，采用延迟加载工具。证据：Claude Code 的 shouldDefer 标志加 ToolSearchTool 把初始提示词缩小了约 40%；Codex 独立地收敛到 defer_loading 标志加 BM25 排序的 tool_search；Hermes 在 schema 会超过上下文窗口的 10% 时，把溢出的 MCP 目录折叠成三个由 BM25 检索的桥接工具。工具少于约 15 个时，这层间接带来的复杂度不值得；超过这个数目，提示词膨胀就会变得难以承受。

16.4 文件编辑

建议 5。让编辑工具的契约与模型档次相匹配：前沿模型用精确唯一子串替换，开放模型或较弱模型用模糊级联——无论哪种，都在工具层处理漂移，绝不依赖行号。证据：观察 8.4。前沿模型阵营已经收敛到精确契约（Claude Code；Mistral Vibe 在 2026 年年中删除了 SEARCH/REPLACE 工具，收敛到精确匹配；Pi 只增加了 Unicode/空白规范化和字节保真叠加）。容忍漂移的阵营服务于更广的模型范围（OpenCode 阈值为 Levenshtein 0.65 的九阶段级联、Hermes 的九策略链、Aider 的 RelativeIndenter）。Gemini CLI 的 LLM 编辑修复器子调用是正在兴起的第三种选择：用模型而不是阈值来修复匹配。避免基于行号的编辑：模型在行号上的漂移比在上下文匹配上更严重。

16.5 记忆与上下文

建议 6。在项目、用户和扩展三个范围自动发现分层的 Markdown 上下文文件——也去读邻居们的文件名。证据：所有管理仓库上下文的十一个系统都收敛于这一模式，而最新的系统会读取多种约定（Hermes：先找自己的文件，然后是 AGENTS.md、CLAUDE.md、.cursorrules；OpenCode：AGENTS.md/CLAUDE.md/CONTEXT.md 加远程 URL；OpenHands 把三个生态的文件作为带范围的规则摄取）。把顶层内容注入到系统提示词靠前的位置，当工具触及嵌套文件所在的子树时再即时呈现它们（Mistral Vibe、OpenCode、Hermes、Gemini CLI），并让模型持久保存经久的事实——通过直接编辑、有上限的快照文件，或一个经人审查的收件箱（观察 9.6）。

建议 7。在模型上下文窗口下方一个固定的缓冲处实施阈值压缩；逐字保留最近的尾部；增量地合并摘要，而不是从头重新摘要；并让同一个例程在溢出时被动触发。证据：Claude Code 在 13K token 缓冲之下触发，并在之后恢复文件；Gemini CLI 在 50% 时压缩，保留最后的 30%；Pi 和 OpenCode 把上一份摘要传回去合并（锚定/迭代式摘要），这能保留从头重新摘要会丢掉的早期决策；Mistral Vibe 把先前的用户消息重新注入压缩后的信封，并在轮次中途出现 ContextTooLong 错误时复用该例程；OpenHands 把溢出错误导向压缩。积极的压缩可以防范上下文腐化 [19]；保守的保留则让最近的推理保持连贯。

建议 8。不要针对代码构建 RAG。改用 ripgrep、glob、tree-sitter 符号提取和文件系统遍历。证据：观察 13.2；0/11 个系统使用向量嵌入做代码检索；Rajasekaran 等人 [19] 在实践中偏向 JIT 检索，他们所有的具体建议都指向确定性工具。代码具有丰富的确定性结构（路径、语言服务器、tree-sitter 解析结果），这是语义相似度无法复制的；而且代码每分每秒都在变化，使嵌入很快过时。

16.6 按部署场景划分的安全架构

建议 9。对于开发者工具（半受信任）场景：实现一个带权限范围模式的三模式审批系统（PLAN / DEFAULT / YOLO）。证据：Gemini CLI 的 PLAN/DEFAULT/YOLO 模式，Mistral Vibe 的四层权限层级（工具全局 + 工具专属 + 会话规则 + 交互式回调）；这与人类开发者对风险进行分级处理的方式相吻合。

建议 10。对于企业/共享/自动化场景：实现 OS 级沙箱，配合策略即代码和逐智能体的审计轨迹。证据：观察 10.2；Codex 和 Gemini CLI 提供原生跨平台沙箱（Linux 上是 Bubblewrap——Codex 中是内置的——macOS 上是 Seatbelt，Windows 上是受限令牌），Claude Code 则把 Anthropic 可复用的 sandbox-runtime 包装为可选功能。Gemini CLI 的实现表明，如果复用操作系统自带的二进制程序（Node 的 child_process 或等价物），而不是从零编写命名空间管道，成本是可以接受的。

建议 11。无论处于哪个档次，都把安全规则写成数据或专门的策略文件，而不是命令式代码——如果你支持 YOLO 模式，要在它下面保留一条底线。证据：Codex 带解析时校验内联示例的 Starlark execpolicy 规则，Claude Code 的 PreToolUse hooks，Gemini CLI 的按模式 TOML，OpenCode“最后匹配者胜出”的规则集。Hermes 补充了底线这一课：它的十二种硬性模式连 --yolo 都无法绕过，而绕过标志在模块导入时就被冻结，因此注入的内容无法在运行时将其翻转。策略即代码能经受住重构，并且可以独立于循环实现进行审计。

16.7 多智能体编排

建议 12。保持单智能体，直到你能指出一个具体的广度优先探索阶段，在那里并行的上下文隔离明显胜过串行搜索。证据：Hadfield 等人 [17] 告诫说，多智能体系统消耗的 token 约为聊天基线的 15 倍，并且“与研究相比，大多数编码任务中真正可以并行的子任务更少”；Mistral Vibe 的 task 工具把任务委派给子智能体（它的提示词鼓励并行启动多个），这对大多数编码工作流已经足够。

建议 13。提供一个 ACP 服务器：它已不再只是编辑器集成——它让你的 harness 能被宿主和元编排器消费。让你自己的子智能体留在进程内。证据：观察 13.3。一个 ACP 服务器现在能同时为你带来三类受众：IDE（Zed、JetBrains）、托管型 harness（OpenHands 把 Claude Code/Codex/Gemini CLI 作为可互换的 ACP 后端来运行），以及 meta-harness（Omnigent 通过 ACP 驱动 Goose 和 Qwen）。语料中十一个系统有六个提供了它。对于智能体 ↔ 智能体的网格拓扑，A2A 仍然只是 Gemini CLI 一家的押注——站得住脚，但未经证明。对于你自己运行时内部的主智能体 ↔ 子智能体协调，两者都不要采用（见建议 12）：生产系统使用的是进程内原语，就连跨进程的例外（Pi 的 JSONL 扩展、Hermes 的 SQLite 黑板蜂群）在这一角色上也都避开了标准协议。

16.8 可扩展性

建议 14。用 Skills 承载能力模板（工作流、领域知识、操作配方），用 MCP 做外部集成（Slack、数据库、内部 API）——优先级按此顺序。证据：观察 12.5：skills 现在在采用率上领先于 MCP（9/11 对 8/11），发现机制是跨厂商的（OpenCode 读取 ~/.claude/skills），分发也有了注册中心和来源证明。MCP 仍然是运行外部进程的合适层；Pi 展示了一个站得住脚的极简立场（skills 加上带 README 的 CLI 工具，不用 MCP）。如果你要安装第三方 skills，就把它们当作软件包对待：信任分级、扫描和隔离区（Hermes）正在成为基线 [89]。

16.9 不该构建什么（反模式）

建议 15。不要用 LangChain、LangGraph、AutoGen、CrewAI、LlamaIndex、Pydantic AI、Genkit、Google ADK 或 Semantic Kernel 来构建智能体运行时。证据：观察 13.2；语料中 0/11 个生产级 harness 使用这些框架——Gemini CLI 连 Google 自家的都不用。Schluntz 和 Zhang [16] 明确警告：“框架常常会制造额外的抽象层，遮蔽底层的提示词和响应，使其更难调试。”使用原始 SDK 调用——或者，按照 2026 年的推论（第 14.2 节）：如果你想要一个开箱即用的起点，harness SDK（Claude Agent SDK、openai-codex、openhands-sdk）如今就是框架层，并且内置了语料中的各种模式。

建议 16。不要为代码构建向量嵌入检索层。证据：观察 13.2；0/11 个系统这样做。确实出现的嵌入服务于对话记忆（OpenClaw 的默认混合搜索；Hermes 需选择开启的插件），而 Hermes 表明，在 64.2 万行的规模下，词法的 SQLite FTS5 就足以胜任这一角色。如果你认为你的领域需要语义代码检索，在加入这套基础设施之前，先在一个留出的任务集上证明它比 ripgrep + tree-sitter 更好。

建议 17。不要把每一个上游 SaaS API 都一对一地包装成工具。证据：Aizawa 等人 [18]：“我们观察到的一个常见错误，是工具仅仅包装了现有的软件功能或 API 端点。”应当加以整合。

建议 18。不要过度设计卡死检测——但要提供那些廉价的上限，它们只需十几行代码。证据：Claude Code 和 Codex 仍然没有自动化的卡死检测，却交付了生产质量的智能体。不过底线已经上移：就连 Mini-SWE-Agent 现在也给连续的格式错误响应和挂钟时间设了上限；OpenCode 的 doom-loop 检查是一个“三次相同调用”的计数器，触发后转为权限询问；Hermes 对调用签名做哈希，但发布时关闭了硬停止，选择相信警告。OpenHands 的五场景 StuckDetector 和 Gemini CLI 的哈希 + LLM 混合服务仍属于平台级的投入。

16.10 最小可行 harness

作为一个具体的起点，代码清单 3 用约 90 行 Python 勾勒了一个最小可行 harness，结合了上面推荐的各种模式：线性循环（Mini-SWE-Agent）、中间件式策略（Mistral Vibe）、四个工具（bash、read、write、search_replace）、分层 Markdown 上下文自动发现（全部四个厂商原生系统），以及阈值压缩（Claude Code/Gemini CLI/Mistral Vibe）。它不是一个拿来即用的库；它是一个供复制和特化的脚手架。

上面的脚手架刻意省略了语料中存在分歧的功能：沙箱（建议 9–10 取决于部署场景）、多智能体（建议 12 主张推迟）、MCP/Skills（建议 14 属于可扩展性，而非核心）。从这里开始，进行测量 [17]，只添加你观察到的故障模式所要求的最小部分。

观察 13。代码清单 3 中的 90 行最小可行智能体直接实现了 18 条建议中的 10 条，并与其余八条兼容。它做到这一点时没有任何框架依赖、没有 RAG、没有向量存储、没有多智能体编排，也没有沙箱，这与双重缺席（观察 13.2）以及 [16] 的“从简单开始”原则相吻合。我们推测（未经证明），这个脚手架在前沿模型上运行，可以达到 Mini-SWE-Agent 的 SWE-Bench 成绩，而要超越这些成绩，主要是模型能力的问题（观察 5），而不是脚手架的问题。

17 结论与未来工作

本文给出了十一个 LLM 驱动的编码 harness 的源码级解剖——每家主要商业 LLM 提供商各一个（Claude Code/Anthropic、Codex/OpenAI、Gemini CLI/Google、Mistral Vibe/Mistral），外加七个开源设计——同时还有一个 meta-harness 对照点、一份一个季度演化的纵向 diff，以及对该领域转向平台的阐述。

17.1 要点

  • 架构很重要，但不是以当前讨论所暗示的方式。智能体循环的复杂度不能预测基准表现（Mini-SWE-Agent 的 50 行循环报告的结果处于前沿区间）。但它确实能预测生产就绪程度：安全基础设施、用户体验、可扩展性——并且越来越多地体现在客户端和传输层上，最大的系统如今把大部分体量都放在了这里。
  • 模型与智能体的关系是协同演化的，而耦合关乎更新回路，而非能力。提供商原生的优化（缓存边界、思考预算、针对特定模型的提示词、路由）从耦合光谱的两端都被用到：厂商系统原生地使用，而 Hermes、Pi 和 OpenCode 则通过集中承担逐提供商调教的成本，从多提供商的基底上使用。只有厂商才保有的是服务端协同演化——Codex 能随每次模型发布，从一个目录端点重新调校提示词、推理档位，甚至它的多智能体工具，无需更新客户端。
  • 安全在架构上代价高昂——而且是一种选择，而不是规模的必然结果。Codex 的跨平台沙箱（现在内置了 bubblewrap）仍然是一笔基准永远不会衡量的可观投入，而 meta-harness 在更上一层又把同一笔账付了一遍。但四月提出的“规模意味着沙箱”的相关性被打破了：Hermes 和 OpenCode 位列最大的系统之中，却没有任何 OS 级隔离，转而把投入花在防御内容传播的威胁和语法感知的权限控制上。
  • 多智能体编排收敛到层级模式，而协议找到了第三种角色。协调者-工人的形态现在出现在七个系统中。ACP 不仅服务于编辑器 ↔ 智能体的边界（语料中有六个采用者），还服务于一个超出其设计初衷的角色：托管 harness，OpenHands 把 Claude Code、Codex 或 Gemini CLI 作为可互换的后端来运行。A2A 仍然是 Gemini CLI 对跨厂商网格的押注。九个多智能体系统中有八个的子智能体协调仍在进程内完成。
  • 可扩展性标准尘埃落定：skills 领先。当 Pi 打破平局——实现 agentskills.io，同时直接拒绝 MCP——之后，Skills（9/11 个系统）超越了 MCP（8/11）。Skills 层有了注册中心、信任分级、来源验证、跨厂商发现（OpenCode 读取 ~/.claude/skills），以及第一批智能体作者（Hermes 的自我改进循环、Gemini CLI 的提取收件箱）。
  • 双重缺席是真实的，经过了复核，现在也有了历史解释。在十一个系统、大约四百万行代码中，没有任何智能体运行时使用通用智能体框架，也没有任何一个对代码使用 RAG——全部依赖手写的异步循环和确定性的结构化检索。这一缺席在语料扩大到三倍和为期三个月的复核中依然成立，印证了 Anthropic 发布的指南 [16,19] 和独立的 AHE 结果 [85]。它的归宿是第 14.2 节所述的 harness 与框架的合并。
  • Anthropic 的 effective-agents 系列预见了我们所观察到的架构。2024 年 12 月至 2025 年 9 月间发表的四篇工程文章，与在十一个独立开发的系统中记录下来的模式高度吻合。这反映的是共同的经验现实、受指南塑造的设计，还是两者兼有，是一个本身就值得探究的问题。
  • 这些分析可以直接付诸行动。第 16 节为构建新 harness 的实践者提炼出 18 条具体的、有证据支撑的设计建议，以及一个直接实现了其中十条的 90 行最小可行 harness 脚手架（代码清单 3）。结合源码审计，据我们所知，这是这门学科第一份不出自单一厂商白皮书的、基于证据的操作指南。
  • 平台转向已不再是假说。四月版以“CLI 即框架假说”谨慎提出的内容，第 14 节现在把它记录为一次已经完成的转向：harness 以可导入的 SDK 形式发布，而框架厂商发布了 harness（第 14.2 节所说的合并）；能力分发有了市场、注册中心、信任分级 [89] 和智能体作者；厂商为彼此存在磁盘上的状态编写导入器，并提供 MDM 级（移动设备管理）的治理；智能体本身可以作为一个“模型”，挂在 OpenAI 兼容端点之后被调用；而一个 meta-harness 在同一个 API 之后编排着十一个厂商 harness——其中包括本文研究的五个系统（第 14.4 节）。周边生态的数据也指向同一方向：MCP 拥有 8,000 多个服务器的生态，并出现了应用商店式的策展病症 [86]；skills 被形式化为可组合的包 [87]，并有了类似 npm 的包管理器 [88]；22–29% 的 GitHub 项目带有智能体的痕迹 [91]；以及把开发视为编排的“SE 3.0”框架 [92]。开发者不再是用框架编程，而是在框架内部编程；观察 7.1 中的厂商锁定，正在变成操作系统和 IDE 一直以来都会产生的那种结构性锁定 [90]——而元层已经在对它进行套利。Harness 是会整合为少数几个主导平台、分裂为可互操作的运行时，还是从上方被商品化，是下一年的竞争性问题；而这三种结局的架构前提，今天都已存在于源码之中。

17.2 未来工作

我们的分析引出了以下几个方向：

  • 统一的评测框架：在正确性之外同时评估安全、用户体验、成本效率和可扩展性，弥合基准表现与生产就绪之间的差距。
  • 参考架构规范：把我们识别出的模式（事件溯源、策略即代码、上下文分叉、延迟加载工具、中间件管线、基于哈希的循环检测、即时仓库上下文）形式化为一个可复用的架构框架。
  • 安全策略的形式化验证：针对策略即代码的系统，确立在给定策略配置下哪些智能体动作被允许的保证。
  • 模型-智能体协同演化的实证研究：追踪智能体脚手架如何随模型代际变化，并量化针对特定模型的优化对性能的影响。Lin 等人的 AHE 系统 [85] 证明自动的 harness 演化已经可行；纵向研究现在可以追踪自动演化的脚手架与手工打造的脚手架在不同模型代际之间的比较。
  • 跨系统基准套件：在受控条件下让全部十一个系统运行相同的任务，从而直接比较我们识别出的架构权衡。
  • 智能体间协议采用研究：追踪 ACP 的三种角色（编辑器集成、托管 harness，以及通过 A2A 实现的跨厂商网格），并测量托管型 harness 拓扑（例如 OpenHands 的 ACP 后端和 Omnigent 的适配器舰队）的开销。
  • 纵向延续：四月/七月这一对快照把本研究变成了一个时间序列；每季度重新固定版本，就可以定量地而非轶事式地测量模式扩散的半衰期、提示词变薄的程度和平台化的轨迹。
  • Meta-harness 经济学：从上方商品化（第 14.4 节）能否持久地获取价值，以及针对 harness 能力的一致性测试台方法是否会成为标准接口。
  • Anthropic 与业界一致性的因果分析：通过访谈、设计文档考古和提交历史关联，区分公开指南的影响与趋同的工程实践。
